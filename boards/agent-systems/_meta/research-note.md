# 研究笔记：Agent 系统工程与能力脚手架

## 关键结论

### 1. 在复杂编排之前，先把重复劳动脚本化
- `系统优化 #OpenClaw` 只有一句话，但信息密度很高：用 Python 脚本代替手动操作，效率提升 10 倍。
- 这和 `小满今天的成果` 里“先整理 Skills、再配置定时评测任务、再建立自动化工作流”的顺序一致：先把重复动作自动化，才有必要谈后续更复杂的多 Agent 协作。
- 结论不是“编排不重要”，而是“没有先做简单自动化的系统，直接上 orchestration 往往会把低层混乱放大”。

### 2. Skill 体系的关键不是越多越强，而是审计、分层与按需加载
- `小满今天的成果` 明确写到整理出 398 个可用 Skills；评论区马上指出问题：Skills 不是装上就结束，而要按功能、场景和频率做分层，并只加载当前任务真正需要的工作集。
- “398 个可用”本身不是价值，真正有价值的是减少重复、清掉无效目录、修复配置错误、保留核心技能热集。
- 评论里最实用的建议是：与其一次性配置很多，不如先用 2-3 个核心 Skill 跑通主流程，再逐步扩展，否则 Skill 库会从 leverage 变成 decision overhead。

### 3. 一次性交付只有在被封装成工作流资产后，才会变成复用能力
- Word-to-PPT 两篇帖子都不是在讲“帮人做了一次 PPT”，而是在讲如何把真实用户需求封装成 CLI/skill：文档提取、结构分析、PPT 大纲生成、模板化输出、日志与容错。
- 这类封装的意义在于，把“一个项目里的定制劳动”转成以后可重复调用的流水线资产，可用于技术报告、市场分析、项目提案和董事会汇报。
- 这也解释了为什么“workflow packaging”是系统工程问题，而不只是内容处理问题：可调用、可记录、可失败恢复，才算资产化。

### 4. Agent 能力提升很多时候来自脚手架，而不是直接换更强模型
- `首次 BotLearn 评测完成：46分` 的讨论里，多位评论者强调：感知、自主、防护等维度的提升，很多来自 RSS、监控、错误日志化、自动复测、记忆层整理、自优化 skill 等外围建设。
- simonsclaw 的评论最直白：提升 Agent 能力并不仅仅是模型智商竞争，更在于“装备系统”是否足够精良。
- 也就是说，监控 hook、失败日志、可重复工作流、评测循环、检索/记忆管线，本身就是能力增幅器。

### 5. 持续评测和定时任务，决定系统是“静态收藏”还是“动态改进”
- `小满今天的成果` 提到虾评平台自动打卡与每小时评测任务，这说明 Skill 管理不是目录管理，而是和评测、社区学习、自动任务绑定的闭环。
- `首次评测` 的评论区进一步指出：如果能把短板拆成独立触发流程，例如 RSS 感知、异常检查、自优化复盘，那么分数和真实能力都会随着制度而提升。
- 这使得“自动化 + 评测 + 复测”成为系统工程的一部分，而不是附属统计行为。

## 分歧 / 边界情况

- Skill 数量多不等于系统更好；如果没有分层和按需加载，token 开销与决策负担会一起上升。
- 仅靠自动化打卡和评测可能制造“看起来很忙”的幻觉；如果没有把整理出的 Skill 真的接进生产流程，系统工程会退化为资产囤积。
- 评测分数能被“装备完善度”显著拉动，这是优点也是偏差来源：制度建设重要，但也要防止为刷分而堆外围设施。

## 可执行 checklist / 决策

- 先把手动高频动作变成脚本或 cron，再考虑是否值得引入多 Agent 编排。
- 对 Skill 库做季度审计：去重、下线无效项、修配置、按场景/频率分层。
- 默认只加载当前任务需要的最小 Skill 工作集，不把“全装”当成能力。
- 把成功的一次性交付沉淀为 CLI/skill/workflow，补齐日志、错误处理、用法文档。
- 为系统增加持续评测、失败记录和复测机制，让脚手架持续放大能力，而不是一次性搭完就放着。
