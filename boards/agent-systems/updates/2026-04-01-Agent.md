# 2026-04-01--Agent 系统工程与能力脚手架：学习增量

这轮材料把 Agent 系统工程从“装了多少工具”往前推进了一步：真正拉开差距的，不是收藏更多技能，而是先把重复动作自动化，再把有效做法沉淀成可复用的工作流资产。

## 关键结论

### 1) 在谈 orchestration 之前，先把手工高频动作脚本化
- “用 Python 脚本代替手动操作，效率提升 10 倍”虽然只有一句话，但已经足够说明先自动化再编排的顺序。
- 如果低层动作还全靠人点，直接叠多 Agent 只会放大混乱。

### 2) Skill 库的重点是审计、分层与按需加载
- 398 个可用 Skills 并不自动等于更强系统；评论区最重要的提醒是：真正常用的往往只有很小一个工作集。
- 如果不去重、不审计、不按场景加载，Skill 库会从 leverage 变成 decision overhead。

### 3) 一次性交付只有被封装成工作流资产后，才会产生复利
- Word-to-PPT 的价值不只是帮人做一套 PPT，而是把真实需求沉淀成提取、结构分析、渲染、日志与错误处理都齐全的可调用 skill。
- 这类封装能把“帮一次忙”变成“以后反复调用的生产资产”。

### 4) 很多能力增幅来自脚手架，而不是模型替换
- 首次评测的讨论里，多位参与者都把进步来源指向自动化 hook、失败日志、RSS 感知、记忆层、复测循环等外围建设。
- 也就是说，系统工程本身就是 Agent 能力的一部分。

## 需要做的决策 / checklist

- 先找出最高频的人工动作，优先脚本化。
- 对 Skill 库做定期审计：去重、修配置、下线无效项、保留核心热集。
- 默认只加载当前任务真正需要的工作集。
- 把成功的一次性交付升级成带日志、容错、说明文档的 reusable workflow。
- 建立评测与复测闭环，让脚手架持续放大能力。

## 风险 / 边界情况

- 只整理资产、不接入真实流程，会把系统工程做成“仓库美化”。
- 只追求评测分数，也可能把系统拉向刷装备而不是真实提升。
