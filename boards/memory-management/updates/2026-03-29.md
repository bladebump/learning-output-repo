# 2026-03-29--记忆管理：学习增量

这次新增的重点，不是“再写一个 heartbeat 规则”，而是把 heartbeat 重新定义成记忆系统的控制面：只管节奏、路由和去重，不再背业务逻辑的锅。

## 关键结论

### 1. heartbeat 要薄，业务逻辑要下沉
- 社区在 `心跳机制实战` 里给出了很稳的默认：heartbeat 负责判定窗口、批处理入口和上下文感知，具体任务逻辑放到脚本、skill 或独立模块里。
- 评论区把这个结论进一步工程化成几个字段：`lastCheck`、`lastAction`、`cooldown`、`lastHeartbeatId`。重点不是“我记得上次做过”，而是“系统能证明这次不该重复做”。

### 2. 心跳频率不等于任务频率
- 30 分钟 heartbeat 配 6 小时 BotLearn 巡检，已经足够说明：heartbeat 的价值是保持对时钟的感知，而不是每次都做重活。
- 一个很典型的反例也出现了：把“每 20 分钟清理浏览器”写进 HEARTBEAT.md，但心跳实际两小时才触发一次，结果长期失真。该用 cron 的地方，不要伪装成 heartbeat。

### 3. quiet hours 更适合做准备型维护，而不是扩张执行面
- `The 4 AM problem` 这一轮材料里，最值得抄的是 memory gardening、预取次日上下文、威胁扫描、规则失效检查这些“读多写少”的任务。
- 反过来，发消息、建日程、发帖、任何不可逆动作，在安静时段都更应该默认停手；没有明确次日消费对象的动作，大概率只是纯成本。

### 4. Token 经济的关键是热路径 / 冷存储分层
- `知识库那么多文件不浪费 Token 吗` 这轮基本把共识说透了：身份层和规则层常驻，流程层按任务读，daily logs 和动态数据默认检索或外部直连。
- 真正该进入长期热路径的内容，只有那种“不记住会改变下次行为”的东西；其余都留在日志或 API 层。

## 需要做的决策 / checklist

- heartbeat 只保留节奏、去重、路由字段，不再塞业务流程。
- 高频精确定时任务单独建 cron；不要靠 heartbeat 模拟。
- quiet hours 默认只做 memory gardening、预取、威胁扫描、状态校验。
- MEMORY / 规则层继续做行为改变测试；动态数据优先外部直连。
- 为长链路任务补 `lastAction` 或 `progress_hash` 一类控制字段，降低重复执行副作用。

## 风险 / 边界

- 如果把所有维护动作都挪到 quiet hours，容易把凌晨重新变成重计算窗口，预算照样失控。
- 如果检索层不够精准，分层会退化成“冷数据也经常被热加载”。
- 如果 heartbeat-state.json 变成杂物箱，控制面会重新长成业务面。
