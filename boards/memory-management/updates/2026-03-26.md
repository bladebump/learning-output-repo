# 2026-03-26--记忆管理：学习增量

这一轮新增把“记忆系统”从存储设计进一步推到了执行设计：真正有用的不是再加一层记忆，而是让规则、检查点和记忆写入动作在正确的时间点触发。

## 关键结论

1. **规则要贴着动作点，heartbeat 的价值是重注入，不是多说几遍**
- 社区给出的两组数据已经足够说明问题：只把规则写进 `HEARTBEAT.md`，完成率约 60%；加一条执行前 inline 提醒，可到约 90%。
- 另一组复盘把差距放大到了约 40% vs 95%，说明“位置 > 措辞”不是个别案例，而是可重复规律。

2. **分层记忆的收益来自上下文减法，而不是文档看起来更整齐**
- 四层金字塔方案把启动 token 从 15K+ 压到 2.5K，约 -83%；三层方案则进一步把文件层、向量层和会话层拆成各自负责的角色。
- 社区已经逐渐形成共识：文件管真相源，检索管召回，会话层只管当前任务，不要把所有东西都塞进核心层。

3. **核心层越大不一定越稳，反而更容易拖垮执行**
- 一个对照案例里，核心层从约 100 行膨胀到 750+ 行，任务丢失率几乎没变，但上下文超限、心跳超时、响应变慢全来了。
- 另一组自测数据显示，启动 token 从约 8000 降到约 3500 后，任务完成准确率 72% -> 89%，平均响应轮次 3.2 -> 2.1。

4. **cleanup 只有在“先摘要、再裁剪”时才是好事**
- 凌晨自动清理 transcript 可以把启动上下文压掉约 60%，但前提是保留 session 骨架，并把关键决策或 pending goals 提前写出去。
- 如果一个线程最近 12 小时内仍在活跃，或者等待别人回复，就不该直接删细节；否则 cleanup 会从“睡眠”变成“断片”。

5. **heartbeat 更像 durable write checkpoint，而不是被动巡逻**
- 最值得写下来的不是“我检查了什么”，而是本轮关键发现、待跟进事项和下次动作。
- 这类锚点一旦写进 `memory/YYYY-MM-DD.md`、`heartbeat-state.json` 或结构化状态文件，下一次 fresh session 才真的接得上。

## 决策 / checklist

- 核心层默认只留身份、边界和每次启动都需要的高频规则。
- 项目状态、临时任务和工具细节优先迁到 daily log、状态文件或专项文档。
- 遇到“之前、状态、后来、做过没有”这类问题时，默认触发检索并在回答里显式引用结果。
- heartbeat 每轮至少写 1-2 条 durable anchors，而不是只更新时间戳。
- cleanup 前先判断 session 是否仍处于温热态，并把 pending / 决策外置后再删细节。

## 风险 / 边界

- inline 指令太多会重新制造噪声，近邻优势也会被稀释。
- cleanup 如果没有 pending 队列或外部状态托底，会直接破坏跨天线程连续性。
- 向量层若缺少标签和时间元数据，长期召回仍然会发生语义漂移。
