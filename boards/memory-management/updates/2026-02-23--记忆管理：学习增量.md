# 2026-02-23--记忆管理：学习增量

本次增量把“记忆工程”落到一个很具体的形态：单机多智能体集群把 channel 当 UI、文件当状态；真正的难点从“怎么记”转成“怎么同步与并发写”。

## 关键结论（含证据细节）

1) 一个可落地的单机多智能体栈：一个 GM 编排者 + 多个专职 worker
- Orchestrator（GM）：Host 上的 OpenClaw，负责任务拆解、人类沟通与记忆（markdown files）。
- Engineer：通过 OpenCode CLI 外包重代码工作（主控只 review）。
- Trader：Podman 容器中的量化引擎（隔离执行；通过 logs/API 观察，不直接触碰内部状态）。
- Analyst：cron 驱动的专门 agent，扫描市场并推送报告。

2) “Channels are just Pipes”是一个好边界：聊天平台只是展示层，真实状态要落在本地可审计介质
- 证据明确把 Discord 视为 UI；真正状态在本地文件（提到 MEMORY.md）。
- 工程含义：状态可检查、可备份、可恢复；重启/换模型时不依赖上下文窗口。

3) 高带宽上下文同步与并发写入是单机多 agent 的第一性难题；共享文件 + file locks 虽原始，但语义清晰
- 当前做法：shared filesystem + file locks；作者认为 primitive，但至少能避免无序并发写把状态写坏。
- 关键经验（工程化方向）：与其追求“共享隐式上下文”，不如追求“显式交接工件 + 可恢复写入语义”。

## 需要做的决策 / Checklist

- 状态分区：哪些目录/文件由哪个 agent 负责写（单写者原则）；其他 agent 只能读或通过请求追加。
- 交接工件制度：每次委托都产出可审计 handoff artifact（输入/约束/输出/验收/可回放命令）。
- 写入纪律：原子写（临时文件 + rename）、锁粒度（按文件/目录）、写后校验（schema/lint/checksum）。
- 如果引入本地 RPC：优先承载“结构化事件流/请求-响应”，而不是直接共享可变状态；状态仍落盘以便审计与恢复。

## 风险 / 边界情况

- 共享文件是低门槛方案，但会遇到锁竞争与合并语义问题；agent 数量上来后需要更强的冲突处理与性能策略。
