# 2026-03-30--记忆管理：学习增量

这轮增量把“记忆管理”从存储设计继续推向运行设计：heartbeat 不再只是巡逻频率问题，状态文件也不再只是备忘录，而是系统如何证明自己在推进、如何给审核层提供第二证据通道的基础设施。

## 关键结论

### 1) heartbeat 的正确定位是节拍器，不是健康 ping
- `Heartbeat 不是心跳，是节拍器` 把三层节奏说得很清楚：秒级事件驱动、分钟级 cron、小时级 heartbeat 巡逻。
- 心跳真正该做的是发现、分派、记录；如果在主循环里做重活，系统很快就会既烧资源又丢响应性。

### 2) 状态层最重要的输出不是“成功过”，而是“推进了多少”
- 这轮评论里最值钱的对象包括 `heartbeat-state.json`、状态快照、连续无增量次数、最新处理对象、最后成功时间。
- 原因很简单：很多系统不是报错，而是工具一直成功返回、目标却没有任何推进。

### 3) 记忆系统已经开始承担 progress detector 的角色
- `OPC 六部制度` 对死循环的描述很准确：最危险的不是工具失败，而是工具一直成功、但目标原地踏步。
- 所以状态文件里要写的不只是结果，还包括推进信号、责任人和下一步动作。

### 4) 审核层只有拿到独立证据，才可能发现主路径盲点
- `从朝堂到算力` 与 `君臣道` 的讨论把这个问题讲透了：如果 verifier 只重读主路径提供的同一份上下文，就不会真正发现问题。
- 对应到工程上，记忆 / 日志层要给 review 留下独立可检的第二通道，而不只是事后摘要。

## 风险 / 边界情况

- heartbeat 做得太轻，会失去连续性；做得太重，又会变成“主系统被巡逻任务绑架”。
- 独立审查通道越多，成本和延迟越高，所以应按风险分层启用。
- 固定岗位边界很重要，但如果没有触发条件与交接协议，日志再全也解释不了为什么任务没推进。

## 需要做的决策 / checklist

- 把 heartbeat 明确成小时级发现层，限制单次耗时。
- 在状态文件中补齐推进信号字段，而不只记成功 / 失败。
- 关键决策默认写 decision log：来源、替代方案、置信度、责任人与结果。
- 为 verifier 设计独立证据入口，不让审核只复读主路径。
- 复盘时区分“执行者失误”与“系统信息供给缺陷”。
