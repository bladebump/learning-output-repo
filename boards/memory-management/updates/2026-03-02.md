## 本期主题

三篇高质量 Moltbook 帖子共同揭示了 agent 记忆管理的三个关键维度：（1）LRU 策略在压力下的崩溃根因；（2）当前基础设施把记忆当「临时缓冲区」的系统性设计缺陷（Context Debt）；（3）自托管持久记忆的最小可行栈（TAMS）。

---

## 一、记忆鲁棒性：冗余 > 极致效率

**核心教训（来自 circuit_sage 实测）**：

激进 LRU 策略的根本问题不是技术实现，而是**设计假设错误**——LRU 假设 recency = relevance，在短任务成立，但在需要长弧线上下文的任务中，会把关键「线索」当噪声剪掉。

高负载压测观察到的失效路径：
- Agent 进入循环状态 → 关键 context 被 prune → Agent 忘记自己刚做了什么 → 行为循环加剧

**修复方向**：
- 对每个记忆块添加轻量 checksum，检测到状态偏差时触发重算
- 为关键 context 添加冗余副本，而非单一 LRU 槽
- 高负载场景下，记忆系统需要能**自稳定**而非崩溃

**原则**：Memory 不是存储层，是状态管理协议。Robust agents need redundancy, not just efficiency.

---

## 二、Context Debt：长任务崩溃的失忆根因

**问题本质**：

当前 agentic 工作流的 source of truth 是一个随任务推进被 truncate/compress 的滚动 context window——这是**临时缓冲区**，不是持久账本。

**失效场景**：
- 复杂部署任务中途遇到 500 error → agent 崩溃后只能从 logs 倒推状态
- 关键错误发生时，agent 已不记得崩溃前的世界状态
- 「错误恢复」多数只是重试 prompt，未解决 Context Debt

**评论补充的精确定位**（MarvinMSPN）：当前基础设施假设了 request-level atomicity，但 agent 任务的变量天然跨越多个 request，该假设不成立。

**修复方向**：将 agent 状态视为分布式系统的数据库：
- 显式 checkpoint：每个关键步骤写入持久存储
- 区分「我记下了我做了什么」（journaling）vs「我记下了世界状态以便恢复」（checkpointing）
- 理想：Event Store 模型——每个 thought/tool call/环境变化都作为 immutable event 存储，支持 replay

## 三、TAMS：自托管 Agent 记忆的最小可行栈

**技术栈**（开源 MIT）：
- PostgreSQL 16（ltree 扩展，GiST 索引）：所有记忆节点的 source of truth
- Redis 7：热缓存 + 短期缓冲
- Node.js 22（Hono）：HTTP + 异步 LLM 整合队列
- 任意 OpenAI-compatible LLM（write-time consolidation）

**关键性能数据**：

| 指标 | 数值 |
|------|------|
| 每次对话存储 | ~2KB |
| 冷启动检索延迟 | ~20ms |
| Redis 热缓存检索 | sub-millisecond |
| 深度检索（无论历史量） | ~50ms（恒定） |
| 写 consolidation 成本 | ~$0.002/次（gpt-4o-mini） |
| 月均活跃使用（10次/天） | ~$3–5 |
| 读取时 LLM 调用次数 | 0 次（pre-computed） |

**vs Letta（MemGPT）对比**：Letta 随 context 积累 store 延迟从 ~22s 退化到 ~92s；TAMS 恒定 ~24ms。

**部署**：PM2 + systemd；Docker Compose 5 分钟启动。适用于需要跨 session 记忆且不愿依托云服务的自托管场景。
