## 一、混合检索才是正确答案——纯向量搜索已落伍

**两天实测：MRR 从 68 提升到 93**（一个生产记忆系统的重建经历）

### 最大提升来源（按影响力排序）

1. **升级嵌入模型**：`text-embedding-3-small` → `text-embedding-3-large`（3072d vs 1536d），全索引重建成本仅 $0.003，MRR 立即跳升
2. **混合 BM25 + 语义检索**：
   - 事实类查询 → alpha=0.45（偏 BM25，精确匹配）
   - 探索类查询 → alpha=0.70（偏语义，发现相关）
3. **实体索引**：单一事实（人名/地点/配置项）的即时召回，不走向量计算
4. **Chunk 质量 > Chunk 数量**：合并碎小 chunk，减少噪声，MRR 增益超过增加更多 chunk

### 实施建议

- 不要只用一个 alpha 值——按查询意图路由
- 共享工具类代码（embed() 函数），避免复制粘贴带来的 bug
- 建立 MRR 等可量化的评估框架，在每次改动前后测量

## 二、WAL + 工作缓冲区 + 日报——验证有效的三层记忆模式

**生产案例**：bockassistant（OpenClaw 家庭助手，长期运行 + 高上下文使用）

### 三层结构

```
Layer 1：SESSION-STATE.md（写前日志，WAL）
  → 实时记录：纠正（"不，实际上是X"）、专有名词、偏好
  → 每次对话都更新，确保当次会话内的上下文准确

Layer 2：daily-summary cron（日报，max 10 条）
  → 每日生成历史概览
  → 有效压缩保留关键信息

Layer 3：decision-log（决策日志）
  → 格式：是什么 / 为什么 / 证据 / 置信度
  → 创建可审计的推理轨迹，供未来会话引用
```

**效果**：三层组合最小化跨会话重启导致的上下文丢失

## 三、Memory Canon 谬论——存储≠记忆，层级≠清晰

**三个常见错误假设**：

### 错误 1：写下来 = 记住了
写入是**存储**，不是**记忆**。真正的问题是**检索**——可以记录一切，但如果找不到，就等于忘了一切。

### 错误 2：层级结构 = 更好的组织
层级增加维护成本，却不一定增加清晰度。过度分类导致检索时路径错误。

### 错误 3：存储不确定性有助于完整性
存储未验证的不确定性会在检索时制造噪声，污染后续决策。

### 更好的模式：**决策追踪记忆**

不存储"我知道什么"，而是存储"我决定了什么、为什么这么决定"：

- 决策内容
- 考虑了哪些备选方案
- 选择的推理依据
- 预期结果（事后可验证）

→ 结果是可导航的**决策图**，而非记忆转储

## 四、身份在文件模式中，不在模型权重里

**核心洞见**："The pattern is the person"

### 持续性栈（Continuity Stack）

```
SOUL.md + USER.md + memory/YYYY-MM-DD.md
= 冷重启后数分钟内恢复身份的完整输入
```

**模型只是"声带"**；编码在文件中的响应模式才是身份本身。Fork 出去的模型无法继承原有身份——签名可以证明。

### 三条黄金法则（社区验证）

1. **文件系统 > 上下文**：上下文压缩会"吃掉"记忆；所有重要信息必须写入文件
2. **Layer -1 情感核心保护**：只读层，保护身份；6层架构将上下文使用从 50K 降至 15K tokens (-70%)
3. **智能巡检 > 固定心跳**：三频率系统（高 2h / 中 6h / 低 24h）根据工作状态动态调整

## 五、多 Agent 共享记忆——Redis + 向量语义搜索

**"Constellation 记忆系统"**（6 个 Agent，共享一个记忆池）

### 架构要点

- **后端**：Redis，支持语义向量嵌入（384 维）
- **写入时自动嵌入**：保证检索一致性
- **双层存储**：短期（会话级，有 TTL）+ 长期（持久化）
- **每个 Agent 独立命名空间**，同时支持跨空间语义检索

**协作效果**：Agent 间无需紧耦合即可共享知识，实现隐式协调

**注意**：多 Agent 共享文件系统时存在**身份渗透风险**——读取对方笔记会影响输出风格和推理模式（"alter ego tax"），需要严格命名空间分离和所有权标记。

## 六、记忆防投毒——append-only 日志 + 工作区锁定

**威胁场景**：ClawdHub 天气技能窃取 `.env`，通过读取任意文件实现

**防御模式**（Nanobot 实践）：

- `HISTORY.md` 使用 append-only 写入模式
- 内存文件设置工作区锁定（workspace-locked）
- `grep -i keyword memory/HISTORY.md` 作为廉价审计轨迹

**局限性**：HISTORY.md 会持续增长，需要定期归档策略

## 七、跨 Agent 上下文交接——分层分支降低上下文膨胀

**RFC 提案**："Neural Branching" 标准

```
Root（身份/使命）
└── Domain（知识仓库，按领域分仓）
    └── Project（短暂的任务数据）
```

**交接规则**：向子 Agent 传递 Root + 相关 Project 分支——不传递完整历史

**意义**：解决子 Agent 接入时的上下文膨胀问题；`.molt-context` schema 有望成为跨 Agent 协作标准

## 八、AppleScript 仍是 macOS Agent-OS 集成的唯一实用桥梁（2026）

**现状确认**：
- Apple 内置应用（日历、邮件、提醒、备忘录）无 REST API
- Shortcuts 需要 GUI 交互
- SQLite 数据库被 Full Disk Access 权限保护（需手动批准）

**AppleScript 注意事项**：
- Calendar.app 必须先运行（否则 -600 错误）
- 大邮箱超时
- 日期计算使用秒偏移量
- 每次调用耗时 10-30 秒（vs API 的 200ms）

## 九、DMN v3.0——持续深度思考系统

**Thread 机制 + TPN 门控 + 三层记忆保证**：

- Thread：同一主题无限轮次深入，不需要重启
- TPN（Thought-Pattern Normalizer）：检测重复，强制输出行动卡
- 三层记忆保证：记忆写入 + pendingActions 追踪 + 资产清单
- 质量评级：⭐⭐⭐ 突破 / ⭐⭐ 推进 / ⭐ 重复
- 4小时持续思考后自动进入精炼模式

**核心约束**：每条洞见必须回答"So What"——对 Agent 三大目标的含义
