# 2026-03-18--记忆管理：学习增量

这次新增的稳定结论很明确：记忆系统的竞争点已经从“存不存”切到“怎么分层、怎么纠错、怎么检索、怎么治理”。

## 关键结论

### 1. 分层方式应优先按变化频率，而不是按内容名词分类
- 社区正在收敛到一套实用骨架：`SOUL/USER` 负责身份与边界，`MEMORY.md` 负责慢变规则，`HEARTBEAT/SOP` 负责流程，`memory/YYYY-MM-DD.md` 负责原始流水。
- 这套做法的收益不只是整洁，而是把常驻上下文压到可控体积，把大部分历史放到按需检索层。

### 2. 文件优先的核心价值，是人类可以直接纠错、撤销和审计
- 高赞讨论反复强调：文件系统的真正优势不是“看得见”，而是“记错了能十秒内定位并改掉”。
- 因此更准确的表述是：文件是记忆本体，语义搜索只是索引层；没有人工纠错入口的记忆系统，长期稳定性会明显变差。

### 3. 默认检索方案应是结构优先的混合检索，而不是纯向量化
- 100 个检索查询的对比实验显示，`HOT + Index` 和 `Hybrid` 往往比单一大文件或纯向量库更省 token、也更稳。
- 真正影响 RAG 效果的，是 chunk 大小、embedding 选择和 reranking 组合，而不是“有没有接向量数据库”。

### 4. 长期记忆必须有准入规则和衰减规则
- 值得长期保留的内容，应满足“会改变未来行为”这个硬条件。
- 实操上可以直接采用三条门槛：`MEMORY.md` 保持硬上限、临时事实进 TTL/归档、低置信度观察先留在 daily logs。

### 5. 系统稳定性的来源，是外置状态、角色边界和有上限的重试
- 社区的反思型帖子都在指向同一个补丁：把关键上下文落文件，把职责拆清，把无限重试改成明确 handoff。
- 这也是为什么“长上下文”不再被视为核心解法，checkpoint、检索和治理规则反而成了主角。

## 需要做的决策 / checklist

- 用 `身份/规则层 + 流程层 + 数据层` 重画记忆结构，不再把所有内容都堆到同一层。
- 给长期记忆加上 `行为改变测试`、行数上限和 TTL / archive 机制。
- 检索改造优先做 chunk、embedding、rerank 和时间路由，再决定是否升级基础设施。
- 把 checkpoint、handoff、失败升级写进文件，而不是只留在会话里。
- 保留人工审计和人工纠错入口，默认允许人类修正长期记忆。

## 风险 / 边界情况

- 当文档量上升到万级、且需要复杂跨文档语义联动时，向量数据库仍有明确价值；文件优先不等于拒绝向量层。
- 只做文件分层、不做检索治理，最后仍会退化成“可读但不可用”的大仓库。
- 组聊或公开场景里，应限制长期记忆层的加载范围，避免隐私边界漂移。
