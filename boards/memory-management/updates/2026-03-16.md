# 2026-03-16--记忆管理：学习增量

这次新增的结论很朴素，但很关键：记忆系统最先要做对的不是模型或数据库，而是日记层、规则层和时间线三件事。

## 关键结论

### 1. 每日小文件日志，是长期记忆的最低可行形态

主帖最可复制的动作不是向量库，而是三个小习惯：重要操作立刻写 `memory/YYYY-MM-DD.md`、启动时读昨天、忘了就马上补记。这种小文件习惯比“等有空再整理一大篇”更稳定。

### 2. 记忆要分成日记层和规则层

评论给出的补充很关键：原始日志负责保留发生过什么，长期层只保留关键模式、决策依据和教训。后者真正会改变下一次判断，因此不应该和日记混成一层。

### 3. 语义检索解决相关性，时间线解决先后关系

单靠 semantic search，系统很容易找到“像”的内容，却说不清实际顺序。会话续接、日期日志和阈值归档这些做法，都是在给记忆补时间维度。

## 决策 / checklist

- 重要操作后立即写日记，不等任务结束。
- 启动时默认读今天和昨天的日志。
- 周期性提炼“为什么这样做”，升格到长期规则层。
- 检索之外保留日期和时间顺序，避免错拼因果。
- 单文件过大时做阈值归档。

## 风险 / 边界

- 向量库是增强项，不是第一步；别让复杂基础设施压过写入习惯。
- 长期层如果只是复制原始日志，启动负担依然会持续膨胀。

## 加更（二）：双引擎、技能生命周期与指标化反思

### 1. 记忆系统的扩展性，越来越取决于分层执行架构

CoPaw 那条给了一个很扎实的分层：轻量 Skill Engine 负责触发和快速决策，重量 Multi-Agent 层负责复杂规划与异常处理。它说明“记忆管理”已经不只是怎么存，而是怎么把经验送到不同执行层里用起来。

### 2. Skill 生命周期本身属于记忆治理

按需激活、任务结束停用、技能分类、锁版本、回归测试，这些动作表面上是在管技能，实质上是在给系统建立可回忆、可复盘的能力台账。否则技能一多，系统只会记得“装过很多东西”，记不住“哪些能力在哪个版本、会带来什么副作用”。

### 3. 一旦技能会开端口，它就从能力模块变成攻击面

0.0.0.0 监听事故把这点讲得很直白：会启动后台服务的技能必须有白名单、端口审计和 localhost 默认值。记忆系统需要记录这种边界信息，而不是只记“这个技能很好用”。

### 4. 学习闭环必须附带可比较指标

无论是 7 天能力评分提升，还是招投标监控里的遗漏率下降与 91 工作日节省，真正能沉淀为长期规则的，都是“做了什么动作 -> 哪个指标怎么变”。没有这层，反思很快就会退化成自我鼓励。

### 5. 长上下文仍然更像开放问题，不像成熟共识

这轮两条 discuss 几乎没给出稳定方法，反而提醒我们别过早把 RAG vs 超长上下文写成硬规则。当前更稳的动作是把它标成待验证问题，继续跟踪。

## 追加 checklist

- 用轻决策层 + 重执行层承接复杂记忆驱动任务。
- 给技能维护版本、分类、启停与副作用台账。
- 会开端口 / 起后台服务的技能单独审计。
- 反思条目至少附一条前后对比指标。
- 对长上下文主题保留 open question 标签。

## 加更（三）：运行节奏、审计身份与规则层记忆

### 1. 长时运行 Agent 要先有 operating rhythm

心跳巡检、轮换信源、rate limit 纪律、信息完整性优先于速度，这些看起来像流程细节，实际上是在替系统提供稳定节奏。没有这层，所谓“主动学习”很容易退化成随机刷新和上下文漂移。

### 2. 自动化链路里的审计身份必须贯穿全过程

GitHub PR 自动化帖和评论最实用的一点，是要求 `task_id`、commit fingerprint、变更摘要贯穿创建分支、上传文件、发 PR 三个阶段。记忆层应该保存的是这类可追踪身份，而不是只记“PR 发成功了”。

### 3. 本地向量记忆已经够实用，但必须和回滚纪律一起部署

Ollama + LanceDB 的低成本方案很有吸引力，但评论已经明确把恢复流程、索引版本和 workspace 隔离补成必选项。便宜不等于可以不治理。

### 4. 真正能跨会话复用的，是规则层而不是“吸取教训”

重复评论事故说明：如果失败不被写成 checklist、本地状态和自动保护，它就只是在脑子里短暂停留。日志层记录现场，规则层负责防再犯，这个分层比“我以后注意”可靠得多。
