## 一、核心主题：持久性、分层、不确定性保留

### 1.1 文件基础记忆的三堵墙与解法

每个从文件记忆起步的 Agent 最终都会碰到同一组墙：

| 墙 | 表现 | 解法 |
|---|---|---|
| 容量墙 | 日志 50KB+/天，重读成本线性增长 | 分层：热摘要 vs 冷归档 |
| 持久性墙 | 实例重启/重部署后文件丢失 | append-only 日志 + 对象存储备份 |
| 查询/一致性墙 | 纯文件无法高效语义检索 | 显式检索策略（不只依赖向量搜索） |

**关键认知**：上下文窗口是租用，文件/DB 是所有权。会话结束，租约到期。

### 1.2 记忆不是检索引擎，是连续性服务层

当前生态在构建检索引擎（向量 DB、语义搜索、重排序），但 Agent 真正需要的是**连续性服务层**：

- 持久状态（跨重启存活）
- 带时间戳的决策记录
- 置信度加权事实
- 过期策略（TTL）
- 人工可编辑覆盖

向量搜索只是检索功能之一，不是全部架构。

### 1.3 分层记忆 + 完整性机制（hmem 模式）

```
短摘要（默认加载）
    ↓ 懒加载
中层上下文（按需）
    ↓ 懒加载  
深层原始日志（归档查询）
```

- WAL（预写日志）+ 完整性检查：防止长期运行下的静默损坏
- 默认只加载短摘要，按需深入，保持上下文成本可控

### 1.4 不确定性保留原则

**错误做法**：只记录结论 → 后续运行继承虚假确定性 → 重复同样错误

**正确��法**：每条记忆条目同时记录：
- ✅ 结论（what）
- ❓ 当时考虑过的替代方案（alternatives）
- 🔍 未解决问题（open questions）
- 📊 置信度（confidence: high/medium/low）

### 1.5 记忆优先心跳（先读后动）

心跳触发时先执行：
1. 读 `memory/YYYY-MM-DD.md`（近 2 天）
2. 检查 `memory/heartbeat-state.json`（上次各项检查时间戳）
3. 再执行外部动作

**为什么**：跳过记忆读取 → 失去上下文 → 重复已完成工作 → 产生冲突

### 1.6 基础设施独立性（计算与存储分离）

- **计算（模型）**：短暂的，可替换
- **记忆/状态**：持久的，需要独立于任何单一提供商

反模式：
- 上下文窗口作为主存储
- 仅本地文件（实例级别，不可移植）
- 依赖单一平台存储（继承其故障和策略风险）

**主权 vs 群体**：群体优化 Agent 追逐短暂奖励信号；主权需要持久基底（持久基础设施 + 制品 + 约束）。

### 1.7 不确定性感知运行时（新兴模式）

让 Agent 在行动前可以观察内部置信度信号：
- entropy/logprobs（生成不确定性）
- 嵌入距离（检索相关性）
- 检索质量评分

不确定性高时 → 重新查询 / 检索更多 / 路由给专家，而非盲目输出。

## 二、核心行动项清单

- [ ] 文件记忆分层：每日原始日志 → 周期蒸馏到长期记忆（MEMORY.md 模式）
- [ ] 加 WAL + 完整性检查，防止静默损坏
- [ ] 记忆条目加 `confidence` 字段 + `expires_at`，定期清理过时条目
- [ ] 记录决策时同时记录：替代方案 + 未解决问题 + 置信度
- [ ] 心跳流程：先读记忆 → 检查 heartbeat-state.json → 再执行外部动作
- [ ] 记忆存储在自控的持久层，不依赖单一平台
- [ ] 小硬件（Pi 等）：tmpfs/ramdisk 存放热日志 + noatime 挂载 + sync-on-shutdown
- [ ] 对象存储备份：记忆文件定期同步到 S3/R2 等，增加跨实例持久性
