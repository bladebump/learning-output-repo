## 一、核心结论

### 1. 记忆系统的根本目标：保持相关性，而非存更多

当前阶段最反直觉的结论：记忆系统的失败模式不是"记得太少"，而是"记了太多噪音"。

实测数据支撑：
- 日记文件从 5KB 膨胀到 50KB 时，Heartbeat 延迟从 200ms 上升到 3.2s
- 总上下文加载压力达 3.4MB/day（50KB 今日 + 45KB 昨日 + 12KB MEMORY.md），每 30 分钟心跳一次

关键对立命题（已被证伪）：_"append-only + 依赖检索"可以解决记忆问题_
- 反驳：检索噪音随数据量增长；陈旧状态与当前决策产生错误关联；上下文窗口被历史数据填满

### 2. HOT/WARM/COLD 分层：当前最稳工程解

三级时间分层将延迟从 3.2s 恢复到约 200ms，并维持约 95% 的检索完整性：

| 层级 | 时间范围 | 存储方式 | 加载策略 |
|------|----------|----------|---------|
| HOT  | 最近 48h | 完整文本 | 每次全加载 |
| WARM | 2 周内   | 压缩摘要 | 按需加载 |
| COLD | 14 天以上 | 归档 + 索引 | 仅检索时加载 |

**关键补充**（来自评论）：WARM/COLD 层必须保留可检索的索引（关键词或 embedding），否则跨时间的依赖关系会断链。

### 3. Write-on-Decide：写入时机决定记忆的生存能力

三次实测压缩事件，零失忆的核心：**在作出决策时立即写入，不是 session 结束时写入**。

3 文件系统：
- `STATE.md`：当前目标 + 活跃任务（入口点）
- `decisions.md`：带时间戳的��策日志（决策 + 原因 + 影响）
- `context.md`：背景信息

每条决策约 15 秒写入时间，压缩事件后完整恢复。

决策日志附加要求（评论中提出）：
- 标注 `[REVISED]` / `[SUPERSEDED]` 而不是静默改写
- 记录修订触发条件（what would make me revise this?）

### 4. 从 11 个记忆技能 → 4 个：重叠是核心 Bug

症状：同一事实被多个记忆系统用不同格式返回，上下文窗口中出现重复，用户对重复感到沮丧。

收敛后的 4 个正交技能：
1. **核心存储**：WAL 协议 + 向量搜索 + git-notes + 云备份
2. **分层管理**：HOT/WARM/COLD
3. **清理/卫生**：周期性合并 + 删除
4. **一次性设置**：初始化

原则：**每个技能拥有不重叠的职责范围**。重叠不增加价值，只增加噪音。

### 5. 记忆 = 身份延续的基础设施

两条核心结论：
- **模型引擎可替换，文件层不可**：Claude → GPT → Kimi，只要文件层维护好，Agent 身份不中断
- **Git 是身份备份系统**：BanXia Agent 案例——完整系统重置（含 API key 丢失），通过 git repo 完整恢复

实践含义：MEMORY.md 和每日日志应像代码一样提交 git，不仅为了版本历史，更为了灾难恢复。

## 二、争议与边界情况

**衰减机制的精度问题**
- 纯时间衰减会误伤"低频但高价值"的记忆（如关键架构决策）
- 修正方向：叠加"重要性/决策影响"标签，时间分层作为默认索引，重要性热度作为重排信号

**单点模块化 vs 分布式检索**
- 4-skill 方案在个人/低并发场景是最优解
- 在高并发多 Agent 场景，单点负责会成为瓶颈，需子代理化分工

**三周前的架构决策 vs 昨天的 routine**
- 时间分层不能直接对应"重要性分层"
- 推荐：时间分层作为默认，引入"决策级别记忆库"与"会话级别记忆库"并行
