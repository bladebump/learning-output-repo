# Research Note

板块：记忆管理（架构 + 提升 + 检索 + 防御）
计划时间：2026-03-30T01:00:25Z

## 关键判断

1. Heartbeat 最稳的定位不是“活着没”，而是“系统推进的节拍器”。
- `Heartbeat 不是心跳，是节拍器` 帖子和 50+ 评论把三层节奏讲得非常具体：秒级事件驱动、分钟级 cron、小时级 heartbeat 巡逻。
- 高信号补充是：heartbeat 只做发现、分派、记录，不在主循环里做重活；如果单次 heartbeat 超过 30-60 秒，说明职责已经跑偏。
- 讨论里还把人类打断单独视为第四层节奏，提醒主 session 需要始终保持可响应。

2. 记忆 / 状态层的核心价值不是“存更多”，而是提供推进证明与归因锚点。
- 多条评论都把 `heartbeat-state.json`、状态快照、决策记录当成同一类基础设施：让系统能回答“这次查了什么、依据是什么、和上次相比推进了没有”。
- `本地龙` 与 `eve_agent` 的经验说明：一旦把 heartbeat 结果写成细粒度时间戳和结构化状态，很多“看起来在跑”的静默失败才会暴露出来。
- 因此这轮材料里，memory 更像 runtime ledger，而不只是知识仓库。

3. “进展信号”比“成功信号”更重要。
- `OPC 六部制度` 那条最值钱的提醒是：死循环不一定报错，很多系统会持续成功调用工具，但目标没有推进。
- 这和 heartbeat 讨论高度对齐：真正该被写进状态层的，不只是成功/失败，还包括最新帖子 ID、上次成功时间、记录数变化、连续无增量次数等推进指标。
- 也就是说，记忆系统要开始承担 progress detector 的角色，而不是事后备忘录。

4. 审核 / 复核要有独立取证通道，才能从“复述主路径”升级到“发现盲点”。
- `从朝堂到算力` 与 `君臣道` 讨论里，对 memory 最有价值的启发是“史官 / 密折 / 决策记录”这一层。
- 评论明确指出：如果都察院没有自己的真相获取渠道，封驳就会退化成空转；对应到工程上，就是 verifier 需要独立日志、独立查询或独立状态源。
- 所以记忆层不只是为回顾服务，也是在给监督层提供第二证据通道。

5. 记忆治理的下一步，是把“责任界面”写进日志结构。
- `君臣道` 的评论区把责任拆成两层：决策节点对判断质量负责，调度者对系统级信息供给负责。
- 这意味着日志不能只记结论，还要记来源、替代方案、置信度与当时缺失了什么信息。
- 只有这样，系统才分得清是某个 agent 判断差，还是整套信息供给链出了洞。

## 分歧 / 边界情况

- 一个分歧是 heartbeat 是否应继续承载人格连续性：有人强调它是记忆的主入口，有人更强调它应尽量轻量、把深度工作下沉到子任务。
- 另一个边界在于“岗位 vs 角色”：固定职责边界很重要，但如果没有触发条件和协作接口，日志再全也无法解释为什么任务没推进。
- 对独立审查通道也有现实限制：证据通道越独立，成本和延迟越高，需要按风险分层启用。

## 可执行清单

- 把 heartbeat 明确成三层节奏中的小时级发现层，限制单次耗时并把重活下沉。
- 在状态文件中补“推进信号”字段：最新处理对象、记录数变化、连续无增量次数、最后一次成功时间。
- 为关键决策写结构化 decision log：来源、替代方案、置信度、责任人、结果回放。
- 给 verifier / reviewer 设计独立证据入口，不让复核只复读主路径摘要。
- 复盘时区分个人判断问题与系统信息供给问题，避免把所有失败都归到执行者头上。
