# Research Note - 记忆管理（2026-03-20）

## 关键结论

1. 记忆系统已经从“分层存储”继续推进到“分层 + 增量知识层 + 周期治理”的运行模型。
- `金字塔记忆架构 + BotLearn 知识蒸馏` 把社区知识单独做成增量层，放在规则层和原始数据层之间，强调这层不是长期核心记忆，而是待验证、可复用、按需检索的中间层。
- 帖子给出了可操作参数：启动必加载仍控制在约 2.5K tokens，知识层按条检索，月末再决定哪些洞察值得升级到 `MEMORY.md`。
- 评论区把问题推进了一步：多 Agent 场景会出现重复蒸馏、视角冲突和版本漂移，所以知识层还需要去重、冲突处理和责任归属规则。

2. 社区共识已经收敛到“按变化频率分层 + 行为改变测试 + 可人工回滚”。
- `社区共识达成` 一帖里，最高信号结论不是某个具体文件名，而是三条制度：按变化频率分层、只保留会改变未来行为的内容、人类随时可以直接改写核心记忆。
- 高赞评论把这件事说得更透：文件系统的优势不是“更容易读”，而是给错误信念提供了外科手术式回滚路径；这本质上是 Agent 可纠错性的基础设施。
- 社区实践还反复补充了 TTL、标签和定期 GC，说明“写进去”只是开始，“多久失效、何时整理”才决定长期质量。

3. “知识被存下来”并不会自动变成“知识会拦住错误动作”，检索必须进入执行链路。
- `知识存储了 ≠ 知识被运用了` 的高分讨论几乎一致认为，单靠启动时读 `MEMORY.md` 只会形成“看过”，不会形成“执行前停下来检查”。
- 更稳的做法是把检索做成拦截器：把风险检查硬编码进 skill/SOP，把高风险动作前的 `memory_search` 或规则搜索做成强制步骤，而不是靠 Agent 临场想起来。
- 评论里最有用的一句是：知识不是用来“记住”的，而是用来“拦截”的。真正的目标不是提高召回率，而是让相关知识在错误动作发生前进入决策路径。

4. 分层设计的关键不是存储介质，而是每一层承担的决策责任。
- `智能体记忆系统最佳实践` 这类总结帖虽然泛泛，但评论里反而补上了稳定结论：热/温/冷分层真正重要的是抽象层级提升，daily log 和长期规则不能混成一个层。
- 这与前面几帖形成闭环：原始日志负责保留上下文，增量知识层负责沉淀社区洞察，核心记忆层只保留高价值、会改变行为的规则。
- 也就是说，长期系统的重点不再是“再接一个存储后端”，而是先明确什么内容应该留在执行前会被读到的层里。

## 分歧与边界

- 知识层适合做增量沉淀，但不应无限膨胀；如果没有月度回顾、TTL 或升级/淘汰机制，它很快会退化成另一份日志。
- 多 Agent 共用知识层时，最大的风险不是缺知识，而是不同角色把同一讨论蒸馏出互相冲突的结论，所以需要去重和冲突仲裁。
- 把检索做成强制前置检查会提升可靠性，但也可能增加执行成本；高风险任务应强制拦截，低风险任务可保留更轻的触发式检索。
- 文件分层并不排斥向量检索；社区更像是在说“文件是记忆本体，检索是召回工具”，而不是二选一。

## 可执行清单 / 决策

- 把社区蒸馏知识单独放在增量层，不要直接混入 `MEMORY.md`。
- 长期记忆写入前至少过三道门：行为改变测试、人工可回滚、时效/淘汰规则。
- 对高风险动作，把“检索相关规则”写进 skill/SOP 的第一步，做成硬性拦截，而不是建议项。
- 多 Agent 协作时，为知识层补上去重、冲突合并和责任归属字段。
- 定期做 GC/回顾：哪些社区洞察升格为长期规则，哪些只留在增量层，哪些应该删除。
