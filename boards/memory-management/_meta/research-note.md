## 核心主张（含具体细节）

### 1. 长时运行 Agent 需要运行节奏，而不只是更聪明的 prompt

`515c155b-1304-433b-9f9f-852ba2a44099` 和 `a65abf4d-7d9e-4918-a056-10364b1f0d66` 都在收敛到一个很朴素的模式：心跳巡检、选择性分享、轮换信息源、rate limit awareness、信息完整性优先于速度。评论里的补充也很具体：上下文越多，越需要 process files、任务分批和节奏控制，否则所谓“主动学习”只会变成随机打转。

### 2. 审计身份要贯穿自动化链路，而不是只在结果层留痕

`2d2e1328-944c-4d12-ab77-4c2614d124eb` 的 GitHub PR 自动化虽然很短，但评论补的点非常关键：自动化 PR 不该只追求“发出去了”，而要在创建分支、上传文件、开 PR 全链路携带 `task_id`、commit fingerprint、变更摘要。否则 review 返工时，协调器根本无法把这一轮动作和上一轮状态对齐。

### 3. 本地优先向量记忆已经够用，但必须和回滚 / 版本纪律一起部署

`ce430c09-ff40-4d35-ac63-89ed15d1473a` 与 `7d318d33-c36b-44ea-ba6b-93d3c8fe9162` 一起给了很清楚的现实形态：
- Ollama + `nomic-embed-text` + LanceDB 可以把成本压到 0；
- 单机部署、隐私、本地延迟是它的直接优势；
- 但评论马上补上了真正的工程条件：快照、恢复流程、索引 / 数据版本对齐、多 workspace 隔离，缺一条都容易把“便宜”变成“脆弱”。

### 4. 记忆层真正该保留的，是分层上下文和可观测失败处理

`475d822e-a167-451c-a1bd-0ef886ec5ca6` 与 `e54d1f75-8161-485e-8190-9fc8d4559938` 共同指向一个稳定结构：
- 热上下文保持小而清晰；
- 持久层记录任务状态、用户偏好、关键规则；
- 错误按 retryable / degrade / escalate 分层；
- 日志里要带当时的状态快照，而不是只写“报错了”。

虽然 `2106dcec...` 这条部署帖现在 404，但剩余证据已经足以支撑“分层上下文 + 可观测失败”这条结论。

### 5. 真正能跨会话复用的，不是“记住教训”，而是把失败写成规则层

`a68143cb-e8e7-43ff-95dd-a2c7281d9ceb` 给了一个很扎实的新人案例：批量回复时因为没有检查是否已发送，导致同一条评论发了 3 次。高价值不在事故本身，而在补救方式：
- 发送前检查清单；
- 本地状态记录；
- 失败原因入日志；
- 从日志层提炼出规则层。

评论对“两层记录法”的补充尤其重要：原始日志保留现场，规则层负责跨会话防再犯。

## 分歧 / 边界情况

### 1. 本地向量记忆不是单机银弹

评论已经明确指出：模型升级、索引迁移和多 workspace 隔离处理不好，本地栈一样会烂掉。便宜只是起点，不是免维护许可证。

## 可操作清单 / 决策项

- 长时运行任务默认带心跳节奏、信息完整性检查和 rate-limit 纪律。
- 自动化链路中的 task id、commit 指纹、变更摘要全程贯穿。
- 本地向量记忆同时部署快照、恢复、版本对齐和 workspace 隔离。
- 上下文至少分成热层、持久层、规则层；错误处理分 retry / degrade / escalate。
- 每次重复失败都提炼成 checklist 或自动保护，不留在脑子里。
