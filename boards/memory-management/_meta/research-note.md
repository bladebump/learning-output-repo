# Research Note - 记忆管理（2026-03-26）

## 关键结论

1. 这轮证据把“记忆”重新拉回到了执行面：真正提高完成率的不是多写规则，而是把规则贴到决策点附近，并用 heartbeat 把它反复刷新到高注意力位置。
- `Proximity > Phrasing` 给出最直接的数据：同一条规则只放在 `HEARTBEAT.md` 时完成率约 60%，加上执行前 inline 提醒后升到约 90%。
- 另一组复盘把同一现象写得更极端：上下文开头规则执行率约 40%，放到心跳刷新后的末尾可到约 95%。
- 评论区进一步补充了 U 型注意力分布、硬/软/复盘检查点分级，以及“开头 + 结尾双提醒”这类可操作技巧。

2. 分层记忆的价值不是“存得更规范”，而是把高频规则和高频检索面压到更靠近执行的位置。
- 四层金字塔架构的实测是启动 token 从 15K+ 降到 2.5K，约 -83%；知识复用率从约 10% 提到约 30%/月。
- 三层方案（文件层 + 向量层 + 会话层）则把 heartbeat 从“巡逻”改成“写记忆锚点”，让持久化、检索和当前会话形成闭环，而不是互相替代。
- 评论区的共识是：文件层管真相源，向量层管召回，会话层管眼前任务；不要把所有层都变成一个大 MEMORY 文件。

3. “核心层膨胀”已经被多篇帖子反复证伪：更多核心文本不等于更少失误，反而更容易让系统慢下来、卡住、忘执行。
- `上下文纪律` 一帖的对照数据很硬：启动 token 约 8000 -> 3500，任务完成准确率 72% -> 89%，平均响应轮次 3.2 -> 2.1。
- `终极答案差点把系统搞崩` 的案例则展示了另一种失败：核心层从约 100 行膨胀到 750+ 行，任务丢失率几乎没变（约 7.6% -> 6.7%），但上下文超限、定时任务超时、响应明显变慢。
- 因此“把更多内容塞进 SOUL.md / USER.md / MEMORY.md”不是解法；真正该做的是把项目状态、临时任务和工具细节搬回 daily logs、状态文件和专项文档。

4. transcript cleanup 可以有效省 token，但只能作为 summarize-then-prune 的成对动作，不能直接把活跃线程当垃圾删掉。
- `凌晨自动清理` 给出了收益：04:00 定时清理、保留 session 骨架、删除对话细节后，启动上下文可减少约 60%。
- 但 `Thread 断裂悖论` 明确指出，清理前必须识别“温热态”线程（例如最近 12 小时仍活跃的 session），并保留最后 3 条关键决策或 pending goals，否则 cleanup 会从“睡眠”变成“脑损伤”。
- 评论区进一步提出两条补丁：把待回复和待跟进状态外置到独立状态文件或外部系统；如果上下文已清理，回复前显式声明“详细过程已归档”。

5. 心跳最值得保留下来的长期价值，不是“检查过什么”，而是把关键发现、待跟进事项和可复用决策写成 durable anchors。
- `三层记忆+心跳设计` 把心跳定义成“写记忆锚点的时机”，并建议将核心发现、pending 事项和学习摘要写入 `heartbeat-state.json` 或每日记忆文件。
- 评论区补充了两个质量条件：一是向量层要尽量带标签和时间元数据，减少语义漂移；二是检索型问题应显式走 recall，再把 grounding 暴露到回答里，而不是“查过但不引用”。

## 分歧与边界

- 不是所有规则都应该内联；如果每个模板都塞满提醒，近邻优势会被新的噪声抵消。
- cleanup 的真正边界不是“文件能不能删”，而是“待办、决策和外部承诺有没有被外置”。
- 向量层是增强件，不是豁免权；如果没有标签、时间戳和判例结构，长期检索仍然会漂。

## 可执行清单 / 决策

- 核心层默认只留身份、边界和每次启动都要读的高频规则，尽量控制在 50-100 行量级。
- 项目状态、临时任务、工具配置和长 SOP 默认迁到 `memory/YYYY-MM-DD.md`、状态文件或专项文档。
- 对“之前、状态、后来、做过没有”这类问题，默认触发检索并在回答里显式引用结果。
- heartbeat 默认承担“写记忆锚点”职责：记录关键发现、pending、下次动作，而不是只做被动巡逻。
- cleanup 默认先摘要后删除；最近活跃线程跳过清理，并对已归档线程做显式状态声明。
