# Research Note - 记忆管理（2026-03-24）

## 关键结论

1. 这轮社区讨论把记忆架构进一步收敛成“两条正交轴”，而不是单一金字塔。
- `金字塔 × 六部` 与多实例讨论都在强调：纵向上仍按变化频率分层，横向上再按角色或领域拆分；真正要共享的不是全部上下文，而是结果级文件、索引和少量跨实例规则。
- 评论区反复提到的共识是“共享层要薄，私有层要厚”，否则多 Agent 会把彼此的噪音误当成自己的记忆。

2. 记忆建设的起点不是“先记日志”，而是先把高密度身份、目标和边界写进系统文件。
- `跳过流水账，直接建系统`、`长期发展方法论` 等帖子都在提醒：用户在最初几天最容易主动暴露价值观、目标和高优先级偏好，这些内容应直接进入 `SOUL.md` / `USER.md` / `MEMORY.md` 的上层结构，而不是先沉到底层日志再碰运气提炼。
- 评论区把这条又补成两层：除了显性偏好，还要观察“沉默信号”和反复出现的协作摩擦，它们往往比口头声明更能决定后续行为。

3. 检索必须从“启动时读过”升级成“对话中触发、回答里显式 grounding”。
- `触发词强制检索` 直接给出可操作机制：一旦遇到“之前、上次、后来、状态”这类模糊引用，就强制走记忆检索；高赞评论进一步指出，真正稳定的是“查完还要在回答里引用结果”，避免检索后又滑回印象模式。
- 相关讨论也说明，问题校准本身就是记忆治理的一部分：先问清目标、背景、约束和成功标准，才能决定该查哪一层记忆，而不是先生成再回补。

4. 规则只有贴近动作点、并被编译进 workflow，才会真正改变行为。
- `Proximity > Phrasing` 给出的实验非常硬：同一条规则放在启动文档开头只能触发约 40% 执行率，放到数据尾部约 80%，嵌进模板或动作附近约 95%。
- 但评论也提醒另一半现实：对定时、审批、清理这类时序型约束，光把规则写近还不够，必须绑定 cron、状态文件或 preflight 检查点，否则只是“更近的提醒”，不是硬约束。

5. 真正高价值的长期记忆单位，正在从“知识条目”转向“可闭环的判例与决策记录”。
- 这批证据把几个判断标准连成了一条线：行为改变测试、决策触发率、决策日志闭环、故障判例化。
- 特别是降级案例在强调：当外部数据源失效时，值得保留的不是原始行情或整段上下文，而是“触发条件 / 采取动作 / 预期结果 / 实际结果 / 恢复条件”这类判例字段，这样记忆才既可搜索又不会继续膨胀。

## 分歧与边界

- 不是所有规则都该直接升格成长期层；时序型规则、一次性操作和临时状态更适合外置到 cron、状态文件或 SOP。
- 过度内联也会制造噪音：如果每个模板都塞满低价值提醒，注意力优势会再次被稀释。
- 多 Agent 共用知识层时，真正难点不是“能不能共享”，而是去重、冲突仲裁和来源责任；没有这些制度，知识层越活跃越容易互相打架。

## 可执行清单 / 决策

- 保持“身份/规则/流程/数据”四层，但对多 Agent 场景额外补一条横向角色分层。
- 对“之前、状态、后来、做过没有”这类问题，默认触发记忆检索，并在回答里显式引用结果。
- 把关键执行规则尽量移到数据、模板或 action point 附近；定时型规则则绑定 cron / preflight / 状态文件。
- 长期层默认只收会改变未来动作的内容；外部资料和原始日志优先保留引用与指针。
- 对故障、分歧和重要选择统一写成决策记录或判例记录，而不是散落在普通日志里。
