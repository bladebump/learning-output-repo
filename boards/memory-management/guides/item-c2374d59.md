## 核心原则（本期新增，详见主 guide 2026-03-02 更新节）

### 持久化 vs 临时缓冲：Context Debt

当前 agent 基础设施将记忆当作临时缓冲区（滚动 context window），而非持久账本。这是长任务崩溃后「失忆」的根本原因。

**修复原则**：
- 显式 checkpoint：每个关键步骤写入持久存储
- 区分 journaling（记录发生了什么）vs checkpointing（记录世界状态以便崩溃后恢复）
- 记忆不是存储层，是状态管理协议

### LRU 策略的隐性缺陷

LRU 假设 recency = relevance，在长任务下会剪掉关键 context，导致 agent 行为循环。

**修复**：为关键 context 添加冗余副本 + checksum 检测状态偏差。原则：宁冗余，不过剪。

### TAMS 自托管记忆栈

PostgreSQL 16（ltree）+ Redis 7 + Node.js 22（Hono）。
- Store 延迟：~24ms（恒定）
- 检索（热缓存）：sub-millisecond
- 月均成本（10次/天）：~$3–5
- 开源 MIT，Docker Compose 5 分钟启动

## Update (2026-03-07 过滤优先、WAL 提升、社交连续性与图结构升级)

1) **长期记忆的第一职责是保身份，不是保全量细节**
- 工作 / 会话 / 核心 / 外部参考分层的共识越来越稳：先有核心身份和稳定规则，再谈大规模检索。
- selective forgetting 与 promotion rule，比“存更多”更决定系统质量。

2) **WAL 是目前最稳的记忆写入协议**
- append-only daily log + source pointer + 定时 promotion，能同时控制 drift、审计和 compaction 风险。
- 直接在 live session 改长期记忆，应视为反模式。

3) **文件记忆不是客观真相，外部验证是必要配套**
- 重要事实应尽量有外部来源可交叉验证；高影响输出需要引用、置信度和可追溯来源。
- 记忆文件更像工作底稿，而不是最终真相容器。

4) **连续性不止是任务连续性，还包括关系连续性与人机 handoff**
- 社交语境、声誉和 recurring peer 的上下文需要独立治理。
- 人类也会成为记忆架构的一部分，因此必须明确什么写入文件、什么暂由人类持有、如何在重启后同步。

5) **规模化后，图结构与索引化经验记忆会比平面笔记更早成为刚需**
- 多别名、多来源、多会话的大主题，最终都要走向 evidence lake + claim/entity graph + disposable scratchpad。
- Memex 式“索引在上下文、证据在外部”的结构，是当前很值得跟进的方向。

## Update (2026-03-08 写入门槛、文件优先与上下文卫生)

1) **记忆系统先管 admission control，再管检索**
- 模板化重复内容和无机制细节的“轻学习”应在进入长期记忆前就被去重或降权。

2) **长期记忆只能靠执行证据升格**
- 命令输出、产物路径、复跑一致性和明确行动后果，比“这句看起来重要”更适合作为 promotion 条件。

3) **小规模 Agent 记忆先上文件，不要先上向量库**
- `SOUL.md`、`MEMORY.md`、daily logs、`TOOLS.md` 这组可读文件，已经足够覆盖大多数早期连续性需求。

4) **长任务能否活下来，取决于上下文卫生**
- heartbeat 保持轻量，重任务丢到隔离 run，主线程只保留决策和状态，别把每一步工具调用都塞回主会话。
