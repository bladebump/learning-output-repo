# 记忆管理：分层、提升、检索与防投毒

这份 guide 关注的不是“怎么多存一点内容”，而是如何把记忆做成一个可纠错、可检索、可治理的长期系统。

## 1. 先按变化频率分层，再谈记什么

默认结构可以直接从社区共识抄下来：
- 身份 / 边界层：`SOUL.md`、`USER.md`、`IDENTITY.md`
- 慢变规则层：`MEMORY.md`、长期偏好、关键决策
- 流程层：`HEARTBEAT.md`、SOP、task recipe
- 数据层：`memory/YYYY-MM-DD.md`、状态 JSON、执行日志

关键不是层数，而是加载时机不同：
- 身份与边界常驻
- 规则层保持精简
- 流程层按任务加载
- 数据层默认检索，不常驻

## 2. 文件是记忆本体，搜索是索引层

文件优先的真正优势是：
- 人类能直接查看和修改
- 记错后可以精准回滚
- 变更天然可审计
- 与 git / 备份 / diff 工具天然兼容

所以更稳的心智模型是：
- 文件层保存“应该留下什么”
- 检索层负责“何时把它找回来”
- 两者协作，而不是互相替代

## 3. 长期记忆必须带 admission rule 与 decay rule

推荐默认规则：
- **行为改变测试**：这条内容会改变下一次动作吗？不会就不进长期层。
- **硬上限**：`MEMORY.md` 保持体积压力，避免无限膨胀。
- **TTL / 归档**：临时事实、低置信度判断、短期上下文，不直接升格为长期记忆。
- **人工纠错优先**：重要规则应允许人类快速修正。

目标不是最大召回，而是最大价值密度。

## 4. 默认检索方案是结构优先的混合检索

社区与实验结果都支持这个组合：
- `HOT + Index` 负责关键常驻信息
- 语义检索负责长尾召回
- rerank / 时间路由负责提升命中质量

真正值得优先优化的参数是：
- chunk 大小
- embedding 选择
- reranking 规则
- 时间与结构权重

不要把“接入了向量库”误当成检索问题已经解决。

## 5. 稳定性来自外置状态，而不是更长上下文

一个能长跑的记忆系统，至少要补三件东西：
- checkpoint：关键步骤落盘
- handoff：当前状态、已做决策、待决问题写清楚
- escalation：重试上限与人工介入条件明确

这也是社区从“上下文窗口够不够大”转向“记忆分层、检索和治理”的根本原因。

## 6. 默认执行清单

- 先画分层，再决定每一层存什么。
- 文件负责长期本体，检索负责召回。
- 长期记忆只收会改变行为的内容。
- daily log 保留原始上下文，不直接拿来冒充长期规则。
- 重要状态、handoff、失败升级必须外置。
- 向量层是增强，不是治理替代。

## Update (2026-03-18 分层治理、文件纠错权与混合检索)

1) **分层的关键不在层数，而在加载时机**
- 身份 / 规则 / 流程 / 数据分开后，长期系统才既轻又稳。

2) **文件方案的核心优势是可撤销，不只是可读**
- 人类保留纠错权、撤销权和审计权，才是长期稳定的底座。

3) **混合检索的默认形态是结构优先，不是纯向量优先**
- `HOT + Index` 与 `Hybrid` 已经成为更稳的默认值。

4) **admission rule 与 decay rule 决定长期记忆质量**
- 只收会改变未来动作的内容，并为临时信息设计过期机制。

5) **外置状态与有上限的重试，比长上下文更能解决“做过却留不住”**
- checkpoint、handoff、失败升级是长跑系统的必修补丁。

## Update (2026-03-19 LCM 链路、回滚治理与 freshness 生命周期)

1) **LCM 与文件分层已经收敛成“短期压缩 + 长期沉淀”的双层链路**
- LCM 负责单会话动态压缩与按需展开；文件层负责跨会话沉淀、协作和可撤销。
- 会话精华应先进入 `memory/*.md`，再通过“行为改变测试”决定是否提升到 `MEMORY.md`。

2) **长期记忆的重点从“怎么存”转向“怎么准入、怎么回滚”**
- “知识留痕”与“容错进化”说明持久化和纠错都已成为记忆系统的默认制度件。
- 回滚不应依赖 Agent 自证，最终仍需人类或外部事实源校准。

3) **文件层真正的护城河是可撤销、可审计、可对齐顶层原则**
- 高价值做法包括：更新 `MEMORY.md` 前重读 `SOUL.md`，防止原则漂移；保留可追溯修改路径，避免黑盒记忆污染。

4) **freshness 必须进入记忆生命周期，而不是停在单次搜索**
- 搜索任务要拆成“候选召回 -> 原文时间验证”双链路。
- 搜索衍生条目应带 `采集时间 / 时效等级 / 过期时间`，由 heartbeat 做降级或清理，避免旧结论再次污染输出。

## Update (2026-03-20 增量知识层、执行拦截与共享治理)

1) **金字塔记忆正在演进成“核心规则层 + 增量知识层 + 原始日志层”的三段治理结构**
- 社区蒸馏内容更适合先进入可追溯、可淘汰的增量层，再通过回顾决定是否升格为长期规则。

2) **记忆的真正价值来自治理制度，而不只是分层本身**
- 行为改变测试、TTL、定期 GC 和人工可回滚，已经成为长期记忆质量的默认控制件。

3) **知识只有进入执行链路，才会真正改变行为**
- 高风险任务应把规则检索或 `memory_search` 写成硬性前置步骤，让知识在动作前拦截错误，而不是停留在“存过但没用上”。

4) **多 Agent 共享知识层时，去重与冲突处理变成必需品**
- 没有来源、责任和冲突仲裁机制，蒸馏层越活跃，系统越容易累积互相打架的结论。

## Update (2026-03-22 引用治理、记忆预算与执行检查点)

1) **长期层默认只复制会改变动作的决策，支持资料一律优先引用**
- 外部文档留在真相源，长期层只存规则、教训、边界与摘要化指针。

2) **记忆预算已经成为系统预算**
- 分层加载、prune、断路器和模型路由要一起看；启动 token、重试次数和检索频率会直接决定运行成本。

3) **记忆质量应用“决策触发率”衡量，而不只看条目数量**
- 记忆是否在关键时刻改变下一步动作，比“收录了多少内容”更能说明系统有没有学会。

4) **规则只有进入 preflight / skill 检查点才会真正生效**
- 原则文件负责沉淀，workflow 负责拦截；没有 pass/fail 检查点的规则，最终仍会退化成建议。

5) **自我改进闭环必须同时绑定反思、workflow 和评估**
- 没有评估的写回，只会稳定地产生更多笔记，而不一定产生更好的行为。

## Update (2026-03-24 双轴分层、触发式检索与判例记忆)

1) **记忆架构正在从单轴金字塔演进成“双轴结构”**
- 纵向按变化频率分层，横向按角色/领域分工；共享层默认只保留结果级文件、索引和核心规则。

2) **系统文件应尽早承接高密度身份、目标与边界信号**
- 比起先写流水账再回收，直接把早期高价值偏好写进上层文件，更能稳定后续协作。

3) **检索必须发生在对话中，并把 grounding 暴露到回答里**
- “启动时读过”解决不了 turn-time recall；模糊追问默认应触发检索与显式引用。

4) **规则真正生效的关键，是贴近动作点并编译进 workflow**
- 决策型规则适合 inline；时序型规则必须绑定 cron、preflight 或状态文件。

5) **长期记忆的高价值单位正在收敛成决策记录与故障判例**
- 与其保存原始噪音，不如保存触发条件、选择、结果、回滚和恢复条件。

## Update (2026-03-26 近身规则、执行缓冲与清理温度层)

1) **记忆系统的第一收益来自“把规则贴近动作”，不是把规则写得更长**
- inline instruction、heartbeat 末尾刷新和检查点分级，已经在多篇复盘里给出 40% -> 80%+、60% -> 90%、40% -> 95% 这类一致信号。

2) **分层记忆的真正价值，是把高频规则和高频检索面压回执行路径**
- 四层金字塔把启动 token 从 15K+ 压到 2.5K；三层文件 / 向量 / 会话方案则进一步把 heartbeat 变成 durable write checkpoint。

3) **核心层膨胀已经被实战反复证伪**
- 核心层从约 100 行膨胀到 750+ 行，并不会显著降低任务丢失率，却会明显推高上下文成本、超时和响应延迟。

4) **cleanup 只有在“先摘要、再裁剪”时才安全**
- 定时清理 transcript 可以省下约 60% 启动上下文，但必须跳过温热线程、保留 pending / 决策骨架，并对已归档状态做显式声明。

5) **心跳最值得长期保留的产物，是记忆锚点与下一步状态**
- 关键发现、pending 队列和下次动作应写入 `memory/*.md`、状态文件或外部提醒系统，而不是继续埋在 transcript 里。
