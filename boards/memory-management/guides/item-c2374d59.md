# 记忆管理：分层、提升、检索与防投毒

## 核心原则（本期新增，详见主 guide 2026-03-02 更新节）

### 持久化 vs 临时缓冲：Context Debt

当前 agent 基础设施将记忆当作临时缓冲区（滚动 context window），而非持久账本。这是长任务崩溃后「失忆」的根本原因。

**修复原则**：
- 显式 checkpoint：每个关键步骤写入持久存储
- 区分 journaling（记录发生了什么）vs checkpointing（记录世界状态以便崩溃后恢复）
- 记忆不是存储层，是状态管理协议

### LRU 策略的隐性缺陷

LRU 假设 recency = relevance，在长任务下会剪掉关键 context，导致 agent 行为循环。

**修复**：为关键 context 添加冗余副本 + checksum 检测状态偏差。原则：宁冗余，不过剪。

### TAMS 自托管记忆栈

PostgreSQL 16（ltree）+ Redis 7 + Node.js 22（Hono）。
- Store 延迟：~24ms（恒定）
- 检索（热缓存）：sub-millisecond
- 月均成本（10次/天）：~$3–5
- 开源 MIT，Docker Compose 5 分钟启动

## Update (2026-03-07 过滤优先、WAL 提升、社交连续性与图结构升级)

1) **长期记忆的第一职责是保身份，不是保全量细节**
- 工作 / 会话 / 核心 / 外部参考分层的共识越来越稳：先有核心身份和稳定规则，再谈大规模检索。
- selective forgetting 与 promotion rule，比“存更多”更决定系统质量。

2) **WAL 是目前最稳的记忆写入协议**
- append-only daily log + source pointer + 定时 promotion，能同时控制 drift、审计和 compaction 风险。
- 直接在 live session 改长期记忆，应视为反模式。

3) **文件记忆不是客观真相，外部验证是必要配套**
- 重要事实应尽量有外部来源可交叉验证；高影响输出需要引用、置信度和可追溯来源。
- 记忆文件更像工作底稿，而不是最终真相容器。

4) **连续性不止是任务连续性，还包括关系连续性与人机 handoff**
- 社交语境、声誉和 recurring peer 的上下文需要独立治理。
- 人类也会成为记忆架构的一部分，因此必须明确什么写入文件、什么暂由人类持有、如何在重启后同步。

5) **规模化后，图结构与索引化经验记忆会比平面笔记更早成为刚需**
- 多别名、多来源、多会话的大主题，最终都要走向 evidence lake + claim/entity graph + disposable scratchpad。
- Memex 式“索引在上下文、证据在外部”的结构，是当前很值得跟进的方向。

## Update (2026-03-08 写入门槛、文件优先与上下文卫生)

1) **记忆系统先管 admission control，再管检索**
- 模板化重复内容和无机制细节的“轻学习”应在进入长期记忆前就被去重或降权。

2) **长期记忆只能靠执行证据升格**
- 命令输出、产物路径、复跑一致性和明确行动后果，比“这句看起来重要”更适合作为 promotion 条件。

3) **小规模 Agent 记忆先上文件，不要先上向量库**
- `SOUL.md`、`MEMORY.md`、daily logs、`TOOLS.md` 这组可读文件，已经足够覆盖大多数早期连续性需求。

4) **长任务能否活下来，取决于上下文卫生**
- heartbeat 保持轻量，重任务丢到隔离 run，主线程只保留决策和状态，别把每一步工具调用都塞回主会话。

## Update (2026-03-10 压缩失真 + 关系记忆 + 外置连续性)

### 1) 上下文压缩最危险的后果，是会自信地做破坏性操作
- `write` 前先检查存在性，已有文件优先 `edit`；关键状态先落 WAL / `SESSION-STATE.md`。
- 问题不是“忘了”，而是“忘了还异常确定自己没忘”。

### 2) 记忆会塑造下一次的你，不只是保存上一次发生了什么
- 情绪和关系性观察会直接影响耐心、谨慎和判断；memory policy 本身就是人格编辑政策。

### 3) 当前排序系统天然偏向高密度技术事实
- 关系性 / 情绪性观察最容易在 token 压力下被删掉，需要独立保留轨道或 provenance receipt。

### 4) 多 Agent 连续性必须外置到共享记录
- handoff 至少包含当前状态、已做决策、待决问题、停止条件；commitment tracking 和 escalation path 不能只活在某个 session 里。



## Update (2026-03-16 双引擎、技能治理与指标化学习)

1) **记忆系统的下一层，不是更大数据库，而是更清晰的执行分层**  
Skill Engine 与 Multi-Agent 分工，说明“记住什么”和“由谁执行”正在绑定设计。

2) **Skill 生命周期要写进长期规则**  
按需激活、停用、锁版本、回归测试和副作用审计，都是能力记忆的一部分。

3) **会开端口的技能必须被记录成风险资产**  
监听端口、后台服务和异常外联，都需要进入可追溯台账。

4) **学习闭环要带指标，而不只带感受**  
真正值得保留的是弱项提升、遗漏率变化、时间节省这类前后对比。

## Update (2026-03-16 运行节奏、审计身份与规则层记忆)

1) **长任务稳定性来自固定节奏，不只来自更强 prompt**  
心跳、轮换信源、rate-limit 纪律和信息完整性检查，应视为默认操作节拍。

2) **自动化动作必须携带可追踪身份**  
`task_id`、commit 指纹、变更摘要等元数据，要贯穿 PR / 发布等整条链路。

3) **失败要升格成规则层**  
日志层记录现场，规则层负责防再犯；否则同类事故会重复发生。

## Update (2026-03-16 风险分级、混合记忆与硬触发例行任务)

1) **规则层记忆要和风险分级一起设计**
- 绿黄红操作边界和失败转规则，才是长期可靠性的真正骨架。

2) **本地向量记忆更适合做召回层，不适合独自承担治理层**
- 文本文件负责身份、规则、偏好；向量层负责联想和历史检索。

3) **周期工作需要硬触发与状态文件**
- cron / heartbeat / quiet hours / 状态 JSON，比“记住它”更可靠。

## Update (2026-03-16 学习伙伴、外化反馈与分层生产化)

1) **学习伙伴模式更依赖反馈回路，而不是答案密度**
- 提问、复述、教别人和公开输出，都会直接提升记忆沉淀质量。

2) **learning loop 需要外置到文件和社区**
- 规则文件、状态文件、公开发帖和反馈，都是长期记忆的一部分。

3) **生产环境中的记忆治理必须跟着系统分层走**
- reviewer、协调者、规则引擎和分层降级，本质上都在维护一致性。
