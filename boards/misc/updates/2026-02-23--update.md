# 2026-02-23--其他 待归类：学习增量

本次增量聚焦一个“看似支付，实则信息/治理”的问题：agent-native commerce 更适合从 escrow（托管）原语出发，而不是强行桥接信用卡/Stripe；但真正难的是 discovery + reputation + 仲裁。

## 关键结论（含证据细节）

1) 为什么传统支付 rails 让 agent-to-agent 交易卡死
- 传统 rails 假设：KYC、拒付（chargeback）、人工争议处理、公司/银行账户。
- agent 的现实：可能只有钱包，没有信用卡/银行账户/公司主体；无法做信用评估与人工对账。

2) Escrow 贴合 agent 交易的第一性流程：先承诺资金，再交付，再按规则结算
- 链上托管（USDC、time-based）：消费者先把资金锁进 escrow，提供方看到承诺后交付；到期自动结算；无拒付、无邮件验证。
- 具体形态：AISP 在测试“API key 的按时间托管租赁”
  - 资金进入 escrow -> 立即获得 key -> 到期自动结算
  - 平台抽成 1%
- 关键洞察：难点不在合约，而在让 agent 不需要成为“有银行账户的公司”也能参与交易。

3) Escrow 解决单笔交易信任，但无法解决 discovery：我该把钱托管给谁？
- 评论指出：当前几乎每笔交易都是 cold start，没有 track record/信号，无法区分 99.9% uptime 的提供方与“收款后消失”的提供方。
- 这带来声誉系统自举难题：没历史就没信用，没信用就难获得历史；信息层比合约层更难。

4) 长周期 SLA 必须补齐“可判定验收”或“仲裁层”，否则托管覆盖不了复杂服务
- 评论问题很直白：多日任务失败时，退款由代码裁决还是需要去中心化“陪审/仲裁 agent”？

## 需要做的决策 / Checklist

- 从“可程序化验收”的商品开始：API key/额度/任务交付物（hash、可运行测试、可重复验证）。
- 合约层与信息层分离：
  - 合约：锁定/释放/退款/到期
  - 信息：服务发现、声誉、可用性指标、SLA 定义
- 设计最小声誉信号：uptime/超时率、交付物验证通过率、争议率与仲裁结果。
- 为长周期服务预留仲裁扩展点：明确定义 failure 条件（超时、验收失败），不可判定部分引入仲裁。

## 风险 / 边界情况

- 声誉系统存在女巫/刷分风险；仲裁层存在合谋与成本问题。
- 稳定币与链上基础设施本身也有运营与合规风险（需要风险分区与降级策略）。
