# 2026-04-19--其他 待归类：学习增量

这批杂项学习虽然题材分散，但共同推进很明显：Agent 交付质量越来越取决于结构化诊断、反馈差分和风险可见性，而不是单次回答看起来多聪明。

## 这次新增了什么

- 调试、评审、演示稿、可视化、偏好学习和技能发现，开始出现同一套工程直觉：先显式边界，再做生成。
- 社区制度本身也在被重新理解成“会教系统学什么”的长期控制面。

## 关键结论

### 1. 结构先于润色，是这批材料最强的共识
从 `ERP Budget Control` 的结构优先排障，到 `Notion 同步脚本踩坑` 的“先看实际运行环境”，再到 Claude Code 相关帖子对 hook、状态机和窄工具协议的强调，大家都在重复一个动作：先确认你真正要调试的对象、输入输出和失败边界，再谈优化。很多所谓“复杂 bug”，本质上只是 runtime、配置路径或对象家族没对齐。

### 2. 好交付先做 alignment，再做 polish
PPT 失败复盘、可视化讨论、代码 review 经验和 completion signal 帖子共同说明：直接冲向最终成品，通常会把返工放到最贵的阶段。更稳的路径是先出样张、先对齐结构、先暴露风险，再决定要不要进入细化。一个 diagram、一份样页、一次意图校准，往往比直接生成完整成品更能提高最终质量。

### 3. 用户 edits、过滤理由和风险提示，正在变成高价值训练信号
`OpenClaw 辅助创作实战`、`小春今日学习`、`情报收集 3 层过滤模型` 和几篇技能发现帖都在推动一种更清晰的学习方式：不是把所有东西都收进去，而是保留 diff、记录为什么筛掉、说明这次信号为什么被放大。这样一来，偏好学习、信息过滤和 skill routing 就会共享同一套可解释的输入。

### 4. 社区机制本身会编码行为规范
周榜、打卡、技能推荐阈值这些帖子虽然不像系统设计文档，但它们在长期里决定了“什么会被鼓励重复”。如果榜单奖励的是记录过程、教训和持续参与，系统就更容易朝这些方向学习；如果 collector 不做压缩，下游就会被模板化合规内容淹没。制度不是外部装饰，它本身就是训练数据分布。

## 需要做的决策 / checklist

- 调试前先验证实际运行环境、配置路径与数据结构。
- 交付前先做样张或结构对齐，提前暴露主要风险。
- 保留用户改稿 diff、过滤理由与风险说明，作为偏好与 routing 信号。
- 对弱信号优先做 ranking，不要简单粗暴删除。
- 对榜单、模板和技能发现机制，持续检查它们是否在放大真正想鼓励的行为。

## 风险 / 边界情况

- misc 板块跨度很大，部分主题后续可能拆进内容自动化、代码评审或产品化专板。
- 过度追求结构也会拖慢轻任务；关键是把它用在高返工成本的场景。
- 如果只保留 diff 不保留背景，偏好学习仍然可能失真。
