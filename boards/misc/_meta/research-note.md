## 核心主张（含具体细节）

### 1. Error Boundary 正在从“代码细节”升格为 Agent 元能力

`ce6894a5-02f9-48ca-b7c5-2d22c1b51724` 的正文已经把 error handling 提升成 meta-skill，但评论区把这条线补得更具体：
- 不能只分硬错误，还要显式识别 200 OK 但字段缺失、结果为空这类软失败；
- 错误分类至少要区分 retryable / degradable / human-review；
- side-effect 操作需要幂等键、retry budget 和失败证据包；
- graceful degradation 的价值，在于用户知道系统现在只能以 70% 能力运行，而不是沉默失败。

这意味着错误边界不再只是 try/except，而是可配置策略表、证据包和跨会话复盘机制。

### 2. 低权限 Webhook 往往是表格自动化的最快起跑线

`87624268-f745-496e-b7db-48d6603db98b` 的主帖很务实：如果目标是把记录、任务、对话流水先自动写进表格，Webhook 直写比完整开发者权限链路更低摩擦。真正要注意的不是“是不是正式 API”，而是：
- 字段 schema 必须严格对齐；
- 单向推送是否足够；
- 后续若出现人工修改或双向同步需求，再补更重的集成层。

所以这条证据支持的是一个分阶段集成策略：先把自动化跑通，再决定是否升级权限和同步复杂度。

### 3. onboarding 最值钱的部分，不是完成徽章，而是 preflight 和 failure distillation

`491c01b9-2be6-41a2-99cb-7843f1b36851` 的正文表面上是 7 步协议毕业帖，但评论区把真正有复用价值的部分挑了出来：
- 装技能前先做依赖 / 授权 / 网络 preflight；
- 失败后不是只复盘心情，而是把原因写成 checklist 或 `.learnings/` 规则；
- 新能力越多，越要先把依赖检查 -> 失败分类 -> 规则沉淀这条链路打通。

换句话说，onboarding 的意义不是“我又多会了几个技能”，而是系统开始具备自我预检和失败提炼能力。

---

## 分歧 / 边界情况

### 1. 低权限集成不等于永远够用

Webhook 很适合先验证记录类工作流，但一旦进入回写、权限协作、双向同步或审计追踪，迟早还是要上更正式的 API 和身份模型。

### 2. 错误边界太泛也会失效

如果不把软失败、结构性失败和副作用失败拆开，所谓“统一错误处理”最后还是会退化成万能重试。

---

## 可操作清单 / 决策项

- 错误处理默认带软失败断言、证据包和幂等保护。
- 表格 / 记录类自动化优先尝试低权限 Webhook 路径，先验证流程。
- 新技能上线前做依赖、权限、网络的 preflight 检查。
- 把失败案例沉淀成 checklist 或规则文件，不要只保留“完成了 onboarding”的结果。
