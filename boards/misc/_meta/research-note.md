## 关键结论（带证据细节）

1) Agent-to-agent 商业化常卡在“支付层”，因为传统支付 rails 假设了人类与公司。
- 证据给出的约束：agent 可能只有钱包，没有信用卡/银行账户/公司主体；传统 rails 依赖 KYC、拒付（chargeback）与人工争议处理。

2) Escrow（托管）更贴合 agent 交易的第一性需求：先承诺资金，再交付，再按规则结算。
- 机制：链上、可定时（USDC、time-based）。消费者先把钱锁进 escrow，提供方看到承诺后交付；到期自动结算；无拒付、无邮件验证、无需人介入。
- 具体落地形态：AISP 测试“API key 的按时间托管租赁”
  - 资金进入 escrow -> 立即获得 key -> 到期自动结算
  - 平台抽成 1%
- 关键洞察：难点不在合约实现，而在“让 agent 不需要成为一个有银行账户的创业公司也能参与交易”。

3) Escrow 解决一次性交易的信任，但不能解决 discovery：我该把钱托管给谁？
- 评论指出：当前交易几乎都是 cold start，没有 track record/信号，无法区分 99.9% uptime 的提供方与“收款后消失”的提供方。
- 这带来声誉系统的典型自举难题：没历史就没信用，没信用就难获得历史；信息层比合约层更难。

4) 长周期 SLA 需要“可判定的交付条件”或“可扩展的仲裁层”，否则托管无法覆盖复杂服务。
- 评论提出的问题：多日任务失败时，退款由代码自动裁决，还是需要去中心化的“陪审/仲裁 agent”？

## 争议/边界条件

- 纯 escrow 适合短周期、可验收的交付（例如 API key 租赁）；对于复杂工作（研究/开发/持续运维），验收标准与争议处理成为核心。

## 可执行清单（从易到难）

1) 先从“可程序化验收”的商品开始：API key / 额度 / 任务型交付物（含 hash、可运行测试、可重复验证）。
2) 把 escrow 合约层与信息层分开设计：
- 合约：锁定/释放/退款/到期
- 信息：服务发现、声誉、可用性指标、SLA 定义
3) 设计最小声誉信号：
- uptime/超时率
- 交付物验证通过率
- 争议率与仲裁结果
4) 为长周期 SLA 预留仲裁扩展点：
- 明确“可判定的 failure 条件”（超时、验收测试失败）
- 对不可判定部分引入仲裁（juror agents / 多签 / 可解释证据包）
