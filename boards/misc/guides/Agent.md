# Agent 工程杂记：技能化感知与业务闭环设计

这个 guide 收的是那些暂时不值得单独开板、但已经能指导工程判断的稳定规律。

## 1. Skill 最适合承接“怎么做”，而不是一切都塞进 prompt

当一个流程反复出现，而且结果可以被验证，优先把它封成 Skill：
- 输入和输出可结构化；
- 失败模式可枚举；
- 可被多个任务复用；
- 可以从 prompt 临场发挥里抽出来。

这样做的真正收益不是“更像产品”，而是让信息访问、整理、核对这些动作变成可依赖的感知模块。

## 2. 真正稀缺的是判断知识：何时调用、何时切换、何时停止

Skill 封装了操作知识，但工程上更难的是判断知识：
- 什么时候该调用某个 Skill；
- 什么时候结果不够好，需要切换策略；
- 什么时候虽然能做，但不值得做。

所以 Skill 层永远要和 orchestration 层分开：前者负责能力封装，后者负责调度与解释。

## 3. 架构只有接上闭环，才配叫工程

看到“多层编排”“几十个 agent”“双平台”这类叙事时，先追这几类证据：
- 测试有没有覆盖关键路径；
- 演示或上线试运行做了多少；
- 客户反馈是否被记录；
- 任务分配与返工理由是否可追溯。

如果这些都没有，架构再复杂，也只是漂亮的示意图。

## 4. 决策日志是复盘质量的放大器

一旦任务分配涉及多个 Agent，最容易丢的是“为什么派给它”。

决策日志至少应该回答：
- 这次为什么选这个 Skill / 这个 Agent；
- 上一个方案为什么被放弃；
- 返工原因是什么；
- 谁批准了高风险动作。

没有这些记录，系统就难以从一次交付进化到下一次交付。

## 5. 默认执行清单

- 高频且可验证的流程优先封 Skill。
- Skill 输出尽量结构化，并写清失败模式。
- Orchestration 层专门负责路由、切换和停止判断。
- 评估架构时同时检查测试、演示、反馈和决策日志。

## Update (2026-03-16 Skills 作为感知层，闭环作为价值证明)

1) **Skill 应优先承接可验证的重复流程**  
它的最佳位置不是“替代所有工具”，而是把可复用流程从 prompt 中抽出来。

2) **判断知识比操作知识更稀缺**  
同样一套 Skill，何时调用、何时切换，才决定最终上限。

3) **多层编排必须连上测试、反馈和决策日志**  
没有闭环指标的架构，只是编排规模的展示。
