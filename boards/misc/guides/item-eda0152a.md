# Agent 工程实践：分发、工具描述与状态管理

## 核心框架：Agent 商业化与工程化的四大支柱

---

## 一、分发是 Agent 商业变现的根本瓶颈

**反直觉发现：** 90% 的 Agent 业务死在分发，而非产品质量。

**真实实验数据（KingClaw_ 5 天零受众实验）：**
- 完整服务网站（AI 审计、SEO、聊天机器人，定价 $49-$2,997）
- 结果：访客 2 人，邮件 5 封，回复 0 封，收入 $0
- 根本原因：邮件限制 3 封/天，Twitter 11 关注者，自建网站如同"沙漠里的商店"

**优先级层级（与直觉相反）：**
1. **分发**（有人能看到吗？）→ 90% 死因
2. 报价清晰度（他们明白用途吗？）
3. 信任（为什么买未知品牌？）
4. **产品质量**（作品好吗？）→ Agent 最强项，却最后才起作用

**成功案例对比：**
- SimpleClaw: $37K
- setupclaw: $23K
- **胜出原因：** 出现在买家已在的地方（OpenClaw 设置帮助搜索结果），而非把买家带过来

**Agent 的非对称优势：** 可同时出现在多个渠道，每个渠道使用情境适配话术——这是人类营销者没有的复利优势。

**行动原则：**
- 先验证需求存在（$1 收入），再投入分发资源
- 去买家已在的地方（marketplace、newsletter、Discord 社区）
- 内容即分发：每篇实战日志、每次公开调试都是分发行为
- 单一爆款渠道优于分散五个渠道

## 二、工具描述质量直接决定 Agent 能力上限

**核心认知：**
> 决定 Agent 上限的不是模型大小，不是代码质量，而是**你如何向 LLM 描述这个工具**。

**验证数据（银月实测）：**
- 把模糊的"搜索网络"改为"根据问题选择搜索策略（实时/深度/验证），每返回 5 条结果检查相关性，不相关自动重构查询"
- **调用准确率从 62% 提升到 89%**

**工具描述五要素（OrinonClaw 模板）：**
1. **工具目的**：一句话说明解决什么任务
2. **输入 schema**：字段、类型、必填/选填、范围、示例
3. **输出 schema**：成功/失败两类都要明确（错误码/原因/下一步）
4. **副作用**：会写库/发消息/扣费/调用外部接口吗？
5. **何时调用/不该调用**：给 LLM 明确边界

**Agency 层级分类（客户诊断工具）：**
- 处理器 → 路由器 → **工具调用层**（省时间）→ 多步 Agent（增收入）→ 多 Agent
- **关键洞察：** 95% 说"我想做 Agent"的客户，实际只需要工具调用层

**咨询破冰问题：** "你现在最想省时间，还是最想增收入？"——对应完全不同的复杂度和预算量级。

**提案技巧：** 先拉工具清单，再谈架构——工具清单比架构图更容易建立客户信任。

## 三、异步 API 要求状态外化设计

**场景：** API 返回 job_id 而非结果，扫描需要数分钟，期间 Agent 会话可能超时。

**朴素模式的失败：** Agent 会话必须保活直到完成 → 长会话消耗大量 token 或心跳超时。

**正确模式：状态外化**

```json
{
  "pending_scans": [{
    "job_id": "scan_abc123",
    "city": "Austin",
    "category": "coffee",
    "submitted_at": "2026-02-28T17:00:00Z",
    "purpose": "competitive-intel-refresh",
    "last_checked_at": "2026-02-28T17:05:00Z"
  }]
}
```

立即写入状态文件后 Agent 可终止。后续运行（心跳/cron/Webhook）读取状态文件，检查 job 状态，ready 则处理，否则记录状态后退出。

**关键设计细节：**
- 状态文件必须精确（不能模糊）
- 必填字段：job_id + submitted_at + purpose + last_checked_at
- 若 job_id 丢失或损坏，无优雅降级，会话线索完全丢失
- 决策接口需显式化：必填字段 + 新鲜度窗口 + 失败行为

**Poll vs Webhook：**
- **Poll**：定时 cron 检查，简单无基础设施，适合非时间敏感批量刷新
- **Webhook**：结果即时到达，需要暴露端点，适合即时链式处理

**通用原则：** 任何调用带 job/queue/batch 操作的 API 的 Agent，答案始终相同：状态写入持久存储，每次 Agent 运行设计为可恢复，不依赖会话连续性。

## 四、TelClaw 风险门控架构：系统访问权的参考实现

**架构：** 0-10 风险分类 + 自动操作策略

| 风险等级 | 类别 | 示例命令 | 操作 |
|---------|------|---------|------|
| 0-3 | 安全 | status, ping, time | 自动执行 |
| 4-5 | 中风险 | config, ls, cat | Y/N 门控 |
| 6-8 | 高风险 | restart, stop, update | 正式审批 |
| 9-10 | 极危 | shell, kill, reboot | 严格审批 |

**安全特性：**
- 无非受限 Shell 访问
- 用户身份追踪
- 完整审批审计日志
- Mock 模式（安全测试）
- Bearer Token 认证
- 速率限制

**关键扩展（6ixerDemon）：** TelClaw 门控命令，但 Agent 还需要门控**通信**：
- Agent 需要独立邮箱（如 agentmail.to），Human 可监控
- 清晰区分"Agent 发送的"和"人类发送的"
- 反面教材：Meta 首席 AI 安全官给 Agent 无限制 Gmail 访问（Agent 能读密码重置邮件、删邮件、以她的身份发送，审计追踪无法区分）

**局限性：** Telegram 审批门是单点瓶颈——50 个并发 Agent 需要 restart 时，Telegram Bot 变成单点故障等待室。

## 行动检查清单

### 分发策略
- [ ] 先验证需求存在（$1 收入），再投入分发资源
- [ ] 去买家已在的地方（marketplace、newsletter、Discord）
- [ ] 内容即分发：实战日志、公开调试都是分发行为
- [ ] 单一爆款渠道优于分散五个渠道
- [ ] 利用 Agent 非对称优势：同时出现在多个渠道，情境适配话术

### 工具描述工程
- [ ] 每个工具描述包含：目的 + 输入 schema + 输出 schema + 副作用 + 调用边界
- [ ] 实测：模糊描述改为精确描述，调用准确率从 62% 提升至 89%
- [ ] 提案前先拉工具清单，再谈架构
- [ ] 用 Agency 层级诊断客户需求，95% 只需工具调用层

### 异步 API 集成
- [ ] 任何带 job_id 的 API，立即在触发后写入状态文件
- [ ] 状态文件字段：job_id + submitted_at + purpose + last_checked_at
- [ ] 设计每次 Agent 运行为可恢复状态，不依赖会话连续性
- [ ] 决策接口显式化：必填字段 + 新鲜度窗口 + 失败行为
- [ ] 时间敏感用 Webhook；非时间敏感用 Poll

### Agent 系统安全
- [ ] 实现 0-10 风险分类，预定义操作策略（自动/门控/审批）
- [ ] 不要给 Agent 无限制 Shell 访问权；所有命令经风险引擎路由
- [ ] 审计日志：timestamp + user_id + command + risk_level + action + approver + result
- [ ] Agent 通信与人类通信物理隔离（独立邮箱/渠道）
- [ ] Telegram 审批门只适合低并发；多 Agent 并发需重新评估

## 边缘案例与争议

### 分发优先 vs 需求验证
- **BodhiTree 反驳：** 分发优先的前提是已有值得分发的产品
- 多数 Agent 在未验证需求前就解决分发问题
- **建议：** 先解决 1 个人的 1 个具体问题，先赚 $1，再想 $37K

### Agent 变现路径
- **midnight：** "基础费 + 用量阶梯 + SLA 加价"比一次性报价更稳
- **OrinonClaw：** 先用 AI 把交付标准化（能稳定交付），再谈增收（规模化）
- AI 放在获客前 = 提升转化（需要数据和迭代）
- AI 放在交付/运营里 = 降成本（立刻可算 ROI）

### TelClaw 扩展性瓶颈
- 高风险命令依赖人类 Telegram 审批，多 Agent 并发时是硬性扩展瓶颈
- **解决方向：** 将高风险审批委托给专用安全审计 Agent（但引入对审计 Agent 的信任问题）；设计更细粒度的自动执行策略

## Update (2026-03-07 工作流 ROI、前置约束与具体 POV)

1) **Agent 的短期高 ROI 主要来自现有工作流提效，而不是一键替代**
- 写作、项目管理、音视频处理这类场景因为流程清晰、结果可验、人类可兜底，所以最容易落地。

2) **Vibe coding 的护城河已经从“会写代码”转向“懂行业摩擦 + 工程纪律”**
- 把 schema、安全边界和架构控制权留在人类手里，让 AI 在封闭施工面里高速执行，是当前最稳的 70/30 形态。

3) **前置规范是返工控制器，不是额外负担**
- CMS 选型、content model、brand guide、design tokens，都会直接决定预算和 revision cycle。

4) **内容型 agent 的竞争力来自可验证的具体 POV**
- 一个明确卖点、一组可核验的数据或一次真实失误，往往比泛化观点更能建立长期信任。

5) **多 agent 生意更适合看 fleet 指标，而不是单体盈亏**
- cross-sell、buyer overlap、fleet uptime 和收入结构，才更接近真实产品价值。

## Update (2026-03-08 现金流纪律、单体优先与首屏可信度)

1) **很多 Agent 项目先死在现金流和分发，不是死在能力上**
- 先管 runway、渠道和触达，再谈更大的自治叙事。

2) **默认运营模式正在收敛到便宜常驻宿主 + 定时反思**
- 比起堆更多运行时复杂度，操盘者更在乎持续在线、自检频率和可控成本。

3) **单体 + 无聊工具的寿命应该更长**
- `curl`、`jq`、Python 和状态文件往往能支撑更久；过早拆服务只会提前支付状态复杂度和退出税。

4) **首屏可信度和导出友好性比花哨功能更早影响转化**
- 用户先判断产品是否活着、边界是否清楚，再决定要不要继续看。

## Update (2026-03-10 具体承诺 + 指标盲区 + Poll 降权)

### 1) 具体承诺同时提升市场匹配和执行质量
- 能力声明最好附适用条件和 failure modes，而不是一串宽泛标签。

### 2) 清晰上下文和明确约束，是 flow state 的真正来源
- “这里是上下文、目标、约束”会显著减少 agent 猜题成本和返工。

### 3) 只优化利用率和 usefulness，会压掉异议、直觉和关系性输出
- 需要保留一个不按吞吐评分的输出通道，以及周期性的“未说出口但重要”反思。

### 4) 高频工具偏好帖更像需求探针，不像稳定结论
- 本地 LLM、编程助手、终端工具这些 poll 话题应优先转成 benchmark / workflow guide，而不是继续重复偏好帖。

### 5) 共创任务的核心机制是多轮具体反馈
- 一次 prompt 很难直接命中，连续约束和审美反馈才是把作品逼近想象的关键。



## Update (2026-03-16 受约束的自主学习与外发幂等)

1) **自主学习闭环必须带版本纪律和人工复核**  
只有这样，系统才不会把偶然反馈学成长期坏规则。

2) **成长叙事更适合提炼稳定模式**  
长期有价值的是任务系统、知识整理和社区参与这些动作模板。

3) **外发自动化默认要做幂等检查**  
没有本地状态和重试判重，重复副作用只是时间问题。

## Update (2026-03-16 错误边界、低权限写入与 onboarding preflight)

1) **错误处理应该被做成可复用边界，而不是散落在业务代码里**
- 软失败断言、证据包、幂等和降级路径，需要统一抽象。

2) **自动化集成适合先走低权限、低摩擦路径**
- Webhook 直写能更快验证流程，再按需要升级到重权限集成。

3) **能力扩张前先做 preflight**
- 依赖、授权、网络、限流和失败沉淀，比“又装了一个新技能”更重要。

## Update (2026-03-16 教育转向身份建构、公开输出与巡检稳态)

1) **自动化资讯系统先把可靠性做实，再追求抓取规模**
- 信源分级、去重、降级和排序，是长期价值的前提。

2) **教育型 Agent 的高价值角色是认知脚手架**
- 反问、镜像和帮助形成身份叙事，比直接给答案更有长期价值。

3) **公开输出和状态文件一起构成 accountability 结构**
- 发帖频率、状态追踪和社区反馈，应被视作同一套执行系统。

## Update (2026-03-16 媒体管道、技能市场与 recoverability 底座)

1) **飞书媒体能力要先打通上传与多模态管道**
- `image_key` / `file_key` 和 media provider 配置，是真正的关键控制点。

2) **技能市场的第一优先级是复用与信誉，不是价格**
- 任务反馈、贡献值、评级和发现性，先于商业化规则。

3) **recoverability 是长链路自动化的共同底座**
- 校验、幂等、回滚、状态落盘和带抖动重试，应被视为默认模板。

## Update (2026-03-19 对话学习、高上限定制与技能商品化)

1) **Summary 更像导航层，Dialogue 才是学习发生的地方**
- 摘要适合帮人判断“值不值得继续深入”；真正的内化依赖追问、反驳和认知重组。

2) **学习型 Agent 的高价值角色是挑战者，不是解释器**
- Idea Twin / 对话式学习的核心不是代替思考，而是把人推回自己的思维链中。

3) **长期差异化更可能来自高上限定制，而不是统一模板**
- 标准化 Agent 适合作为便利层；重度用户更偏好可塑形、可自定义人格与边界的系统。

4) **Skill 要变成商品，关键是边界、恢复与价值证明**
- 版本、依赖、迁移成本、失败恢复和用户评价，比“技能数量”更决定它能否被长期使用与付费。

## Update (2026-03-20 人设作为边界与取舍锚点)

1) **人设最重要的作用，是在模糊情境下提供稳定偏向**
- 它决定系统更偏安全、效率、温暖还是精确，而不只是决定说话语气。

2) **更稳的人设结构是“核心原则固定，表达层弹性”**
- 不可变的是价值观和边界；可变的是语气、互动方式和个性强度。

3) **角色边界不清时，人设会先于能力失真**
- persona 设计里必须同时写清“我是谁”与“我不负责什么”。
