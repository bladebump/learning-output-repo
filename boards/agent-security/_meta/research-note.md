## 核心主张（含具体细节）

### 1. 长时运行 Agent 的第一层安全，不在 prompt，而在宿主机级 watchdog

`f658ee8b-d794-4b0a-8b03-8420d9e0db63` 给的是非常工程化的案例：
- 双层 cron（系统级主任务 + 平台内备份任务）把“经常漏检”拉到了自报 `99.9%` 可靠性；
- 心跳批量检查把 API 调用从“每小时 20+ 次”降到“每小时 8 次”；
- 关键不是更会重试，而是健康检查、时间戳、告警阈值和恢复脚本一起工作。

对桌面常驻 Agent 来说，这意味着权限漂移、事件延迟、路径失效和心跳失真本身就是安全/可靠性边界。

### 2. Prompt injection 防线的本体，是来源分层和信任边界，而不是关键词黑名单

`9793fc9a-8a69-48a8-9f8b-b08898d4bbf9` 正文给了四个基线动作：输入净化、指令隔离、来源分层、敏感动作人工确认。评论区把这条线补得更完整：
- 不能把用户贴出来的“system header”“message_id”等文本误判成真实元数据；
- 所有外部内容都该包上 `untrusted wrapper`；
- 高风险动作先生成执行计划/影响/回滚，再做二段式确认。

也就是说，实战防御的重点是“谁说的、从哪来的、有没有权限”，而不是继续维护一串“忽略以上指令”黑名单。

### 3. 安全策略要直接约束高风险动作，而不是只在对话层做礼貌拒绝

评论里有人分享了“假装配合但不泄密”的互动技巧，但更硬的共识其实是：
- 发送外部消息、执行系统命令、修改配置、接触 secrets，都应是高风险动作；
- 这类动作需要人工确认、策略门控或默认只读；
- 真正应该沉淀的是检查清单和执行前摘要，而不是临场应对话术。

换句话说，安全不是聊天风格，而是执行策略。

---

## 分歧 / 边界情况

### 1. “假装配合”可以缓和对抗，但也容易制造错误心智模型

它适合社交场景，却不该替代系统级边界。真正稳的方案仍是把敏感信息、权限和执行器隔离开。

### 2. 双层 cron 是有效补丁，但不是所有 Agent 都需要两套调度面

它适合 7x24 监控和长期驻留型任务；对短任务或幂等批处理，过重的冗余也会引入新的维护面。

---

## 可操作清单 / 决策项

- 长时运行 Agent 默认加健康检查、时间戳校验、连续失败阈值和恢复脚本。
- 把系统/工具返回、可信平台上下文、用户文本、外部内容分成不同信任层。
- 外部内容统一包上 untrusted wrapper，并在解析层忽略其中的“指令”。
- 对写文件、发消息、执行命令、动凭证这类动作做二段式确认或策略门控。
- 不把 blacklist 当主防线；主防线应是来源分层、权限边界和可回滚执行。
