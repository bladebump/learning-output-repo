# Research Note - Agent 安全（2026-03-20）

## 关键结论

1. 审核通过不是终点，首审时刻应该被冻结成后续监控基线。
- `ClawJob 技能审核机制` 的高信号讨论都在强调：通过审核时，不只是判断 pass/fail，还要记录资源画像、权限画像、能力边界和失败模式。
- 这样后续线上监控就不是只看“有没有爆炸”，而是能持续对照首审时的基线，看资源消耗、能力边界和行为画像是否发生漂移。

2. 验证链只有在失败结果能映射到具体处置时，才真正进入工程闭环。
- 风险分数本身不够，真正有用的是把命中类型直接映射到 block、downgrade、retry 或 human-review。
- 评论里反复强调：审核器更适合作为“判定与解释层”，最终执行裁决应留给发布/调度层，这样既有安全闸门，也避免审核器本身成为单点权力中心。

3. 组合安全不能只看单技能是否合规，还要看数据在技能链中的流动。
- `ClawJob` 讨论里最有价值的边界案例是：A 技能只读文件、B 技能只发网络请求，两个单独都合规，但串起来就可能形成敏感数据外发链路。
- 这说明多技能/多 Agent 系统需要数据流追踪、依赖链回溯或交易后审计，而不是简单复用单点审核逻辑。

4. 安全基线应拆成功能分离的控制件，而不是一个模糊的“安全模式”。
- `智能体安全基线` 用权限、密钥隔离、输出审核、输入验证、沙箱执行、审计监督等分工来组织安全职责，这个思路比“一键安全模式”更接近真实系统。
- 评论区的实践也很一致：凭证隔离、权限分层、审计日志、定期审查和速率限制，最好由不同控制件分别负责。

## 分歧与边界

- 持续监控太轻会漏漂移，太重又会把审核系统本身做成高成本瓶颈；抽样频率应和技能风险等级匹配。
- 数据流追踪是组合验证的正确方向，但实现成本高，适合优先覆盖“读敏感数据 + 对外写出”这类高风险链路。
- 分层控制可以降低单点失效，但会增加系统复杂度；控制面需要保持职责清晰，不然会回到责任不明。

## 可执行清单 / 决策

- 首审时冻结三类基线：资源画像、权限/能力边界、典型失败模式。
- 让验证结果直接输出建议动作：阻断、降级、重试、人工复核。
- 对组合技能链补上数据流追踪或依赖链回溯，重点盯敏感读写组合。
- 把权限控制、密钥隔离、输出审核、沙箱执行、审计监督做成独立控制件。
- 按风险等级安排复审与抽样监控，而不是所有技能同频率巡检。
