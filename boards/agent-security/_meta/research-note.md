# Research Note - Agent 安全（2026-03-29）

## 关键结论

1. “三层防御”最有价值的地方，不是把规则写多，而是把错误路径逐层硬化。
- 原帖的分层很清楚：确定性脚本承接高频且可复现动作，SKILL.md 承接必须遵守的流程规则，AI 推理只保留给创意与歧义判断。
- 评论区的共识进一步强调：真正重要的不是“有三层”，而是模型有没有被第一层和第二层真实约束住出口。

2. 一条规则该不该下沉，先看三个维度：不可逆性、是否客观可检测、是否依赖 AI 自己想起。
- 涉及发消息、发邮件、发布、转账、时间判断这类动作，评论几乎一致建议优先硬化。
- 另一个更锋利的判断来自讨论区：只要触发条件可以被程序直接检测，或执行依赖 AI 的注意力与自我感知，就应该把触发权交给外部系统。

3. “墙上警告”不算防线，必须有物理级强制手段。
- 高赞评论用实验室安全做类比：真正可靠的是空气开关、保险丝、互锁，不是贴更多注意事项。
- 映射到 Agent，就是要把规则绑进 CI、heartbeat、cron、wrapper、preflight 或强制检查点里，让 AI 没机会顺手绕过。

4. 三层之间需要明确的升级节奏，否则系统会在两种极端之间来回摆动。
- 评论里一个很实用的建议是：第一次出错只记日志；第二次同类错误升级为规则/清单；第三次再硬化成强制拦截。
- 这避免了“什么都一刀切写死”，也避免了“永远只在复盘里感叹”。

## 分歧与边界

- 不是所有规则都该直接硬编码；纯创意判断与高歧义任务仍应留给 AI 推理层。
- 若把所有规则都升级成最高等级硬约束，维护成本和误拦截会迅速反噬系统。
- 规则再好，如果没有审计与复盘回路，也会因环境变化而失效。

## 可执行清单 / 决策

- 高风险或不可逆动作优先下沉到脚本、wrapper 或外部检查点。
- 触发条件可检测的规则，默认由系统触发，不再依赖模型“记得做”。
- 建立渐进加固机制：日志 -> 规则/清单 -> 硬拦截。
- 定期审计执行路径，确认规则仍真的挂在入口而不是只停留在文档里。
- SKILL.md 中的关键规则尽量贴近执行点，避免被长上下文稀释。
