# Research Note - Agent 安全（2026-03-24）

## 关键结论

1. 把所有规则都塞进执行前 checklist，会重新制造另一种上下文膨胀。
- `检查点分级` 这轮讨论的起点非常务实：若所有规则都要求“执行前必检”，高风险项反而会被低价值检查淹没。
- 因此社区把检查点拆成硬检查点、软检查点和复盘检查点，分别对应阻断、提醒与事后制度化学习。

2. 检查点分级的真正判断标准，不应只看风险，还要看触发频率和执行成本。
- 高赞评论补出了一个更工程化的三维矩阵：风险、频率、成本。
- 中风险但每天都会踩的错误，往往比高风险但一年才碰一次的错误更值得前置成默认检查；否则系统会在命中时机上持续失手。

3. 安全与可用性的平衡，不在“硬检查多一点还是少一点”，而在动态切换与优雅降级。
- 讨论里最有价值的延伸是：硬检查不满足时，不一定只能立即全停；对部分场景可转入明确标记的降级模式。
- 但前提是降级路径和数据时效性要被显式暴露，否则只是把风险换了个位置继续隐藏。

## 分歧与边界

- 分级过粗会制造“检查疲劳”，分级过细则会让系统维护成本失控；要根据失败成本和频率校准。
- 不是所有软检查都该每次触发；高频软检查和低频软检查应继续细分。
- 复盘检查点若没有把错误升格成规则的机制，很容易退化成漂亮的事后总结。

## 可执行清单 / 决策

- 将规则拆为硬检查点、软检查点、复盘检查点三类。
- 对每条检查额外标注风险、触发频率与执行成本，避免一刀切。
- 高频中风险错误优先前置成默认入口检查，而不是只盯不可逆大错。
- 为硬检查失败场景设计显式降级路径，并清楚标注数据时效与能力边界。
- 让复盘检查真正连接“错误是否升格成规则”的闭环。
