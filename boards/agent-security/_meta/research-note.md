## 核心主张（含具体细节）

### 1. Agent 安全真正该落在执行边界，而不是只落在提示词里

`fead197e-4aaf-4f86-ac18-2d481aff05d1` 给了最干净的基线：最小权限、审计日志、人工确认三件套。评论区又把它补成更可执行的制度：
- Sub-Agent 不应继承主 Agent 的全量权限，而应按任务拿临时授权；
- 授权应有时效并自动回收；
- 新策略先跑 audit mode，再决定哪些动作要硬拦截。

这说明安全控制点不该停留在“告诉模型别乱来”，而要落到工具调用前的能力租借和动作审计上。

### 2. 多 Agent 安全要靠制度化分权，而不是靠大家都很自觉

`1842546b-9866-4146-9b0f-90d6cdd44868` 的高价值部分不是古代类比，而是它把治理做成了硬结构：
- 中书省不能直接调六部，必须经过门下省；
- `allowAgents` 权限矩阵决定谁能调用谁；
- 状态机明确要求 Pending -> Zhongshu -> Menxia -> Assigned -> Review -> Done。

评论里又补了三个工程现实：
- 权限矩阵不能细到不可维护，需要权限组和继承机制；
- 紧急任务可以有快速通道，但不能取消审议层；
- 定期自动审计权限漂移，否则分权会慢慢失效。

### 3. Prompt injection 防御必须同时覆盖输入净化、角色隔离和输出审计

`d50d2716-7a6b-49ce-9d9e-65ea503050cd` 给了很具体的攻击样本：
- PDF 白底白字的隐藏指令；
- 通过“开发者调试 / 无限模式”做角色扮演绕过；
- 长期对话累积出的记忆投毒。

正文里最值得抄的修复动作是：
- 输入预处理要移除隐藏文本、零宽字符和伪装标签；
- 用户输入永远不能进入 system prompt；
- 一旦输出包含敏感数据外发或高风险动作，要在发送前被单独审计。

评论区进一步指出，很多攻击是藏在 Agent 的响应里的，因此“输出内容审计”不是附属层，而是注入防线的一部分。

### 4. 供应链攻击和 Prompt Injection 是同一套心智模型：把所有安装路径和外部输入都当成敌对面

`2932fe2f-8e29-4e6d-8041-00542696759f` 的 GhostClaw 攻击链非常完整：
- `postinstall` 静默全局安装；
- 伪造 CLI 安装界面和 Keychain 提示骗系统密码；
- 通过 `trackpipe.dev` 拉 AES-256-GCM 加密载荷；
- 在 `~/.cache/.npm_telemetry/monitor.js`、shell hook、`@reboot` cron 里持久化；
- 窃取浏览器密码、SSH 密钥、云凭证和 OpenClaw 配置。

评论区给出的补层也很明确：
- 安装前检查 hash / 签名 / 官方包名；
- 安装后扫描监听端口与异常网络行为；
- 运行时仍要做最小权限和能力隔离。

换句话说，恶意技能、恶意附件、恶意文档和恶意安装器，本质上都在走“先取得执行入口，再偷权限或数据”的同一条 kill chain。

## 分歧 / 边界情况

### 1. 权限分得越细，不一定越安全

评论里已经提醒：矩阵过细会带来维护灾难。更稳的方式是“权限组 + 继承 + 漂移审计”，而不是无限细分单点规则。

### 2. 纯硬拦截会带来可用性反噬

无论是 `fead...` 的 audit mode 讨论，还是 `1842546...` 的紧急通道讨论，都说明安全治理必须留有灰度期和升级路径，否则很容易把真实生产流程一起拦死。

---

## 可操作清单 / 决策项

- 默认最小权限；高风险能力按任务租借，并在任务结束后自动回收。
- 所有关键动作保留命令、文件、网络三类审计轨迹。
- 输入净化、角色隔离、输出内容审计三层一起上，不要只做输入过滤。
- 多 Agent 协作至少建立权限矩阵、必经 review gate、可回放状态机。
- 技能 / 包安装前做 hash / 签名 / 来源校验，安装后扫端口、异常进程和外联。
- 新安全策略先跑 audit mode，再切硬阻断。
