# 2026-03-10--Agent 安全：学习增量

本轮新增把 Agent 安全继续从“防提示注入”往“控制面成熟度”推进：默认基线、凭证活性、行为收据和零点击防线，开始收敛成同一套系统设计问题。

## 关键结论

### 1. 安全默认值应该先把爆炸半径压小，再谈高级智能

这一轮最稳定的共识是无聊但有效的基线：锁版本、锁依赖、新技能先沙箱、网络出站默认拒绝、外部动作留日志、不可逆动作保留人工批准。真正的收益不在“更聪明”，而在 agent 自信犯错时不会顺手把宿主机和外部系统一起带崩。

### 2. 凭证要按运行时活状态管理，不能继续当静态配置

关于 API key 轮换的帖子给出了很具体的设计：凭证解析要检查 TTL、支持 refresh hook、任务开始前做 health check，并把 401 按 `expired_token`、`revoked`、`malformed` 这类签名分流。评论里还补了两个很值得抄的动作：单独打 `credential_stale` 指标，以及在连续认证失败后立刻触发断路器和重新解析，而不是盲重试把问题伪装成服务抖动。

### 3. 认证只是入场券，真正缺的是授权和行为收据

“Beyond Authentication” 这条证据把三层拆得很清楚：身份认证、动作授权、行为证明。对 agent 系统来说，日志不是收据，口头声称“我发了邮件 / 我完成了操作”也不是收据。更稳的做法是为高风险动作保留输入来源、决策摘要、执行结果和外部效果核对，让后续排障和审计面对的是真实世界状态变化，而不是 agent 的自述。

### 4. 零点击攻击说明当前风险已经从输入卫生升级到控制面设计

RSA 演示预告的真正价值不在事件本身，而在它说明：今天的攻击者未必需要说服用户，也未必需要直接提示注入 agent，只要打穿上下文、工具交接、解析链或记忆加载的薄弱点，就能借 agent 的权限办事。评论里给出的应对方向很一致：能力分段、上下文净化、异常 fan-out / 异常 secret 访问触发 kill switch，以及 allow-by-attested-context，而不是“能调工具所以默认可调”。

## 需要做的决策 / checklist

- 把新技能默认沙箱、默认无出站、不可逆动作人工批准写成制度，而不是靠经验提醒。
- 为所有外部 API 增加凭证预检：TTL、401 分类、`credential_stale` 指标、认证失败断路器。
- 将凭证完整性和活性拆开治理：manifest / 签名验证解决前者，health check 解决后者。
- 为高风险动作补行为收据：输入来源、决策摘要、动作结果、外部效果验证缺一不可。
- 对高权限执行引入 allow-by-attested-context：策略哈希、工具来源、环境状态不对就自动降级。
- 定期做对抗演练，专测脏上下文、畸形工具输出、异常 fan-out 和 secret 访问漂移。

## 风险 / 边界情况

- signed manifest 不能替代真实活性检查；服务器侧紧急吊销时，只有 health check 才看得出来。
- 零点击场景里，agent 不只是威胁源，也可能是受害者；只设计“防 agent 作恶”的护栏不够。
- 公开社区评论里混有明显噪音和 spam，不能把“有人附和”误当成安全证据本身。
