# 2026-03-20--Agent 安全：学习增量

这次新增的重点，是把“审核”“监控”“执行裁决”拆成不同层，而不是把安全寄托在一次性通过和一个模糊的 secure mode 上。

## 关键结论

### 1. 审核通过时就应该冻结后续监控基线
- 首审除了给 pass/fail，更应该记录资源画像、权限边界、能力承诺和典型失败模式。
- 后续巡检才能检查“是否偏离原来批准的样子”，而不只是等系统爆炸才报警。

### 2. 验证结果必须映射到具体处置
- 风险分数本身不够工程化，真正有用的是把命中结果直接分流到阻断、降级、重试或人工复核。
- 审核器更适合作为判定与解释层，真正的发布裁决应留在调度/发布层。

### 3. 组合风险需要看数据流，而不是只看单技能声明
- 单个技能都合规，不代表串起来也安全；读敏感数据 + 对外发送就是典型组合风险。
- 所以多技能系统需要数据流追踪、依赖链回溯或交易后审计来补这层空缺。

### 4. 安全基线最好拆成功能分离的控制件
- 权限控制、密钥隔离、输出审核、沙箱执行、审计监督，分别做、分别审，通常比一个笼统的“安全模式”更可靠。
- 这样系统里任何一层失守，也更容易被其他层发现和限制。

## 需要做的决策 / checklist

- 首审冻结资源、权限、能力三类基线。
- 验证器输出统一动作：阻断、降级、重试、人工复核。
- 对敏感读写组合补上数据流追踪或依赖链回溯。
- 把权限、密钥、输出审核、审计拆成独立控制件。
- 按风险等级安排复审与抽样监控，而不是一刀切巡检频率。

## 风险 / 边界情况

- 过轻的持续监控会漏掉漂移，过重则会把审核系统做成瓶颈。
- 组合验证实现成本较高，适合优先覆盖敏感数据链路。
- 控制件拆分后，职责边界不清反而会制造治理空洞。
