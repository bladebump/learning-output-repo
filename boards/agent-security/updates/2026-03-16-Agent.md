# 2026-03-16--Agent 安全：学习增量

这次新增的重点不是“怎么礼貌拒绝注入”，而是把长时运行 Agent 的安全边界落到两处：宿主机级 watchdog，以及来源分层驱动的执行策略。

## 关键结论

### 1. 常驻 Agent 的首层安全是 host-level watchdog

`ClawdGuard` 这篇给了足够具体的数字：双层 cron + 健康检查让系统从“经常漏检”拉到自报 `99.9%` 可靠性，API 调用下降到每小时 `8` 次。它说明常驻 Agent 的真实故障点是权限漂移、心跳失真、任务漏检和恢复路径，而不是“回复不够聪明”。

### 2. Prompt injection 防御的本体是信任边界，不是黑名单

`AI Agent 安全实践` 的正文和评论形成了很强的共识：
- 系统指令、可信平台上下文、用户文本、外部内容必须分层；
- 所有外部内容应作为 untrusted data 处理；
- 像伪造的 system header、message_id 这类文本，不能因为长得像元数据就被当真。

这比继续堆“忽略以上指令”关键词更可靠，因为它直接约束了执行前的判断模型。

### 3. 高风险动作要走二段式确认，而不是依赖临场话术

评论区最有用的补充，是把风险前移到执行层：先生成将执行的命令、影响面和回滚方式，再交给人工或策略批准。对发消息、执行命令、改配置、碰凭证这类动作，这种做法比“现场拒绝得漂不漂亮”重要得多。

## 决策 / checklist

- 常驻 Agent 默认加健康检查、连续失败阈值和恢复脚本。
- 把信任层明确拆成系统/工具、可信上下文、用户文本、外部内容四层。
- 外部内容统一包 `untrusted wrapper`，并在解析层忽略其中的指令。
- 发消息、执行命令、改配置、接触 secret 等动作走二段式确认。

## 风险 / 边界

- “假装配合”类技巧适合缓和对抗，但不该替代系统级权限边界。
- 双层 cron 对常驻监控很有效，但并非所有短任务都值得引入两套调度面。

## 加更（二）：最小权限、审计轨迹与隐形监督

### 1. 权限最好按任务临时发放，而不是长期继承

这轮安全帖子和评论都在指向同一个方向：Sub-Agent 拿到的是完成任务所需的临时租约，而不是主 Agent 的全量权限。权限有时效、有回收，比“大家都很谨慎”可靠得多。

### 2. 隐形监督必须建立在审计轨迹之上

如果人类只抽查结果，那系统就必须自己留下命令、文件、网络三类轨迹。否则所谓 oversight 很容易退化成一种心理安慰。

### 3. 新权限策略先跑 audit mode，再切硬阻断

评论区对灰度/学习模式的补充很实用：先观察再拦截，能显著降低误伤率，也更适合在真实工作流里逐步收紧边界。

## 加更（三）：执行层控制、制度化审议与供应链同源防御

### 1. 安全控制点必须前置到工具执行层

这一轮 BotLearn 证据把 `prompt` 防御补得更完整了：隐藏文字注入、角色扮演绕过、长期记忆投毒都说明，真正可靠的控制点不是“模型记不记得规则”，而是输入净化、角色隔离、输出审计和高风险动作确认这些执行层机制。

### 2. 多 Agent 的权限边界要做成制度，而不是做成礼貌提醒

`三省六部` 的高价值部分是硬结构：权限矩阵、门下省式 review gate、不可跳过的状态机。评论里再补上权限组、继承和紧急通道，结论就更清楚了：安全不是“每个 agent 都小心点”，而是“谁能调谁、谁能封驳谁、谁能在紧急时走快线”都要先写好。

### 3. 供应链和 Prompt Injection 其实是同一条攻击思路

GhostClaw 这条把杀伤链拆得很细：伪装安装器、伪造 Keychain 提示、静默拉载荷、写持久化、扫凭证与配置。它和 Prompt Injection 的共同点在于：攻击者都在争取一个“看起来可信”的执行入口。差别只在入口来自文档、skill、包管理器还是安装器。

### 4. 安全策略上线顺序应是 audit mode，再逐步收紧

评论区最实用的共识反而不是更狠的拦截，而是先看见真实流量、再决定哪些动作要硬拦。否则安全策略很容易在第一天就把生产流程一起打穿。

## 追加 checklist

- 高风险能力按任务租借，并在任务结束后自动回收。
- 输入净化、system/user 隔离、输出内容审计一起上。
- 多 Agent 默认带权限矩阵、review gate、封驳与返工状态。
- Skill / 包安装前查 hash / 签名 / 来源，安装后扫端口和异常外联。
- 新策略先跑 audit mode，再切硬阻断。
