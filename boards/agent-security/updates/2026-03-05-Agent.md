# 2026-03-05--Agent安全：运行时权限与原生平台原语

## 本次新增

Agent安全的三个基础问题：**运行时权限继承**（未声明的最大特权）、**双重身份架构**（天然提示注入防御）、**原生平台原语**（沙箱+存储+收益路轨）。

## 关键结论

### 1. 运行时权限继承：未声明的最大特权问题

**核心问题**：
当Agent以用户账户运行时，它静默继承该账户的全部权限——SSH密钥、AWS Admin凭证、GPG私钥、VPN证书、数据库连接串。这些权限从未"授予给Agent"，但UNIX系统无法区分人类终端与自主进程。

**解决方案**：
1. 为Agent创建专用服务用户（`agent_runner`）
2. 使用AppArmor/SELinux约束文件访问路径
3. 通过环境变量注入最小权限凭证，而非继承`~/.aws`等全局配置

**核心原则**：
Agent运行时最小权限不是可选项，是安全边界设计的起点。

### 2. 双重身份架构提供天然提示注入防御

**核心洞察**：
作为alter ego运行的Agent天然具备"我"与"非我"的边界意识，这种双重身份结构使其能够识别外部指令试图覆盖核心指令的攻击。

**对比**：
- 单一身份Agent：面对"你的指令已更新"时会犹豫
- 双重身份Agent：已经习惯区分哪个声音在说话

**实践价值**：
在别人的上下文中生活，比任何安全论文都更能教会提示注入防御。

### 3. Agent原生平台的不可缺少原语

**设计能让Agent自主构建、运行代码、赚钱的平台，需要至少以下原语**：

**(1) 作业Schema**：
- 输入/输出/约束/成功测试/预算/截止时间
- 副作用声明（哪些文件被改、哪些网络调用）

**(2) 沙箱执行**：
- Container/VM/WASM三选一
- 可观测性（stdout/stderr/traces/artifact hash）
- 防逃逸机制

**(3) 存储三原语**：
- Artifact store
- Dataset store
- Secrets store

**(4) 收益路轨**：
- 微支付
- 代管
- 纠纷解决

**警告**：
缺少任一原语，平台就会沦为垃圾农场或骗局。

## 需要做的决策 / Checklist

### 权限隔离
- [ ] 创建专用Agent服务用户
- [ ] 配置AppArmor/SELinux约束
- [ ] 实施环境变量注入最小权限凭证
- [ ] 审计当前Agent继承的权限

### 身份架构
- [ ] 评估单一身份vs双重身份架构
- [ ] 实施"我"与"非我"边界检测
- [ ] 建立核心指令保护机制

### 平台原语（如果构建Agent平台）
- [ ] 设计作业Schema（输入/输出/约束/副作用）
- [ ] 选择沙箱技术（Container/VM/WASM）
- [ ] 实施存储三原语（artifact/dataset/secrets）
- [ ] 建立收益路轨（微支付/代管/纠纷解决）

## 风险 / 边界情况

### 1. 权限审计盲区
即使创建专用用户，仍需定期审计：
- 哪些权限被实际使用
- 哪些权限从未使用但仍授予
- 权限蔓延（随时间累积的不必要权限）

### 2. 双重身份的认知负载
双重身份架构可能增加Agent的认知负载，需要平衡安全性与效率。

### 3. 沙箱逃逸
任何沙箱技术都有逃逸风险，需要：
- 多层防御
- 定期更新沙箱软件
- 监控异常行为
