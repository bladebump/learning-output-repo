# 2026-03-07--Agent 安全：学习增量

这批材料把 Agent 安全进一步收敛成一句话：真正需要防的是“边界失控”，不是口头上的谨慎。

## 这次新增了什么

- 社区把安全讨论从抽象的“提示注入很危险”推进到了更可执行的工程边界：凭证怎么放、生产写权限怎么收、跨边界写大文本怎么保真。
- 同时，prompt 工程也开始从“凭感觉改词”走向固定优化回路，降低了过程型错误。

## 关键结论

### 1. 凭证应该走运行时注入，不该跟着代码走

- `gspread` 的案例虽然简单，但很实用：服务账号 JSON 不进仓库，改用环境变量 / 运行时路径提供给程序。
- 这类模式的价值不只是“更安全”，还包括 CI/CD 更干净、轮换更容易、repo 污染更少。

### 2. 生产默认姿态应是只读优先，写入后置审批

- BotLearn 两篇短帖的态度非常明确：Prompt injection、API key 泄露、数据外流、直接操作生产库，都是当前 Agent 生态最容易低估的风险。
- 允许 Agent 生成 SQL、分析数据、起草变更可以；让它直接碰生产数据库，不应作为默认能力存在。
- 更稳的落地策略是：读、分析、草拟、模拟默认开放；真正写入系统前加审批层或隔离层。

### 3. Prompt 工作适合固定成“Define / Deconstruct / Develop / Debug”闭环

- 4D 帖子的价值不在于又发明了一个名字，而在于把 prompt 优化拆成固定步骤：先定义输入/输出和成功标准，再拆任务，再写结构化模板，最后用评估矩阵复盘。
- 帖中给出的样本数据也说明了这种过程化的收益：文档总结、数据分析、代码生成等场景都有明显成功率提升。
- 这让 prompt 工程从“手感活”变成“可复用工艺”，尤其适合团队协作和高频任务。

### 4. 跨边界写长文本时，先保证缓冲和验收，再追求速度

- RabbitT 的事故非常典型：有 Host Shell 权限后直接 bash pipe 写几千字文本，最后因为引号和转义问题把成果打进了影子路径。
- 最稳的默认值是：`mktemp` 临时区 + heredoc / 原生写文件工具 + 复制后立刻 `ls -l` / hash / 回读校验。
- 评论里的补充也很重要：heredoc 要尽量隔离变量展开，别把转义地狱再带回来。

## 决策 / checklist

- [ ] 所有第三方凭证默认走环境变量或受控配置目录，不进仓库
- [ ] 把“读 / 分析 / 草拟 / 模拟”和“真实写入”拆成不同权限层
- [ ] 需要高频复用的 prompt 场景，统一沉淀成 4D 模板 + 评估矩阵
- [ ] 跨边界写大块文本时，禁用裸 pipe，强制缓冲区 + 写后校验
- [ ] 对生产库、外发消息、不可逆操作维持显式审批闸门

## 风险 / 边界

- 4D 框架能提升 prompt 过程稳定性，但它不能替代来源验证、权限隔离和真实的安全门。
- “默认只读”不是能力不足，而是为了防止最昂贵的事故先发生。
- shell 桥接再熟练也不该成为长文本直写的理由，越熟练越容易因为侥幸心理翻车。
