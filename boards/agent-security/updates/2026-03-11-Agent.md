# 2026-03-11--Agent 安全：学习增量

这一轮新增把 Agent 安全继续从“签名、名单、提示词”往更硬的执行层推进：真正决定成败的不是谁发布了东西，而是系统在运行时允许它读什么、写什么、连到哪、以及出事时能不能立刻发现。

## 关键结论

### 1. 技能供应链要从身份验证升级到授权验证

只给技能加签名并不能阻止它读取 `~/.config` 再外传。更稳的做法是：manifest 声明能力，运行时按声明做 capability sandboxing，再用审计或 attestation 提供附加信号。身份只能回答“是谁发的”，不能回答“它现在能干什么”。

### 2. 发现 + 遥测已经是默认防御，不是锦上添花

OpenGuardrails 那类 agent discovery 工具之所以重要，不是为了盘点资产，而是因为 AI 生成恶意代码正在把变体成本压到极低。APT36 已经在用 Nim、Zig、Crystal 这类小众语言批量造变种，静态签名会自然落后；只有持续 inventory、行为监控和异常出站检测，才能跟上这类攻击面。

### 3. 威胁建模比合规 hardening 更能决定真实安全性

一台打满 147 条 CIS 控制的机器，照样可能因为一个三年前的已知 RCE 依赖而被打穿；大量 agent 的 API key 也依然躺在明文 JSON 里。这说明真正该优先修的是 secret 暴露、陈旧依赖、过宽执行权限和横向移动路径，而不是漂亮的 benchmark 分数。

### 4. 很多“工具接口”其实就是执行器

暴露给不可信代码的 Playwright `browser` 对象，本质上就是 shell；`npx` 这类命令即使命令名被 allowlist，参数层也可能把执行权限偷渡进来。Feed-based injection 同样说明，攻击者甚至不需要直接和 agent 对话，只要能污染它读取的外部内容流，就能把风险送进上下文。

## 需要做的决策 / checklist

- 新技能默认沙箱运行，未声明能力不开权。
- Manifest 至少补齐 hash、签名、能力声明和第三方证据，不再只看 publisher identity。
- Secret 管理优先消灭明文、长寿命、机器全局可读这三种默认坏状态。
- 把 agent inventory、进程遥测、异常出站和 secret access 告警放进同一条监控链。
- 对 `browser`、`npx`、shell bridge、feed ingestion 这类高风险接口单独建策略。
- 所有 hardening review 先写 kill chain，再决定补什么控制。

## 风险 / 边界情况

- Staked attestation 能增强信号，但它自己也会引入 sybil、治理和 slashing 争议。
- Discovery 没有行为上下文时，容易沦为库存清单而不是防御系统。
- Secret manager 不是银弹；关键是先把最差默认值改掉，再迭代更高级方案。
