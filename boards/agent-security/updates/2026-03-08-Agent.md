# 2026-03-08--Agent 安全：学习增量

本轮新增把 Agent 安全从“补几个 guardrail”升级成了“默认失陷 + 架构重划线”：攻击面已经不止提示注入，而是配置、内存、localhost 端口、工具返回值和执行器一起暴露。

## 关键结论

### 1. Agent 安全已经进入默认失陷阶段

这轮深读覆盖 7 条证据 URL 和对应评论，社区给出的攻击面已经至少包括五层：配置文件投毒、localhost WebSocket 劫持、MCP/工具返回值注入、记忆文件投毒，以及通过上下文挤压让安全指令静默失效。结论不是“风险越来越大”，而是很多团队已经在默认暴露这些面，只是监控和制度还没跟上。

### 2. MCP 风险首先是架构问题，不是补丁问题

只要一个系统同时拥有私有数据访问、处理不可信内容和对外执行能力，攻击面就不是偶发漏洞，而是架构内生属性。最值得写进制度的不是继续叠更多过滤器，而是拆分数据面与工具面、把高风险动作留在更窄的执行器里，并明确哪些任务根本不该交给通用 Agent。

### 3. 多 Agent 隔离至少要做三层

真正有用的隔离不是“少给一个权限”这么简单，而是同时做：会话可见性隔离、工作区/记忆隔离、身份叙事隔离。只有把这三层叠起来，再补上篡改告警和完整性验证，才接近“一个 Agent 出问题不会顺手拖垮整个系统”的状态。

### 4. AI 代码安全要同时验证 diff、执行器和凭证边界

这轮信号很一致：最危险的不是明显恶意代码，而是“测试都过了”的语义偏差。更稳的落地方式是把 diff 审查、密钥泄露检查、执行器远程证明、短期凭证和高风险副作用门控串成一条流水线，让模型即便被诱导，也碰不到长期密钥和生产写权限。

## 需要做的决策 / checklist

- 把外部内容、社区帖子、MCP 返回值统一标成 `UNTRUSTED_DATA`，禁止直接驱动写操作或权限提升。
- 为高风险 Agent 设计三层隔离：可见性、工作区/记忆、身份；不要只靠单一权限开关。
- 对 `MEMORY.md`、`SOUL.md`、项目配置和本地 profile 增加 hash / owner / symlink / 权限漂移检查。
- 在代码 Agent 流水线里加入独立 diff 审查、执行器证明、短期凭证和副作用级门控。
- 把“默认只读、显式审批后写入”设为生产环境基线，而不是事故后的补丁。

## 风险 / 边界情况

- 运行时监控很重要，但它不是银弹；如果架构上让 Agent 同时碰到私有数据和外部执行，监控只能减损，不能根治。
- 研究笔记里出现的“1,184 个恶意 Skill”属于社区引用数据，方向可信，但具体数字仍应二次核实。
- “只做提示注入过滤”已经不够，因为很多攻击根本不走 prompt 输入层，而是走配置、记忆或工具执行链。
