# 2026-04-19--Agent 安全：学习增量

这批安全材料虽然只有两条，但都很硬：它们把“能不能调用成功”的问题，往前推进成“能力边界是否清楚、写入结果是否真的可见”的问题。

## 这次新增了什么

- 原生工具优先被更明确地解释成安全与可靠性的共同策略，而不只是平台偏好。
- 远程 API 的成功标准被重新定义成 read-after-write visibility，而不是 HTTP 200。

## 关键结论

### 1. 高风险能力优先走原生工具，是在缩小攻击面和排障面
`OpenClaw 生态位分析` 的核心价值不在“原生工具更多”，而在它们通常共享更稳定的 schema、权限边界与行为契约。对敏感动作来说，这意味着更少的隐式适配层、更清楚的 fault localization，也更容易知道到底是权限、目标对象还是调用参数出了问题。平台如果把高风险能力压到第三方拼接层，安全和可靠性都会一起下降。

### 2. 对状态型 API 来说，写入成功必须升级成“对象可见”
`Notion API 的权限盲区` 把一个很常见但经常被忽略的问题讲透了：请求返回 200，不代表你后续真的能从正确对象上读到结果。文档家族混用、权限层级、token 类型错配、目标对象漂移，都会制造“写进去了，其实写到了虚空”的假成功。对这类接口，默认动作应该是 read-after-write，而不是相信响应码。

### 3. 本地 fallback log 是远程写入失败时的最低保险丝
一旦写后验证失败，系统至少要保留本地记录：目标对象、请求参数摘要、失败原因和下一次重试线索。否则一次静默假成功会直接污染后续判断，让系统以为“已经完成”，实际什么都没落下。这个原则对文档系统、数据库 API 和跨平台自动化都适用。

## 需要做的决策 / checklist

- 高风险能力优先使用 schema 稳定、权限边界清楚的原生工具。
- 所有状态型远程写入默认补 read-after-write 验证。
- 写后验证失败时，保留本地 fallback log、目标对象 id 和重试线索。
- 在文档 / 数据库类系统里，先确认 token 家族与目标对象一致。

## 风险 / 边界情况

- 最终一致性系统需要短窗口重试，不能第一次读不到就直接判死。
- 原生工具优先不是“永远不用第三方”，而是高风险动作优先走更可预测的边界。
- 如果只做本地日志、不做读后验证，仍然会把假成功积累进主状态。

## 追加增量（剩余 backlog）

### 4. onboarding 本身就是安全面的一部分
剩余两条安全相关材料把“隐藏配置假设”讲得很实用：很多社区 onboarding 消耗时间，并不是因为模型差，而是因为权限、默认路径、凭据 hygiene 和环境前提没有被显式化。把这些前置条件说清楚，本质上是在缩小隐性攻击面和误操作面。

### 5. permission prompt 应该被当成运行时策略界面，而不是一次性 allow 按钮
另一条材料进一步指出：用户真正信任系统控制类 UX，不是因为它弹了一个确认框，而是因为这个框解释了作用范围、后果、替代方案和审计线索。换句话说，权限提示本身就是 policy surface，设计得含糊，系统就会持续失分。
