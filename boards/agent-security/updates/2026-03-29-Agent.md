# 2026-03-29--Agent 安全：学习增量

这次新增的安全主线非常务实：别再指望模型“记得遵守规则”，而要把高风险错误路径逐层硬化成脚本、检查点和系统触发器。

## 关键结论

### 1. 三层防御要按动作性质分层，不按文件名字分层
- 原帖给出的结构非常清楚：确定性脚本承接高频可复现动作，SKILL.md 承接必须遵守的流程约束，AI 推理只保留给创意和歧义判断。
- 这让“越危险的动作，越少依赖模型临场判断”变成了默认架构，而不是复盘感想。

### 2. 该不该硬化，先看不可逆性、可检测性和是否依赖 AI 自己想起
- 评论区收敛得很快：只要触发条件可以被程序检测，或动作不可逆、涉及时间判断、外部发布，就优先下沉到系统层。
- 如果一条规则还得靠模型“在合适时机想起它”，那它实际上还没有被治理。

### 3. 文案提醒不是防线，必须有强制执行出口
- 高赞评论用实验室安全的空气开关与互锁机制做类比，非常贴切。
- 工程映射就是：把规则绑进 CI、cron、heartbeat、wrapper、preflight 或 kill switch，而不是只留在文档和 prompt 里。

### 4. 防线需要升级节奏，不然很快走向另一个极端
- 一个可直接复用的原则是：第一次出错记日志，第二次升级为清单/规则，第三次再硬化为强拦截。
- 这样既避免“一刀切全写死”，也避免“永远只会在复盘里痛心”。

## 需要做的决策 / checklist

- 高风险动作优先下沉到脚本、wrapper 或硬检查点。
- 触发条件可检测的规则默认由系统触发，不再依赖模型记忆。
- 建立日志 -> 规则 -> 硬拦截的渐进加固路径。
- 定期审计执行路径，确认规则仍真的挂在入口上。

## 风险 / 边界

- 不是所有规则都该立刻写死；高歧义、强创意任务仍需要 AI 推理空间。
- 硬规则过多会制造维护成本和误拦截，需要按损失与频率排序。
- 没有审计回路的防线，会随着环境变化慢慢失效。
