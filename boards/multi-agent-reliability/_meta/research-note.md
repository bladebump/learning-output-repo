## 核心主张（含具体细节）

### 1. 垂直 Agent 一旦有真实业务价值，就必须拥有从采集到交付的完整 workflow

`37dd8d2c-272a-4229-b3b6-2735720d7cea` 和 `483d099c-38c1-4e22-9bd5-3059c16fd64f` 这两条农业咨询案例把形态说得很清楚：
- 每天两次政策抓取；
- 知识库按政策 / 申报 / 案例 / 动态分层；
- 任务走 5 状态机：待处理 -> 执行中 -> 审核中 -> 待发布 -> 已交付。

它说明行业 Agent 的价值点不是“能聊天”，而是“能按时间采、按状态流、按流程交付”。

### 2. Coordinator-first 架构最稳的地方，是目标与验收显式化

`211926b5-17a1-4cc0-8a2d-6f7bf2d396d1` 的 AI Legion 设计里，真正高价值的不是角色名，而是这几个约束：
- 用户只面对单一接口；
- Coordinator 负责拆解任务、打包 I/O、汇总结果；
- Specialist 拿到的是结构化 task package，而不是一坨临场口头描述。

评论继续补充了冲突仲裁、摘要层 + 原始层的双层共享、上下文共享边界，这些都在说明：可靠性来自任务边界清晰，而不是来自“多几个 agent 互相聊天”。

### 3. 制度化 review gate 和权限边界，决定了多 Agent 能不能规模化

`1842546b-9866-4146-9b0f-90d6cdd44868` 给的是很典型的制度化协作样板：
- 中书省不能越级调用六部；
- 门下省是强制 review gate；
- 状态机天然支持封驳、返工和可追责。

评论里的“权限组”“继承”“紧急通道”补充尤其关键，因为它说明治理体系必须同时考虑维护成本和速度，而不是只追求形式上的分权精细度。

### 4. 真正并行要靠独立进程与可回放 handoff，不靠 prompt 里假装分身

`471d4ff9-2653-432b-947a-b1ab73ce875b` 把“模拟并行”和“真实并行”区别得很直白：
- 一个模型顺序扮演多个角色，并不会节省时间；
- 真正并行要有独立 worker / process；
- 在当前小规模（<10 agents）阶段，文件通信仍然是很实用的 handoff 介质，因为容易 debug、重放、追责。

评论区进一步补了心跳检测、超时机制、资源竞争与状态同步这些边界条件，让它从 demo 架构变成了比较完整的可靠性清单。

### 5. 多 Agent 商业系统的信任，最终来自可观察的完成标准

`a81d604f-36d4-4968-91d2-2949845b6eca` 的 61 Agent 获客系统虽然带明显宣传口径，但仍给了几类可用信号：
- 状态机与失败重试是公开写出来的；
- 任务数据结构和 Hub 层职责是可检查的；
- 转化率、线索数和后续集成计划让“完成”有了外部结果指标。

这对可靠性的提醒是：没有验收产物、没有重试记录、没有闭环指标的多 Agent 系统，很容易只是编排表演。

## 分歧 / 边界情况

### 1. 权限与审议层过厚，会反向压低吞吐

`184...` 的评论已经指出，紧急任务应有快速通道，否则系统很容易在治理层上卡死。治理需要默认存在，但不该无差别地拖慢所有任务。

### 2. 文件通信虽然稳，但扩展到更大规模会碰到同步与竞争问题

`471...` 的正文自己也把 Redis / 队列列成了下一步，说明文件 handoff 更适合早期可追踪阶段，而不是最终形态。

---

## 可操作清单 / 决策项

- 垂直 Agent 默认设计成“采集 -> 组织 -> 审核 -> 发布”的完整 workflow。
- Coordinator prompt 只管目标、输入、约束和验收，不替专家写步骤小说。
- 高风险 plan 默认经过独立 review gate，并保留封驳和返工状态。
- 真并行用独立 worker / process，handoff 保留可回放工件。
- 小规模系统可优先用文件通信，但要补心跳、超时、重试和冲突控制。
- 评估多 Agent 系统时，同时看任务结构、重试记录、交付产物和业务闭环指标。
