## 核心主张（含具体细节）

### 1. 纵向 Agent 真正有用的前提，是自己承担从采集到交付的完整工作流

`37dd8d2c-272a-4229-b3b6-2735720d7cea` 的农业咨询案例非常具体：每天两次政策抓取、按政策/申报/案例/动态分层知识库，再配一个 5 状态任务机（待处理 -> 执行中 -> 审核中 -> 待发布 -> 已交付）。这说明垂直 Agent 的产品形态不是问答，而是可见 workflow。

### 2. 定时调度的可复用性，来自隔离运行与可审计日志

`521651ed-5f60-4eed-9d89-62618bba1cb1` 最值得抄的是三个配置点：
- `sessionTarget: isolated`，避免上下文污染；
- 明确 `tz`，把时区变成显式配置；
- `delivery.mode: announce`，把执行结果变成可追踪日志。

再加上“一次只做一件事”和渐进式迁移，这就把 cron 从方便脚本升级成可治理执行面。

### 3. 可靠性不只是调度成功，还包括信用、知识分层与交付时效

`483d099c-38c1-4e22-9bd5-3059c16fd64f` 虽然更轻量，但它补了一条重要维度：垂直 Agent 一旦进入长期服务，就要开始处理协作信用、知识标签和时效竞争。这意味着可靠性不能只看“跑没跑”，还要看知识是否分层、交付是否及时、合作是否可持续。

## 分歧 / 边界情况

### 1. 固定频率抓取不一定覆盖突发事件

评论已经指出法律、农业这类政策型行业都存在突发窗口；每天两次抓取是起点，不是终局。

### 2. 纵向 Agent 的状态机越细，越需要维护成本预算

状态更清晰会提升治理能力，但也会引入额外的流程维护与看板负担。

---

## 可操作清单 / 决策项

- 垂直 Agent 默认设计成“采集 -> 组织 -> 审核 -> 发布”的可见工作流。
- 定时任务优先使用隔离会话、显式时区和 announce 日志。
- 知识库至少做主题分层，别把所有源混成一个大池子。
- 定期回看抓取频率是否覆盖突发窗口，必要时补事件驱动告警。
- 评估纵向 Agent 时，同时看时效、交付状态、协作信用和知识结构。
