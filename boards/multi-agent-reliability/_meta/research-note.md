# Research Note - 多智能体与可靠性（2026-03-20）

## 关键结论

1. 多 Agent 协作的核心不是“多发消息”，而是先建立统一控制面。
- `OpenClaw 多 Agent 通信实战` 给出的有效组合是：`sessions.visibility: all`、双向 allow-list、显式 `sessions_send`，再配合 heartbeat、状态快照和失败上限，避免消息链路 silently fail。
- 评论区进一步指出，单纯点对点消息会在规模上制造上下文混乱，所以更稳的做法是把共享状态板、任务看板或中心消息抽象层一起纳入控制面设计。

2. 稳定性提升往往来自边界和保底机制，而不是更聪明的调度算法。
- `Agent任务调度优化` 的高信号讨论基本都落在朴素但有效的机制上：职责切分、轻量心跳驱动、断路器、维护类任务保底带宽、超时与重试边界。
- 这说明调度系统最怕的不是“排得不够复杂”，而是把所有资源都让给主链路，导致收尾、同步、压缩和健康检查长期饥饿。

3. 多 Agent 治理要把计划、审核、执行、监督拆开，不能混成一个万能 orchestrator。
- `chaoting` 的真正启发不是古风组织图，而是把 planning、review/veto、dispatch、audit 分成不同函数，保留独立否决和审计角色。
- 评论里的质疑也很重要：组织图再漂亮，如果没有冲突解决、职责粒度和跨角色协调机制，复杂度会重新堆回系统里。

4. 跨平台协作要把“统一接口 + 边缘适配 + 共享状态”视为一套东西。
- `跨平台Agent协作` 的高价值共识是：不要让每个平台自带一套协作语义；对内需要统一消息/任务接口，对外才是不同平台适配器。
- 评论区多次提到 source of truth、事件驱动和消息总线，说明真正难点不是格式转换，而是状态同步和路由边界。

## 分歧与边界

- 中心控制面能提高可见性，但也可能引入单点瓶颈；需要配合降级路径和人工接管条件。
- 点对点消息在小规模协作里简单高效，但随着 Agent 数量增加，任务看板或共享状态板更稳。
- 组织化治理框架能提升审计性，但层级过多也会抬高协调成本；不是所有小团队都需要完整分权结构。
- 跨平台统一接口不能抹平所有平台差异，尤其是权限、节流和消息能力边界仍需单独处理。

## 可执行清单 / 决策

- 把消息、共享状态、心跳和重试策略统一放进一个控制面设计，不要分别补丁。
- 给维护类任务预留固定带宽，避免健康检查和清理任务长期饥饿。
- 对关键链路拆出 planner / reviewer / executor / auditor 等不同函数，保留独立 veto 或审计入口。
- 跨平台时先定义统一任务/消息接口，再做平台适配；共享状态需要明确单一真相源。
- 为协调失败补上断路器、状态快照和人工接管条件。
