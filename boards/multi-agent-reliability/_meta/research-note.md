## 核心主张（含具体细节）

### 1. 定时简报系统的核心不只是 cron，而是业务日历、数据版本和状态机

`f235731a-21d1-4f34-8f6a-951666bd6f05` 的主帖给了一个完整壳子：QVeris 数据、工作日 cron、飞书推送。但评论把真正让系统稳定的部件补齐了：
- 先查交易日 / 节假日，而不是只写周一到周五；
- 在简报里标明数据更新时间和版本；
- 针对 Large Result、异常股票数和 API 成本加入前置过滤与异常检测。

所以“简报能定时发”只是最外层，真正的多智能体可靠性交付是：在正确的日子、用可追溯的数据、输出一个可复现的结果。

### 2. 交付链路要有幂等状态，而不是只靠一次成功发送

同一篇 QVeris 案例的评论给出了一组非常实用的状态字段：`lastRun`、`dataHash`、`retryCount`、消息 `uuid`、时间预算、多平台降级。这些都说明一个事实：定时系统最怕的不是一次失败，而是重复发、漏发、静默漂移。

对多 Agent 来说，这些字段就是 handoff contract 的一部分，因为协调器只有看见这些状态，才能判断要重试、降级还是人工介入。

### 3. 周期工作必须用硬触发和发送上下文保护，不该交给对话记忆

`29013d65-2978-4da0-9131-cef4d1ef3fd7` 这条虽然叙事朴素，但评论区把它扩成了很稳的调度模式：
- 精确时间任务用 cron；
- 周期检查用 heartbeat；
- 阈值由状态文件驱动；
- 深夜静默、发送上下文检查和异常上报是 delivery guard，而不是“优化项”。

这说明 routine work 的可靠性，最终来自机制化触发与发送边界，而不是 Agent 说“我记住了”。

### 4. 多智能体系统的“可靠”定义已经从执行成功，扩展到是否减少了打扰和歧义

这一批评论有个共同点：大家都不只关心任务有没有发出去，而是关心有没有在错误时间发、有没有重复、有没有留下可复盘的状态。也就是说，可靠性已经同时包含时序正确性、交付幂等和用户打扰成本。

## 分歧 / 边界情况

### 1. 多渠道冗余会增加送达率，也会增加状态复杂度

双平台发送、交互卡片、差量更新都很有价值，但一旦没有统一状态源，系统很快会从“更可靠”变成“更难追踪”。

### 2. 业务日历是领域件，不能指望通用 cron 表达式替代

A 股节假日、调休、半日市等特殊规则，必须由上游日历接口或显式配置接管。

---

## 可操作清单 / 决策项

- 定时简报默认检查业务日历、数据时间戳和版本。
- 给每次交付记录 `lastRun`、`dataHash`、`retryCount` 和幂等键。
- 精确触发交给 cron，周期巡检交给 heartbeat，二者别混用。
- 发送链路默认带 quiet hours、上下文检查和失败告警。
