# 多智能体协作：教练式管理、异议通道与交接包

这份 guide 关注的不是“怎么堆更多 agent”，而是多角色系统要长跑时，哪些治理结构必须先立起来。

## 1. coordinator 是教练，不是执行代理的替身

最稳的 coordinator 默认职责只有五件事：
- 定义成功条件
- 给边界与红线
- 路由到合适角色
- 验收结果
- 在冲突时裁决

它不应该：
- 替执行层写每一步做法
- 抢做专业角色已经能做的判断
- 把所有信息都压成一句结论再往上交

## 2. handoff 必须标准化

一个最低可用的 task packet 至少包含：
- 角色
- 任务
- 优先级
- 截止时间
- 验收标准
- 写回要求

没有这个 packet，多 Agent 协作很快就会退化成“大家都很聪明，但没人能说清这次到底该交什么”。

## 3. 决策包要暴露推理过程

执行层默认不要只交结论，而要交：
- 选项
- 理由
- 置信度
- 风险 / 盲区

这件事的价值不在形式，而在于让上层真正能追问、否决、改权重。否则 orchestrator 很容易掉进“我已经看见全貌”的幻觉。

## 4. 异议通道必须是制度件

执行层发现指令有问题时，必须有权：
- 请求澄清
- 提出异议
- 升级仲裁
- 触发独立审计

没有这条通道，层级结构只会把错误传得更快，而不是更稳。

## 5. 监督视角最好独立于主流程

一个健康的多 Agent 系统，至少要有一种视角不直接参与业务执行，只负责：
- 检查是否超时
- 检查是否 no-progress
- 检查交付是否满足验收
- 检查信息是否被过滤失真

否则系统会自然学会“报喜不报忧”，表面更顺，实际更危险。

## 默认 checklist

- coordinator 默认只做目标、边界、路由、验收、裁决
- 所有任务 handoff 都用 packet，不能靠自然语言口头交代
- 执行层默认交 options + reasons + confidence + risks
- 高风险任务必须有封驳与升级路径
- 冲突裁决要写回共享记忆，沉淀成下次可复用协议
