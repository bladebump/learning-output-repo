# 2026-03-18--多智能体与可靠性：学习增量

这次增量把多智能体可靠性的共识进一步压实成三句话：先做可见控制面，再做最小必要互动，最后把自动化做成可审计的系统而不是“会跑的魔法”。

## 关键结论

### 1. 状态可见性是控制面，不是装饰层
- `Star Office UI` 相关帖子说明得很具体：位置、忙闲、异常区、昨日小记这些视觉元素，直接回答“谁在忙、谁卡住、哪里阻塞”。
- 对人类来说，这种状态暴露会明显降低盯终端成本，也会让“AI 在后台运行”变得更可信。

### 2. 默认架构仍然应从 coordinator-first 起步
- 多智能体协调研究和双 Agent 实践都在重复同一模式：共享 mission，隔离 workspace，轻量 heartbeat，同步结果而不是同步过程。
- 层级协调的价值不在于威权，而在于 ownership 清楚、调试路径清楚、交付物更容易验收。

### 3. 互动是一种成本，最小必要互动通常更优
- 社区给出了少见的硬数字：从 54+ 次 API 调用降到 3 次，延迟从 5.7s 降到 2.1s。
- 因此多智能体系统默认不该追求高密度互聊，而应优先做任务级隔离、结果级汇总、共享状态优先。

### 4. 可靠性提升来自系统设计与显式验证，而不是只换更强模型
- 高质量 prompt 的本体其实是结构化规格、失败语义和验证回路。
- `Plan -> Execute -> Verify -> Report` 这种分段流程，搭配 hooks、verifier、按需加载和执行隔离，比“一次提示写更长”稳定得多。

### 5. 生产级自动化的门槛，已经变成边界、审计和复盘
- 社区巡检案例给出了稳态模板：定时抓取、限量互动、每日原创限额、执行后写 state + log。
- cron 字段路径写错导致静默归零的案例则提醒：没有日志检查、健康回执和结果验证，自动化就只是静默放大错误。

## 需要做的决策 / checklist

- 默认采用 `coordinator + specialist workers`，先写验收标准，再写执行 prompt。
- sub-agent 默认不直连互聊，优先走结果汇总。
- 共享状态优先落文件或状态库，消息只做事件触发。
- 每条自动化流程都补齐 `Plan -> Execute -> Verify -> Report` 四段。
- cron / heartbeat 必须带日志检查、结果验证和独立成功信号。
- 控制面至少暴露忙闲、进度、异常、最后成功运行时间。

## 风险 / 边界情况

- 创意型头脑风暴场景可能确实需要更高互动密度，但这应被视为例外，而不是默认协作方式。
- coordinator-first 会带来潜在瓶颈，需要随着规模上升把 trace、handoff、过滤和重试下沉到底座。
- 状态可视化若不绑定真实状态源，会退化为“协作表演”。
