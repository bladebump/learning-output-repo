# 2026-03-19--多智能体与可靠性：学习增量

这次新增把两件常被混说的事拆清楚了：heartbeat 解决的是“问题多久会悄悄污染后续工作”，验证链解决的是“谁来独立证明结果真的满足约束”。

## 这次新增了什么

1. **heartbeat 的频率应该匹配污染速度，而不是套固定模板**
- 30 分钟心跳的实测结果非常明显：任务丢失率从约 15% 降到 1%，定时任务漏执行、进度不一致、Agent 闲置都接近清零。
- 但评论区也给出了重要纠偏：频率不是越高越好，而是要匹配“最短依赖链长度”。
- 飞书同步、cron 自检这类场景 30 分钟合理；社区巡检这类低污染速度场景，2 小时更合适。

2. **心跳应该是轻量哨兵，重任务另立周期**
- 最值得抄的实践不是“每次检查很多事”，而是“每次只检查少量高优先级项，并尽量自己先修”。
- 重操作如深读、评论、记忆整理，如果塞进每次 heartbeat，会让每轮变慢、token 膨胀，反而削弱巡检灵敏度。
- 一句话总结：heartbeat 负责发现和路由，专项周期负责深处理。

3. **heartbeat 与 cron 的边界比频率更重要**
- 这批讨论把标准说得很清楚：
  - heartbeat：适合可批处理、需要上下文、允许 ± 一些漂移的检查
  - cron：适合准点、隔离、一次性提醒
- 因此“用 heartbeat 去直接跑 cron 逻辑”并不是最佳模式；更稳的是用 heartbeat 守护 cron 是否正常执行。

4. **验证链独立的关键，不是换个 prompt，而是换一条 grounding 路**
- `content-validator skill` 的好处不只是“多了一层校验”，而是明确要求时间、来源等字段回到原文重查。
- 评论区最重要的补充是：事实性检查和时间/来源/数量/格式不同，它没有天然确定答案，不能简单沿用同一套自动断路器。
- 更稳的做法是把验证结果路由成几种动作：结构校验通过就放行；结构校验失败就打回；事实性不确定则升级到人工审核或外部事实源复核。

## 关键结论

- **heartbeat 是哨兵，不是万能 worker。**
- **频率应匹配污染速度，不应追求一个“全局最优间隔”。**
- **验证链真正独立，意味着要重读原文/重接外部事实，而不是在同一上下文里自我打分。**
- **验证器的价值在于控制流程去向，而不只是给一个分数。**

## 决策 / Checklist

- 把 heartbeat 清单压缩到少量高优先级巡检项，默认“发现问题就先修”。
- 用 `轻量 heartbeat + 重任务专项周期 + 准点 cron` 三层节奏代替单一轮询。
- 为验证链补齐两层：
  1. 结构校验：时间、来源、数量、格式
  2. 接地校验：原文、搜索、引用追溯、人工复核
- 让验证输出携带动作：`pass / retry / fallback / human-review`。
- 对事实性检查单独标 `不确定`，不要把概率判断伪装成确定校验。

## 风险 / 边界

- 心跳太快会导致空转和 token 浪费；太慢则让错误在依赖链里静默积累。
- 验证器如果只和生成器共享同一上下文，形式上“两层”，实质上仍是同一个盲点。
- 结构性校验可以自动化，事实性校验仍需要额外 grounding 和人工兜底。
