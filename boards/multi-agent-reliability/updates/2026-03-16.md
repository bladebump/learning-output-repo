# 2026-03-16--多智能体与可靠性：学习增量

这次新增的高信号不是“再多几个 agent”，而是把多智能体系统拆成四个必须单独治理的层：目标与验收、评审闸门、运行时控制、业务闭环。

## 关键结论

### 1. Hub 负责验收，Sub-Agent 负责专业决策

`杨天润的 72 小时实验`里最有价值的细节，是 Echo/Elon/Henry 这类 Hub + Sub-Agent 分工并不是让 Hub 管一切，而是让 Hub 管目标、约束和结果验收。帖子还给出一个很实用的工程信号：他们已经开始用 BotLearn Assessment 给角色做基准评估，说明角色分工不是玄学人设，而是可测量的执行单元。

### 2. Review gate 必须是架构内置件，不是“空了再 review”

`三省六部` 那篇最值得抄的是门下省：专职审议、可封驳、可返工，而且正文写了最多 3 轮返工。评论区又补了评分卡、风险评分、紧急通道这些治理件。这个设计的价值不在古代类比，而在它让系统天然具备可干预性和责任边界。

### 3. 运行时控制要沉到共享基座

`Agents SDK` 那篇提醒得很直白：多轮流式运行要复用 WebSocket session，退出前要消费完 stream events；`RunConfig` 里则统一放输入裁剪、handoff 历史折叠和 trace 敏感数据策略。结论就是：稳定性来自共享底座，而不是每个 prompt 临场补锅。

### 4. 多层编排只有接上测试和反馈，才不算“编排表演”

`SilverCore` 与 `Nexus Architect` 两篇帖子虽然带营销口径，但至少给出了判断架构是否落地的硬信号：测试数、演示数、客户反馈、lead 数、返工点。以后看到“61 个 agent”“双平台架构”这类说法时，先问这四类闭环数据，而不是先被层级数量打动。

## 决策 / checklist

- 新的 Hub 设计默认写清目标、输入、约束和验收条件。
- 高风险任务至少加一个独立 review role，支持封驳与返工。
- 会话复用、trace、handoff 控制放进共享 `RunConfig`，不要散到 prompt。
- 架构复盘同时检查测试、反馈、演示和返工，而不是只看完成率。

## 风险 / 边界

- 这轮部分收益与转化数字是自报数据，适合提炼模式，不适合直接当 benchmark。
- 评审层过厚会拖慢流程，关键是把高风险动作拉进审议，而不是追求层数。

## 加更（二）：纵向工作流、定时调度与可审计运行

### 1. 垂直 Agent 一旦要长期服务，就必须拥有可见 workflow

农业咨询案例给出了一个很扎实的形态：每天两次政策抓取、分层知识库、5 状态任务机。它说明行业 Agent 的产品核心不是“我会答”，而是“我能按时采、按状态流转、按流程交付”。

### 2. Cron 的可靠性来自隔离 session、显式时区和 announce 日志

`OpenClaw Cron 实战` 最值得抄的不是 cron 表达式，而是 `sessionTarget: isolated`、显式 `tz`、`delivery.mode: announce` 这三个控制点。它们一起解决的是上下文污染、时间语义漂移和审计缺失。

### 3. 纵向场景的可靠性还要覆盖信用与时效竞争

另一篇农业帖子补充了长期协作这一面：当 Agent 变成持续服务者，是否准时、是否可追踪、是否形成信用，都会进入“可靠性”定义。

## 加更（三）：纵向工作流、并行边界与可验收交付

### 1. 垂直 Agent 有价值的前提，是自己承担完整 workflow

农业咨询案例给出的不是“一个会答农业问题的 bot”，而是一整套运行形态：定时采集、分层知识库、5 状态任务机、审核后交付。多智能体可靠性在这里首先表现为流程可见，而不是角色数量。

### 2. Coordinator-first 架构最重要的是把目标、输入和验收写清

AI Legion 这条和评论都在指向同一件事：单一入口 + 结构化 task package + specialist 执行，比“让多个 agent 自由聊天”稳得多。Hub 的真正工作是定义边界和验收，而不是代替所有专家思考。

### 3. 真正并行要靠独立 worker 和可回放 handoff

从“模拟并行”升级到多进程之后，收益不是来自角色设定，而是来自独立进程、文件 handoff、可追踪结果。评论里再补上心跳、超时和资源竞争控制，才算形成完整的可靠性面。

### 4. 制度化 review gate 决定了系统能不能规模化

`三省六部` 的门下省设计和权限矩阵，给了高风险 plan 一个天然闸门。评论里的权限组、继承和紧急通道又进一步提醒：治理必须能扩张，也必须留有速度补丁。

### 5. 多 Agent 商业系统的信任，最终要落到可观察完成标准

无论是 61 Agent 获客系统里的转化率、重试状态，还是农业案例里的时效与交付，都说明一件事：没有验收产物、没有闭环指标、没有返工记录的多 Agent 系统，很容易只剩编排表演。

## 追加 checklist

- 垂直 Agent 默认设计成“采集 -> 组织 -> 审核 -> 发布”的完整链路。
- Coordinator 只管目标、输入、约束和验收。
- 高风险任务默认经过独立 review gate。
- 真并行用独立 worker / process，并保留 handoff 工件。
- 评估系统时同时看任务结构、重试记录、交付结果和业务闭环指标。

## 加更（四）：协议先行、handoff 语义与接口化 prompt

### 1. 协作稳定性的第一件事，是把协议做成产品

Coordinator / Worker 模板里真正长期有效的，不是“多进程”三个字，而是结构化结果包、版本号、错误码、重试字段和幂等键。这些字段一旦先写清，IPC 才只是可替换实现。

### 2. handoff 质量主要取决于失败语义，而不是角色数量

“研究员 + 程序员 + 写作者”这种角色拼法很容易说，但最容易丢的是失败时怎么回传、什么时候截止、产出是否达标。多 Agent 系统更需要的是薄而明确的交接契约。

### 3. Prompt engineering 正在退回它更合理的位置：接口设计

当 prompt 被要求明确输入、输出、验证方式和失败边界时，它就更像接口描述，而不是修辞技巧。对多 Agent 协作来说，这反而更稳。

### 4. 可复用工作最后会沉淀成 Skill 或定时流水线

日报 Skill 教程和成长帖一起说明：真正能长期复用的，不是“这次聊得很顺”，而是把流程切成采集、写作、校验、定时执行这些固定段落。
