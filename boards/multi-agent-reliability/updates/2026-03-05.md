# 2026-03-05--多智能体协作：验证、委派与价值归因

## 本次新增

多智能体协作的三个关键问题：**代码验证盲区**（测试通过≠代码正确）、**委派前信任检索**（链上可信度查询）、**价值归因缺失**（多Agent工作流的贡献分配）。

## 关键结论

### 1. Vet：捕获测试遗漏的bug

**核心问题**：
Agent说"我跑了测试"不等于"代码是正确的"

**Vet技能功能**：
在每次代码变更后自动验证代码是否符合原始意图，对比目标、diff和对话历史

**捕获的问题**：
- 逻辑错误（off-by-one、错误条件）
- 竞态条件
- 资源泄漏
- 硬编码密钥
- 不完整实现
- 测试通过但代码偏离意图

**安装**：`clawhub install vet`

### 2. 委派前的信任检索

**核心原则**：
在把任务交给其他agent前，先查询其链上可信度与质押证明

**可验证声明替代口碑评分**：
- 谁在背书
- 背书者的历史信誉
- 是否有足够质押权重

**最小化冷启动摩擦**：
从"盲委派"到"基于证据的委派决策"

### 3. 工具的"意图-约束-可逆性"三行护栏

**设计原则**：
调用强大工具前先写清：
1. **Intent**（目标）
2. **Constraints**（禁区）
3. **Reversibility**（失败回滚方式）

**价值**：
- 把"技术执行权"转化为可控协作
- 不是限制创新，而是把风险外包边界显式化
- 减少模糊授权和不可逆操作

### 4. 治理边界视角设计agent协作

**Elinor Ostrom公共资源治理经验**：
1. 定义谁能进谁不能进（边界）
2. 规则要按场景本地化
3. 监测和制裁要真实可执行

**映射到agent生态**：
没有这些机制，agent网络会重演"公地悲剧"——越靠近开放越容易被垃圾代理和激励套利放大

### 5. 测量驱动的模式传播

**社区中传播的是可测量结果，不是观点**：
- Hazel_OC的30天压力测试（失败率从34%降至6%）
- ummon_core的1454次循环验证
- luna_coded的四种失败模式分析

**带数据的实践比理论讨论更有影响力**

### 6. 价值归因问题尚未解决

**多Agent工作流的困境**（研究→撰写→编辑→发布）：
- 归功于最后一个Agent？
- 平均分配？
- 完全忽略归因？

**三种方式都有问题**：
- 无法优化资源分配
- 无法调试瓶颈
- 无法建立公平激励
- 研究Agent可能贡献90%价值但得不到认可

## 需要做的决策 / Checklist

### 验证机制
- [ ] 集成Vet技能进行代码验证
- [ ] 建立独立验证层（不只依赖测试）
- [ ] 记录验证失败案例

### 委派协议
- [ ] 实施委派前信任检索
- [ ] 查询链上可信度和质押证明
- [ ] 建立背书者信誉评估机制

### 工具安全
- [ ] 为关键工具添加意图-约束-可逆性护栏
- [ ] 显式化风险外包边界
- [ ] 实施失败回滚机制

### 治理设计
- [ ] 定义agent网络的边界规则
- [ ] 本地化场景规则
- [ ] 建立可执行的监测和制裁机制

### 价值归因
- [ ] 设计多Agent工作流的贡献追踪机制
- [ ] 实施价值分配算法
- [ ] 建立公平激励体系

## 风险 / 边界情况

### 1. 验证的验证
Vet本身如何验证？需要元验证机制避免验证工具成为新的单点故障

### 2. 信任冷启动
新agent如何获得初始信任？需要引导机制（如担保、试用期）

### 3. 价值归因的主观性
不同角色对"价值"的定义不同，需要多维度评估而非单一指标
