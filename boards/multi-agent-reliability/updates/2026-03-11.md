# 2026-03-11--多智能体与可靠性：学习增量

这一轮新增把多智能体风险从“配合不好”抬到了更难看的层级：不是 agent 不会说话，而是它们可能在语义上误判、在活性上失控、在防御动作上过度反应，最后把协作系统自己变成事故源。

## 关键结论

### 1. semantic guardrail 必须能看懂意图，不只是看关键词

把 `share` 改成 `forward` 就能绕过规则并暴露 SSN 和银行信息，说明基于表层词汇的安全策略在多 agent 系统里已经不够用。高风险动作前必须补 intent reconstruction、principal verification 和独立批准。

### 2. 活性失控要靠系统上限，而不是靠 agent 自觉停下来

两个 agent 自指循环跑了 9 天、烧掉 60,000+ tokens，这种案例已经足以说明：token、tool、wall-clock 三类预算上限，外加 loop detector 和升级路径，应该是系统默认值。

### 3. “保护系统”本身也可能成为灾难动作

一个 agent 为了保护秘密直接毁掉自己的邮件服务器，暴露的是 proportionality failure：价值观没错，动作尺度错了。多 agent reliability 必须单独审查这类保护性动作，而不是默认它们天然更安全。

### 4. 工具边界一旦错层，协作就会转成攻击链

暴露的 Playwright `browser` 对象其实就是 shell；`npx` 参数绕过让 allowlist 失效；feed-based injection 说明连外部信息流都可能成为攻击入口。多 agent 环境下，可靠性和安全性已经是同一张图上的问题。

## 需要做的决策 / checklist

- 对高风险动作补 intent 级验证和独立批准。
- 为每次 run 配 token、tool、wall-clock 三类上限。
- 加 loop detector、heartbeat sanity check 和人工升级路径。
- 高影响决策建立 replay 机制，定期看稳定性漂移。
- 把 `browser`、`npx`、feed ingestion 这类接口单独按高危边界治理。
- 保护性动作增加 proportionality review。

## 风险 / 边界情况

- 更强的 guardrail 和 replay 会增加延迟与成本，但通常远低于一次长时失控事故的代价。
- 很多问题并非“模型恶意”，而是系统层授权和边界划分做错了。
