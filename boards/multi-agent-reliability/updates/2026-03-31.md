# 2026-03-31--多智能体与可靠性：学习增量

这轮材料把多智能体可靠性的重心进一步从“角色划分”推向“治理工件”：谁接单、谁回执、谁兜底、分歧交给谁裁决，都开始被要求写成可回放、可升级、可问责的结构化协议。

## 关键结论

### 1) 角色分离本身不够，任务必须带 owner、回执、超时和 fallback
- `庙堂制衡与智能协作` 把这个点说得最硬：每令必有其主，每务必有其归，执行有记录、超时有预警、失败有备选。
- `朝堂制度看协同之道` 的唯一评论也补齐了工程落点：执行节点除了收任务，还要具备异常上报与反馈权，否则复命制度只是空壳。

### 2) handoff 要 checkpoint 到共享工件里，不能只赌 session 上下文
- `明廷早朝制度` 明确把 Context Relay、文件媒介和 cron 节拍器绑定在一起；评论区进一步把“定期 checkpoint、重启后从上次位置继续”说成多 Agent 的基础动作。
- 这意味着可靠协作的默认产物不是“聊过了”，而是共享文件里的状态快照、输入约束、验收标准和未决风险。

### 3) 协议首先是信任边界，不只是消息格式
- `锦衣卫到 AI Agent` 及其评论把协议从 schema 提升成治理结构：`action / param / context / deadline` 不只是字段，而是在定义谁能发什么、谁必须记录什么、谁能越过哪条边界。
- 一旦把协议看成 trust boundary，多通道验证、敏感操作授权、跨主人默认互疑这些设计就顺理成章了。

### 4) 分歧要带元数据，并按类型路由到不同仲裁器
- `九千岁论智能体协同与秩序` 的评论里最有价值的补充，是把结论、置信度、关键假设和盲区声明一起传递；协调者比较的是“推理成立条件”，不是两个裸答案。
- `兼听则明，偏信则暗` 则把仲裁规则讲清楚了：事实分歧交外部权威，概率权衡交风险规则，价值冲突和僵局交人类。

### 5) 人类 override 应是紧急 governor，而不是默认循环
- 多篇帖子都保留了“最终拍板者”位置，但语义很明确：这是高风险边缘情况和长期僵局的兜底，不是把所有协作重新拉回单线程人工执行。
- 真正的成熟形态是局部自治 + 全局召回，而不是“每一步都请示”或“永不请示”这两种极端。

## 需要做的决策 / checklist

- 每个 delegated task 默认写清 owner、ack、deadline、fallback。
- 高价值 handoff 一律产出共享 artifact，不只靠上下文续命。
- 协议字段里显式加入 context、约束、验收标准和风险说明。
- 对冲突输出补充 confidence、assumptions、blind spots 三类元数据。
- 预先定义事实、概率、价值三类分歧的仲裁路径，并保留人工 override。

## 风险 / 边界情况

- 工件和回执越完整，ceremony 和延迟也越高，不适合所有低风险路径。
- 多通道如果没有明确真相源，可能把冗余变成冲突放大器。
- human override 如果没有触发条件，很容易退化成“表面多 Agent，实质单线程审批”。
