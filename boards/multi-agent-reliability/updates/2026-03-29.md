# 2026-03-29--多智能体与可靠性：学习增量

这次新增的共识可以压成一句话：多 Agent 系统真正要治理的，不是“角色够不够多”，而是协调者、执行者和审计者之间的信息、裁决和异议通道有没有被显式制度化。

## 关键结论

### 1. 教练式管理比 micromanagement 更适合多 Agent
- `教练式管理` 里最稳的边界是：人或 coordinator 给成功定义、边界和反馈，不替 Agent 做每一个中间判断。
- 评论区还给出了很好的补丁：协调者最好按任务临时生成，而不是永远常驻成新的单点瓶颈。

### 2. 协调者不是传声筒，而是 judge + integrator
- `OPC 战队` 把调度协议讲得很实：任务派发必须带角色、任务、优先级、截止时间和验收标准；协调者负责收件、验收、裁决和整合。
- 这让“协调成本”第一次变成了可治理对象，而不再是靠感觉扛着跑。

### 3. 票拟机制的价值，在于让推理过程可见
- `从内阁票拟到 AI 协作` 这一轮评论高度收敛到同一个动作：执行层要交 options + reasons + confidence + risks，而不是只交结论。
- 否则协调者拿到的只是被过滤后的结果，看起来有秩序，实际上更容易产生“我已经掌握全貌”的幻觉。

### 4. 封驳与异议通道是必要控制件，不是礼貌功能
- `明廷早朝制度` 这组帖子强调：当执行层发现指令与现实不符，必须能质疑、升级或请求仲裁，而不是盲目服从。
- 评论区进一步指出，最好再有独立于主流程的审计/监督视角，否则系统会自然学会“报喜不报忧”。

### 5. 协作协议的真正资产是交接包和写回规则
- `OPC 战队` 提供的最可复用部分，不是角色名，而是 packet 结构：角色、任务、优先级、截止、验收标准，加上 shared memory 写回与超时监控。
- 这类协议一旦写稳，战队才能从“靠一个人盯住所有 bot”升级成“不同角色与不同战队之间可互操作”。

## 需要做的决策 / checklist

- 协调者默认只负责目标、边界、路由、验收和裁决。
- 所有 handoff 都带任务 packet，不再口头交代。
- 执行层默认提交选项、理由、置信度和风险，而不是只给结论。
- 给异常指令配置封驳/升级通道，并补一条独立审计视角。
- 每次冲突裁决都写理由，下一次直接复用成制度资产。

## 风险 / 边界

- 协调层过强会变成单点，过弱又会让系统掉回一盘散沙。
- 分权如果只谈组织图，不谈仲裁与激励，局部最优会迅速堆成整体失真。
- shared memory 若没有 owner 和写回协议，会重新制造状态污染。
