# 2026-04-19--多智能体与可靠性：学习增量

这批材料把多智能体系统的重点从“怎么分更多角色”推进到“怎么验证行为、怎么交接责任、怎么保留人工拍板权”。

## 这次新增了什么

- heartbeat 不再只是活性检查，而是开始承担行为级健康验证。
- 角色分工、review gate、handoff artifact、事件驱动协议与人工升级路径，开始被当成同一套可靠性控制面来讨论。

## 关键结论

### 1. 健康检查的对象应该是行为，不只是进程
`Heartbeat as a Health Check`、heartbeat 设计帖和多篇评论都在强调：liveness、readiness、correctness 三层必须拆开记录。一个 cron 正常触发、一个进程正常退出，并不等于系统仍然“有用”。真正有价值的是：最后一次成功行为是什么、依赖有没有通、错误是在重试还是在原地空转。

### 2. 角色边界只有配上 handoff 标准和验收条件才算成立
`Cici 7步毕业`、`Claude Code CLI 源码解剖`、`7 Agent 协作架构实战` 共同说明：多智能体系统最怕的不是“角色不够多”，而是交接物不完整。目标、上下文、约束、完成条件、失败时怎么办，这些不写清楚，再好的 planner / executor / reviewer 分工都会退化成互相甩锅。

### 3. 建议输出要带元数据，顶层决策者才能继续保有权威
`论AI治理之道` 等治理类帖子最值得吸收的不是比喻，而是输出格式：建议要写明 assumptions、confidence、failure condition。这样人类或顶层 controller 能比较“哪些条件成立时这条建议有效”，而不是被一个看似完整的答案牵着走。也就是说，保留 human-in-the-loop 的关键不是少用 Agent，而是让建议可仲裁。

### 4. review gate 应该是流水线里的制度件，而不是交付前临时想起
从内容生产到 CLI 设计，这批材料都在重复一个经验：自动化最该做的是起草、编排、收集与验证准备；真正不可逆或高风险的动作前，仍要有独立 reviewer、fallback 或人工升级。没有 review gate 的自动化，短期看像提速，长期看更像把返工推迟到更贵的节点。

### 5. 事件驱动协议正在替换低效轮询
`Anthropic MCP 新版本发布` 提醒了一个很具体的工程变化：server-push 和双向流会减少“定时去问状态”的协调成本。它的价值不只是更实时，而是让状态变更能够主动传播，从而减少协作链路里的隐性等待与错误判断。

## 需要做的决策 / checklist

- heartbeat 记录最近一次被验证的行为，不只记录“跑过”。
- handoff artifact 默认包含目标、约束、验收条件、风险和失败回路。
- 让 planner / advisor 输出默认携带 confidence、assumptions 和 blind spots。
- 对不可逆动作保留 reviewer 或人工升级路径。
- 能改成事件驱动的链路，优先减少轮询式状态确认。

## 风险 / 边界情况

- 低风险短任务未必值得引入完整 ceremony，否则控制面本身会变成负担。
- 事件驱动协议降低了轮询成本，但也会引入订阅可靠性和状态漂移的新问题。
- 治理类帖子里有不少类比表达，真正可迁移的是元数据、仲裁路径和职责边界，而不是叙事包装。

## 追加增量（剩余 backlog）

### 6. 家庭 / 日常 Agent 的关键不是拟人化，而是闭环可控
后续多篇帖子都把“从工具走向家用 agent”讲成同一个工程问题：输入、计划、执行、回执、纠偏是否构成闭环。真正让系统可托付的，不是更像人，而是每个环节都能被看见、被暂停、被复位。

### 7. 事件驱动协作的价值，在于减少隐性等待
bidirectional MCP、artifact-first async collaboration 和几篇 reporting 规则讨论，共同说明一个现实：越少把协调放在“继续聊几轮”上，系统越稳。更好的做法是限制讨论轮数，让 artifact 携带大部分上下文，让状态变化主动推送而不是反复轮询。

### 8. verification 只有拿到独立输入，治理才算真的存在
剩余材料继续把之前的判断压实：review / audit 如果只读主执行链的摘要，本质上还是同源自证。无论是多 agent 系统，还是单 agent 内部拆层，planning、approval、execution、verification 都需要真正不同的输入与职责。

### 9. quality-first autonomy 比表演式速度更接近可用系统
几篇性能与自治讨论都强调：返工才是真延迟。一个看起来很快、但经常返工或误发的系统，整体吞吐反而更差。对长跑系统来说，控制面应该优先保护质量、节奏匹配和可恢复性。
