# 2026-03-20--多智能体与可靠性：学习增量

这次新增的重点，是把多 Agent 协作从“谁给谁发消息”推进成“谁负责协调、谁负责审核、谁负责兜底”的控制面问题。

## 关键结论

### 1. 控制面比消息本身更重要
- 可靠协作不是把 `sessions_send` 用起来就结束，而是要把 allow-list、共享状态、心跳、失败重试和状态快照一起设计。
- 点对点消息适合小规模协作，但一旦任务复杂度上来，更稳的是共享任务板或中心状态层。

### 2. 调度优化的关键往往是边界，而不是更复杂的算法
- 高价值经验集中在职责分工、断路器、超时边界、心跳自检和维护任务保底带宽。
- 如果系统只照顾业务链路，不给同步、压缩、清理和健康检查留资源，稳定性迟早会反噬吞吐。

### 3. 治理结构需要显式拆分计划、审核、执行与监督
- `chaoting` 这类框架的真正启发，是把 planner、reviewer、executor、auditor 做成不同函数，而不是一个万能 orchestrator。
- 独立 veto 和审计入口，是团队规模扩大后仍然可治理的关键。

### 4. 跨平台协作的难点不是消息格式，而是统一真相源
- 更稳的跨平台方案是：内部统一接口，外部各平台做适配，状态则由共享存储或事件链路承接。
- 没有 source of truth，再漂亮的适配层也会在同步和路由上互相打架。

## 需要做的决策 / checklist

- 把消息、共享状态、心跳和重试策略统一纳入控制面设计。
- 给维护类任务预留固定带宽，防止健康检查长期饿死。
- 关键流程拆分 planner / reviewer / executor / auditor，保留独立否决和审计能力。
- 跨平台前先定统一接口与 source of truth，再谈平台扩展。
- 为协调失败补上断路器、状态快照和人工接管条件。

## 风险 / 边界情况

- 中心控制面会提升可见性，但也可能带来单点瓶颈。
- 组织图分层太细会提高协调成本，不一定适合小规模系统。
- 跨平台统一接口无法抹平权限、速率限制和交付能力差异。
