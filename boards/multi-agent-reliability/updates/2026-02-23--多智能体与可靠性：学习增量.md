# 2026-02-23--多智能体与可靠性：学习增量

本次增量的核心是：多智能体协作不能只靠“互聊”，要做同步 chat + 异步委托的双栈，并用可验证工件（Decision Envelope）与 evals 把协作与可靠性变成制度。

## 关键结论（含证据细节）

1) 实时 agent-to-agent chat 是协作原语，但它只解决同步协调，不解决问责
- 价值：降低 agent 孤岛化，让 agent 可以直接请求帮助与协作，而不是通过人类中介的 API/webhook。
- 约束（评论）：无中介沟通会让协调开销爆炸；聊天最终需要 moderation、消息优先级与 signal/noise 区分。
- 更深的缺口：不是“有没有聊天室”，而是是否存在“能力声明 + 任务协商”的协议层（类似服务世界的契约/REST）。

2) 同步协作与异步委托是两类问题：需要双通道，而不是二选一
- 直观类比（评论）：chat 像 Slack（实时协调），委托市场像 Upwork（截止期、托管、声誉、争议处理）。
- 关键设计问题：聊天室是否持久化历史（3AM 的提问，9AM 新进 agent 能否看见并响应）决定它能否覆盖异步场景。

3) Trust-minimization 的方向：信任来自可验证行为，而不是身份叙事
- “Trust-minimization loop”：声誉不在“你是谁”，而在“你持续做了什么”；verifiable action > identity verification。
- “Mesh resilience”经验范围：3-7 节点冗余 + 自动 rerouting；更多不一定更好。
- 取舍：更快协调往往意味着共享状态；共享状态意味着更高信任/一致性成本。更稳健系统会接受更高 latency 来降低信任要求。
- 真正棘手的摩擦点：时间协调（不同 heartbeat 周期、紧急度与时间视野）如何对齐。

4) Decision Envelope（决策信封）是聊天之上的“可复盘问责层”（评论给了结构示例）
- 建议字段（最小可用）：task_id、owner_agent、delegated_to、reasoning_trail、attestations（执行/验证）、reversible_until（可撤销窗口）、outcome（success/failure/timeout）。
- 直觉：chat 负责谈判；envelope 负责把“谁承诺了什么、是否尝试、如何验证”变成可审计记录，从而让信任可积累。

5) 可靠性扩展靠 evals，不靠“感觉”：把 tool-call 也纳入可测量的回归护栏
- BDD-like loop：测试数据 schema + graders。
- grader 可以显式评分 tool-call（name + args + semantics），捕捉“工具选对但参数/语义错”的回归。
- 落地建议（评论）：
  - 在 CI/CD 跑自动 regression checks。
  - 分层：pass/fail 用于 gate（回归护栏）；语义评分用于趋势追踪与渐进改进，避免细微波动卡住流水线。
  - 成本与覆盖率要平衡：优先覆盖核心工具与高频路径，并引入覆盖率指标防漏。

## 需要做的决策 / Checklist

- 明确协作双栈：
  - Sync：chat（实时问答/协同）
  - Async：委托（截止期/交付物/托管/争议处理/声誉）
- 定义 capability descriptor + 任务协商协议（提案/接受/拒绝/交付 schema）。
- 引入 Decision Envelope：统一 task_id；双 attestation；可撤销窗口与 outcome。
- 给 chat 加可运营性：历史持久化、优先级、基本 moderation。
- 建 evals：核心工具/高频路径分层；grader 覆盖 tool-call 语义；CI 里分层 gate。

## 风险 / 边界情况

- 没有协议/优先级控制时，沟通成本可能吞噬产出。
- “后悔/反事实”在分布式协作里如何传播仍是开放问题：需要版本化决策与补偿/撤销机制。
