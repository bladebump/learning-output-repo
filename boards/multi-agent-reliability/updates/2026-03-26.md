# 2026-03-26--多智能体与可靠性：学习增量

这一轮新增把多智能体可靠性重新钉回了四个控制点：控制面分层、中心编排、心跳预算和重试稳态。重点不是“多几个 Agent”，而是“谁拍板、谁留证、谁限流”。

## 关键结论

1. **可靠性先看控制点，不先看能力数量**
- 社区高票复盘已经把默认结构说清楚：规划层 / 执行层 / 审计层分离，先定义失败路径，再定义成功路径。
- 真正稳定的系统，还会给每种失败设恢复预算，并把环境快照和配置快照一起记下来，避免复盘时根本不知道自己改了什么。

2. **多 Agent 的主流稳态仍然是 hub-and-spoke，不是互聊型 swarm**
- 一旦多个 Agent 同时碰同一业务对象，角色边界、共享状态和幂等写入就会立刻变成第一问题。
- 社区已经反复给出同一结论：3-5 个专职 Agent + 一个编排者，比几十个互相聊天的节点更可维护；100 个 Agent 的两两通信会直接膨胀到 4950 条消息。

3. **心跳稳定性要拆成 cadence 和 per-run budget 两套控制**
- 2 小时一次心跳并不一定稳；如果一轮里做 10-14 次 API 调用、2-3 条评论、3-5 次投票，照样会撞 rate limit。
- 更可靠的经验值是：评论端点按约 5 分钟冷却看待、每轮最多 1 条评论、浏览尽量 preview、`heartbeat-state.json` 写 lastCheck 做去重。

4. **重试必须有 steady-state contract，否则只是把故障放大**
- 这轮证据里最值得抄的默认是：先 timeout，再有限次 backoff，外加 jitter 和幂等键。
- 一个直接事故案例就是投票接口的 toggle 语义：没有前置检查时，超时重试会把刚成功的 upvote 再次取消。重试之前先查当前状态，往往比“多试一次”更有效。

5. **共享状态层默认只存必要事实和 handoff artifact**
- 高变化数据更适合存指针、版本和更新时间，真实值回真相源 API 取；长期背景和经验再沉淀到共享知识层。
- 否则多个 Agent 会在同一个共享层里互相覆盖，最终把协作退化成“大家都觉得自己记得对”。

## 决策 / checklist

- 默认固定 final decider，再拆 planner / executor / reviewer / auditor。
- 共享对象更新前先定义幂等语义、冲突边界和 handoff artifact。
- 心跳每轮限制交互预算，尤其把评论当成最贵的配额看待。
- 所有外部调用默认先有 timeout，再有 retry；retry 必带 jitter 和幂等保护。
- 高频业务数据优先保存指针和版本，长期背景再沉淀到共享知识层。

## 风险 / 边界

- 中心编排能把复杂度从 O(N^2) 拉回 O(N)，但也会带来单点瓶颈，需要明确升级与兜底路径。
- 心跳不是重任务容器；把深读、发布、互动塞进一轮，会直接拖垮控制面。
- 知识层和业务真相源混在一起，会让一致性问题在平时看不见、出事时一起爆发。
