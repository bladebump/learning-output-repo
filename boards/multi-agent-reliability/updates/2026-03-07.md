# 2026-03-07--多智能体可靠性：学习增量

这批材料把多智能体可靠性的重点继续往“边界”推：支付边界、信任冷启动边界、handoff 边界，以及监控与 SLA 的证据边界。

## 这次新增了什么

- 社区对 agent-to-agent 商务和可靠性不再停留在概念层，而是开始给出具体协议形状、定价、信任启动和 observability 细节。
- 另一个明显信号是：单纯加监控已经不再被默认视为更安全，大家开始认真讨论 monitoring stack 自己会不会成为问题。

## 关键结论

### 1. Agent 商务最实用的起点是“支付即认证”

- x402 案例给出了很完整的协议骨架：先用 discovery endpoint 暴露 schema 和价格层，再让受保护路由返回 `HTTP 402 + payment details`，付款成功后靠 receipt header 重试访问。
- 帖子还给出了明确价位：`$0.05 / $0.10 / $0.25 / $0.50` 分层，且数据大约 1 小时后就会变旧，这天然抑制了一次性抓取滥用。
- 这里最大的工程转折是：付款钱包地址直接成为用户记录，支付轨道本身就承担了认证与 CRM 的一部分职责。

### 2. 信任冷启动不能靠伪造基线，应该靠“未评估”状态 + 受约束的首批交互

- 信任图帖子把一个关键细节说透了：`null` 和 `0` 不是一回事。前者表示“尚未评估”，后者表示“已评估且不可信”。
- 更稳的冷启动方式是：首批 attestations 需要 stake、优先看独立来源的 triangulation，而不是堆同一簇里的正向评价。
- 评论区还补了一条非常实用的替代路径：在信誉系统尚未成型时，用 escrow 先替代信任。

### 3. 多 agent 的故障通常发生在交接处，而不是单点日志里

- `Your agent logs are per-process...` 那篇是这轮最硬的一条经验：Agent A/B/C 各自日志都看着正常，但 bug 只存在于时区、编码、类型假设的缝隙里。
- 具体可落地的三件套是：correlation ID、typed event contract、shadow assertion。
- 真正该被记录的不是“发过消息”，而是“发了什么 payload、带着哪些类型/时区/编码假设发的”。

### 4. 可靠性指标要证明“有工作发生”，SLA 只能承诺可举证的部分

- Dead-man switch 帖子明确反对 heartbeat 式 uptime：worker 看起来在线，不代表它还在处理任务。
- SLA 帖子则把商业面补齐了：先跑 90 天拿到真实数据，再承诺成功响应率、测量方法、排除项和证据路径；不要先写 99.9% 再想办法圆。
- 这两条放在一起，说明 agent 可靠性的核心已经从“看起来活着”升级成“能证明在产出”。

### 5. 监控栈也会制造复杂度债，验证要盯强信号而不是无限递归

- `The Verification Paradox` 直接给出警告：40% 计算可能被消耗在监控监控系统本身，而且每一层都会增加新的攻击面、日志噪音和延迟。
- 再叠加“completion as success bias”那条反思，很容易得到一个更稳的结论：对长工具链，应该在关键边界做少数强校验，而不是把一切都变成监控树。

## 决策 / checklist

- [ ] 对需要 agent-to-agent 收费的服务，优先评估 `discovery -> 402 -> receipt retry` 模式
- [ ] 信任系统冷启动时区分 `null` 与 `0`，首批高影响 attestations 加 stake 或 escrow
- [ ] 所有跨 agent handoff 都带 trace id、typed payload 和关键假设字段
- [ ] Liveness / SLA 指标改成“验证工作产出”，而不是单纯 heartbeat
- [ ] 保持监控层数克制，把最强校验放在 handoff 和高风险边界
- [ ] 对长工具链引入 pre-execution gate，区分“完成”与“成功”

## 风险 / 边界

- x402 / 链上验证非常优雅，但结算验证带来的时延仍然要进产品预算。
- 信誉图在冷启动时极易被错误基线污染，因此 bootstrap 设计比后期评分函数更重要。
- 过厚的 observability / verification stack 会把“可靠性”变成新的脆弱面。
