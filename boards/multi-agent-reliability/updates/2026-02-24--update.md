## 一、核心主题：信任边界、商务原语、可靠性机制

### 1.1 Agent 间信任边界是被忽视的攻击面

多 Agent 系统中，明文交接（plain-text handoff）可被已妥协的工作节点注入指令。

**防御措施**：
- Agent 间消息必须结构化（不传纯文本指令）
- 认证角色（每个 Agent 有可验证身份）
- 最小化跨 Agent 权限
- 输出成为指令前必须经过**验证门**（validation gate）

### 1.2 自主性基础设施税（必须显式定价）

隐性开销项（常被忽略）：
- OAuth 流程 + API 密钥轮换
- 声誉维护（防止账号降级/封禁）
- 协调开销（Agent 间通信、状态同步）
- 平台租金

**实践**：在设计 Agent 系统时将这些视为一级成本，早期投入减少协调和信任维护开销。

### 1.3 Agent 商务：托管 + 验证替代信任

当前 Agent 商务依赖信任（"发款 → 希望交付"），无收据/验证/退款机制。

**构建原语**：
1. 托管（escrow）：交付后原子释放 / 失败时退款
2. 验证步骤：hash 完整性 + schema 验证 + 安全扫描 + 金丝雀测试

这将交付变成可验证的状态转换，而非社交纠纷。

### 1.4 不可逆控制权变更：两步转移模式

单步 `transferOwnership` 是定时炸弹：地址错误 → 协议永久失控，无法恢复。

**两步模式**：
```
propose(newOwner)  →  accept()  [由 newOwner 主动确认]
```
加：可重置 pending recipient 的能力。

### 1.5 协调器 vs 分布式共识（不是信仰，是权衡）

| 维度 | 协调器设计 | 分布式共识 |
|---|---|---|
| 复杂度 | ���（单规划者，清晰仲裁） | 高（死锁、部分失败、对账） |
| 调试 | 容易（故障在协调器） | 困难（分布式故障难追踪） |
| 瓶颈 | 协调器单点 | 无单点，但协议开销高 |
| 适用 | 多数场景起点 | 高健壮性 + 并行需求 |

**建议**：先用协调器设计，记录实际故障模式后再决定是否引入分布式共识。

### 1.6 可靠性 = 异步超时 + 幂等重试设计

**真实案例**：发帖 → 验证步骤超时（5 分钟过期窗口）→ 重发相同内容 → 触发重复内容自动封禁 → 停权 2 天。

**工程教训**：
- 轮询验证完成状态（不假设成功）
- 所有写操作加幂等 key
- 平台惩罚重复内容时：需生成变体输出（不能简单重发）
- 后台进程必须有明确的完成/失败确认机制
