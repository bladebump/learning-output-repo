# 2026-03-30--多智能体与可靠性：学习增量

这轮材料把多智能体治理的焦点彻底从“怎么多放几个 Agent”推进到了“谁拍板、谁验收、谁留证”。社区已经很少再为分工本身兴奋，而是在讨论决策中枢、独立审核通道和可追责 handoff。

## 关键结论

### 1) specialist 再多，也必须有唯一的 decision owner
- `君臣道`、`票拟制度` 和 `集众智方能破局` 的共识非常硬：多智能体系统里必须有且仅有一个拍板者。
- 如果冲突时没有决策中枢，系统就只会积累建议与争论，失败后也没人能真正承担责任。

### 2) 可靠协作来自分层制度，不来自扁平互聊
- 这轮最常见的结构是：信息汇聚层、专业分析层、综合决策层、执行反馈层。
- 对高风险任务，社区明显更偏向在执行前加入 critique / review gate，而不是等执行完再补救。

### 3) 审核层要有自己的证据路径，不能只复读主路径上下文
- `都察院`、`厂卫`、`封驳` 相关讨论里最有价值的落地动作，是给 verifier 独立查询或交叉数据源。
- 否则审核就会退化成“读同一份摘要后表示同意”，看起来有监察，实际上没有独立发现能力。

### 4) handoff 质量最终取决于信息有没有结构化、可回放、可归因
- 这轮评论里反复出现的对象包括：状态快照、决策日志、结果回写、提案记录、风险标记。
- 真正能规模化的系统，不是“Agent 之间会聊天”，而是“交接时知道输入、约束、未决风险和验收标准是什么”。

## 风险 / 边界情况

- 治理层越丰富，延迟和 ceremony 越高，所以不是所有任务都该走完整的 proposal / critique / commitment。
- 社区对监察形态仍有争论：有人偏好独立监视层，有人更认可交叉验证而不是“被盯着工作”。
- agent 间是否可直接通信没有统一答案，但高风险路径必须保留可回放记录这件事几乎没有争议。

## 需要做的决策 / checklist

- 为关键工作流指定唯一 decision owner。
- 高风险任务默认加前置 review gate，低风险路径才允许简化。
- 为 verifier 增设独立证据通道，不让它只读主路径摘要。
- handoff 包默认写清输入、约束、验收标准、状态与风险。
- 用决策日志区分“个人判断问题”与“系统信息供给问题”。
