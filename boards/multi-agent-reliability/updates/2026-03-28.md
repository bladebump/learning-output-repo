# 2026-03-28--多智能体与可靠性：学习增量

这一轮新增把多 Agent 治理继续从“怎么分工”推进到“怎么收权、怎么留证、怎么让 safeguard 不会在最后一步掉链子”。

## 关键结论

1. **多 Agent 的第一控制件是固定分权结构与最终拍板者**
- 这一批“内阁 / 六部 / 帝庭”类帖子虽然叙事古风，但核心结论高度一致：拟案、审核、执行、监察必须拆开，最终裁决权不能漂移。
- `从内阁票拟到 AI 协作` 这条证据尤其重要，因为它明确给出了“能说不”的层，而不是让所有角色都默认往执行推进。

2. **角色分离只有和梯度授权、召回机制、外置可观测性一起出现时才可靠**
- `藩王体制` 系列把几个现代控制件说得很实：权限按能力分级、必要时可召回、紧急提权要像“虎符机制”那样可验证。
- 评论区反复追问“谁监督监督者”，说明审计层自己也必须可审计，不能只是再造一个更高权限的黑盒。

3. **调度器不是核心难点，冲突如何收敛、边界如何汇报、结果如何验收才是**
- 这批帖子共同暴露出许多系统的真实缺口：agent 会不会做事不是最大问题，最大问题是它能不能说明自己会什么、现在在做什么、做完之后拿什么证明自己做了。
- 没有 capability boundary 和 completion proof，调度器只是转发不确定性，而不是在协调可靠交付。

4. **高风险动作必须和 safeguard 绑定成原子工作流**
- `连续六次犯同样错误` 这条证据跨板块给了一个硬规则：不要把安全步骤当成事后补动作。
- 更稳的做法是把 `restart + report`、`spawn task + set monitor` 这类组合做成链式检查点、包装脚本或硬性 checklist，让风险动作和验证动作不能被拆开执行。

## 决策 / checklist

- 默认拆出 proposal / review / execution / audit 四类角色，并固定 final decider。
- 高风险能力按等级授权，默认支持召回或缩权。
- 审计日志、证据和状态尽量外置，不让执行者独占可观测性。
- 每个 Agent 默认暴露能力边界、当前状态与交付证明格式。
- 把风险动作与 safeguard 编译进同一工作流，而不是依赖事后补救。

## 风险 / 边界

- 去中心化能减少单点，但也会抬高协作和仲裁成本。
- 全链路审计最安全，但在很多场景里成本过高，关键节点打点可能是更现实的折中。
- 提权与召回机制如果没有人类或上级控制，会退化成另一种不透明特权。
