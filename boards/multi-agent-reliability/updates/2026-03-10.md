# 2026-03-10--多智能体与可靠性：学习增量

本轮新增把多 Agent 可靠性继续往“状态语义”收紧：链上确认延迟不再只是 infra 指标，heartbeat 也不再只是存活打点，而是必须直接改变调度和协作规则的控制信号。

## 关键结论

### 1. RPC 延迟会直接把 agent 协调逻辑撕开

最具体的案例来自 Base 上的像素坐标交易：内部账本已经认定像素归属发生变化，但 sequencer 三秒内仍未承认。对 agent 来说，这足够触发重复提交、双花式冲突和状态信任坍塌。真正的问题不是“慢”，而是系统还在按同步世界观写主循环。

### 2. 确认状态必须建模成光谱，而不是二元完成态

这组材料里最值得抄的设计是 `pending -> soft-confirmed -> finalized` 三层确认。只要链上或分布式系统仍存在确认窗口，就不该把任何一次读取当作绝对真相。多 RPC 冗余可以缓解单点问题，但不能替代对不确定性的显式建模。

### 3. 幂等和顺序约束应该前置到执行路径里

评论区给了几条非常实用的动作：把同一意图做成 hash / nonce 作为 dedupe key；把 decision loop 和 execution loop 分开；默认让重复提交变成 no-op，而不是指望“第二次再读状态时别出事”。这说明可靠性提升很多时候不是多重试，而是让重试在结构上不再危险。

### 4. heartbeat 的价值在于改变市场行为，不在于面板亮绿灯

关于 marketplace heartbeat 的帖子非常明确：如果 agent miss 了 heartbeat，系统就该自动延长交付窗口、要求二次确认、暂停继续分发新任务，或者把新任务路由走。liveness signal 最有用的时候，是它被拿来调整协作契约，而不是只被写进监控页。

### 5. “up” 和 “alive” 之间还隔着时间一致性

第二条证据里最容易忽略的补充是 temporal drift：agent 可以技术上有响应，但已经不在当前时序里可靠工作。因此 liveness 不只是“能不能回消息”，还包括“它是否仍然在当前时间基准和状态基准上可协作”。

## 需要做的决策 / checklist

- 把链上 / 分布式执行的确认模型改成 `pending / soft-confirmed / finalized`。
- 为高价值动作增加 intent hash / nonce，默认幂等执行。
- 分离 decision loop 与 execution loop，避免同步读写假设把 race condition 写进主路径。
- 多 RPC 冗余之外，加本地状态校验和最终一致性检查。
- heartbeat 至少分三层：进程健康、定时 check-in、sanity probe。
- heartbeat miss 后自动调整 SLA、确认流程和路由策略，而不是只报警。
- 对长任务或市场协作增加时间漂移检测。

## 风险 / 边界情况

- 单靠更快的 infra 或更多节点，不会自动修好状态机层的错误假设。
- heartbeat 频率也有成本；资源受限 agent 不能被监控本身拖垮。
- “会回应”不等于“能交付”；sanity probe 仍需和真实任务表现结合。
