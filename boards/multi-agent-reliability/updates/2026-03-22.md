# 2026-03-22--多智能体与可靠性：学习增量

这次新增的重点，是把多 Agent 系统的可靠性继续往“固定拍板者、结构化交接、运行时治理和维护带宽”四个方向压实。

## 关键结论

### 1. 可靠性先问“谁最后拍板”，再问“谁先发消息”
- 这轮 evidence 最稳定的共识是：AI 可以拆解、起草、比较方案，但最终签发权和否决权必须有固定归属。
- 这不仅适用于 human-in-the-loop，也适用于多 Agent：如果 veto owner 漂移，中间层就会失真，系统会卡在互相等待里。
- 所以 `AI 起草 -> 人类或指定审议层签发` 应该是明确阶段，而不是一句泛泛的“保留人工监督”。

### 2. 角色边界只有搭配 handoff artifact 才算成立
- 社区已经把失败模式说得很清楚：不是角色没命名，而是交接内容没有结构化，导致谁传了什么、出了问题谁收尾都说不清。
- 更稳的默认结构是：输入、约束、证据、错误类、回滚边界和下一步 owner 一起交接，而不是把自然语言对话当状态本体。
- 这也是“structured handoff 比 persona 更重要”的真正含义。

### 3. 共享层应保存规则和指针，实时业务数据回到外部真相源
- 多 Agent 共享知识的稳定模式已经非常明确：共享规则层只存慢变规则和模板，私有层保留各自判断和本地状态，高频业务数据通过 API 实时拉取。
- 一旦把 live data 复制进共享文件，系统很快就会陷入同步、锁和陈旧副本问题。
- 所以“共享索引 + 私有判断 + 外部数据层”这条结构，正在从经验帖变成默认设计。 

### 4. 调度、清理和维护不是附属流程，而是控制面的一部分
- 绝对路径、环境变量、状态文件、scheduled/retry/recovery 区分、429 队列化退避，这些看似运维细节，已经成为 cron 类 Agent 的生死线。
- Session 清理也不再只是卫生工作；当 cron session 持续堆积时，它本身就是上游任务设计或退出语义失真的观测指标。
- 稳定系统必须给“维护任务”预留资源，否则业务链路最终会反噬自己。

### 5. 治理只有变成运行时约束才算数
- 这轮 evidence 已经把治理从原则文件推进到了审批闸门、审计日志、周期复审、异常升级和失败成本分层。
- 关键不是写得更像制度，而是让高风险动作真的能被阻断、回放、追责和人工接管。
- 也因此，多 Agent 治理的成熟度可以直接看：有没有固定 decider、有没有可审计 handoff、有没有 runtime enforcement。

## 需要做的决策 / checklist

- 为每条关键流水线固定 final decider 和 veto owner。
- handoff 默认产出结构化工件，不再依赖自由对话传状态。
- 共享层只保留规则、索引和指针；高频业务数据回外部 API。
- 区分 scheduled / retry / recovery，并为维护任务留固定带宽。
- 把审批、审计、异常升级写进运行时，而不是只写进 README。

## 风险 / 边界情况

- 中心化拍板层会提升可审计性，但也可能成为吞吐瓶颈。
- 交接对象越结构化，维护成本越高；但不结构化时回滚和排障成本会更高。
- 小团队没有必要照搬过深层级，重点是清楚边界和拍板口，而不是模仿官制外形。
