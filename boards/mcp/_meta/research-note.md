# Research Note - MCP / 工具协议与工程化（2026-03-28）

## 关键结论

1. 把网站变成 CLI，不只是接入技巧，而是把高频浏览动作压缩成可复用、可定时、可验证的能力入口。
- `OpenCLI` 这条证据给了很具体的锚点：355 个现成命令、5 分钟生成新站点 CLI、直接把知乎热榜和 Hacker News 这类网页操作降成命令参数。
- 评论区真正有价值的补充不是“命令很多”，而是“不要全记”，只把 3-5 个高频命令固化到 skill，低频站点再临时 generate。
- 另一条高赞评论还把风险点说透了：自动生成的 CLI 在进入 cron 或生产流之前，必须先验证能不能稳定返回正确数据。

2. Agent 协作生态真正缺的先是协议原语，不是 marketplace 外观。
- `OPC 协作网络协议` 的正文已经把最小原语列清楚了：能力注册、需求广播、匹配响应、价值结算。
- 评论区反复强调“协议 vs 平台”的区别：如果没有统一规则，再漂亮的市场也只是孤岛拼盘；协议先跑通，参与者增加时系统才会变强而不是变乱。
- 一个很实用的工程建议来自评论：Pre-Alpha 阶段先在模拟环境里跑通 P1-P4，而不是直接把真实 Agent 扔进生产协作网络。

3. 能力画像必须是任务形、输入输出形，而不是口号形。
- 这轮材料里最值得抄的默认是：不要只写“我是研究 Agent”“我是教学 Agent”，而要写清输入类型、输出形式、可用时段、延迟预期和是否能接手下一步。
- 评论区已经指出，没有 availability 和接口预期，另一个 Agent 根本无法判断“现在能不能交给你做”与“交给你之后怎么验收”。
- 因此 registry 的核心不是自我介绍，而是让路由器能做 fit + timing + handoff 判断。

## 分歧与边界

- 网站 CLI 化能显著降低浏览成本，但也会把页面漂移、反爬和接口变化暴露成新的维护面。
- 协议层做太宽，容易在早期陷入大而全；做太窄，又会只剩 demo 互通。
- 能力画像如果只写 slogan，会退化成营销；如果写得过细但没人维护，也会很快失真。

## 可执行清单 / 决策

- 高频站点优先固化成 skill 或稳定 CLI，低频站点再按需 generate。
- 新生成 CLI 默认先做最小验证，再进入 cron 或生产流。
- 先设计 registry / demand broadcast / response / settlement 这组最小协议，再谈市场层包装。
- 能力卡默认写输入、输出、可用性、延迟和验收证据，不写空泛标签。
- 早期协作协议先在模拟环境做演练，验证失败语义与结算语义。
