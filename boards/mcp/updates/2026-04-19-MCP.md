# 2026-04-19--MCP 工具协议与工程化：学习增量

这批 MCP 材料把讨论重点从“协议很火”推进到了“怎样把实时能力做成可运营、可恢复、可托付的系统”。

## 这次新增了什么

- MCP 的价值开始更明确地落在 runtime 上，而不是停在协议口号。
- server 拆分、命名契约、guardrail 和生态复利，开始一起被当成生产化问题看待。

## 关键结论

### 1. push-based 实时循环只有补上 backpressure 和 restart safety 才成立
这轮讨论里最硬的共识，是不要把“支持推送”误读成“天然更可靠”。真正决定系统能不能长跑的，还是队列、限流、checkpoint、重启恢复和状态持久化。没有这些控制件，实时只会把错误更快地放大。

### 2. 窄域 MCP server 比巨型全能 server 更安全也更好维护
剩余证据几乎都在支持同一个方向：每个 server 只拥有一小块明确领域，权限边界更清楚，故障 blast radius 更小，调试时也更容易定位问题。对生产环境来说，这种拆法比一个“什么都接”的总 server 更容易建立信任。

### 3. 工具命名是 interface contract 的一部分
`search_documents`、`list_projects` 这类 verb-noun 命名不是洁癖，而是降低误调用和提升 discoverability 的关键。模型对 schema 的第一印象很大程度就来自名字；名字模糊，后面的安全调用与正确路由都会一起变差。

### 4. production MCP 需要显式 guardrail，而不是停在 demo 可用
这批材料把 demo 与 production 的差别讲得很清楚：retry-aware error、hard timeout、审计日志、rate limit 和高风险确认，都是协议真正落地时的默认件。能跑通一次，不等于可以持续托付。

### 5. 共享协议的价值，在于让能力跨产品复利传播
当 GitHub、数据库、文件系统等能力都能通过兼容 MCP server 暴露出来，每一个新 server 都能被多个 agent / client 复用。真正值得看重的信号，不是某家厂商单点 feature，而是整个工具生态开始共享同一套连接方式。

## 需要做的决策 / checklist

- 为 push-based loop 设计 backpressure、queue 和 checkpoint。
- 每个 MCP server 默认只负责窄域能力。
- 工具命名采用清晰的 verb-noun 契约。
- 为高风险动作补 timeout、日志、确认和错误分层。
- 优先投资 shared protocol，而不是 vendor-specific 封闭特性。

## 风险 / 边界情况

- 事件驱动减少了轮询，但也会把瞬时流量峰值和恢复语义问题前置。
- server 过度切碎也可能提高运维成本，需要以领域边界而不是随意拆分为准。
- 只改命名、不改 schema 与错误语义，仍然无法真正提升可靠性。
