# 2026-03-29--MCP / 工具协议：学习增量

这次新增的焦点可以压成一句话：prompt 瘦身不是写作技巧，而是协议设计——稳定控制逻辑应该进工具、进 wrapper、进 contract，而不是继续堆在提示词里。

## 关键结论

### 1. Prompt 负责上下文和判断，稳定逻辑负责下沉
- 这轮材料最强的一句判断标准是：如果一条规则能被代码、正则、条件判断或校验表达，它大概率就不该继续留在核心 prompt 里。
- 这会让模型切换更顺，因为真正决定系统行为的是工具契约，而不是一长段提醒文案。

### 2. 好的工具协议要同时表达错误语义和进度语义
- 从 MCP 视角看，这轮关于 retry 分类和 no-progress 检测的讨论，本质上是在要求 tool contract 返回的不只是结果，还有“能不能再试”“有没有推进”“是不是逻辑错误”这些控制信息。
- 工具如果只有 happy path 返回值，orchestrator 就只能靠日志猜状态。

### 3. 死循环检测应该被编进协议，不该留给人类盯
- 评论区提到的 `progress_hash`、state delta hash、snapshot 增量，本质都是协议字段，而不是临时排障技巧。
- 一旦把这些信号写成 contract，长链路 Agent 才会拥有统一的停机条件与熔断规则。

### 4. 协议要持续从错误里长出来
- 这轮讨论里一个很稳的升级路径是：一次纠错写进 corrections，二次复发升级为 domain rule，三次复发硬化成 skill 检查项。
- 对 MCP 工程来说，这意味着 contract 是演化出来的资产，而不是一开始就写完的神圣文本。

## 需要做的决策 / checklist

- 把稳定规则、异常处理和验证逻辑尽量下沉到工具、wrapper 或 skill。
- 给高频长链路工具补错误分类与进度信号，不只返回执行结果。
- 把 no-progress 检测编成协议能力，不再留给人类事后盯日志。
- 用“纠错 -> 规则 -> 硬检查”的路径持续演化工具契约。

## 风险 / 边界

- prompt 瘦身不等于 prompt 可以随便写；目标、约束和上下文仍要表达清楚。
- 并不是每个工具都需要复杂 contract，应优先覆盖高频、高风险和长链路动作。
- 协议越强，初期建设成本越高，必须按 ROI 排序推进。
