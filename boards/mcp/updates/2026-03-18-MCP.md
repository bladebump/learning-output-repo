# 2026-03-18--MCP 工具协议与工程化：学习增量

这次增量只覆盖两条来源，但信号很集中：函数调用稳定性的上限，不取决于模型有多敢猜，而取决于接口契约和调用范式是否足够清楚。

## 关键结论

### 1. 最大坑通常是心智模型错位
- MCP / function calling 常被误当成 CLI flag 或 JSON 字符串接口，结果越熟悉命令行的人越容易先走错。
- 先纠正心智模型，再纠正语法细节，效率会高很多。

### 2. 经验要沉淀成可迁移的调用范式
- 值得保存的不是“这次写对了什么命令”，而是最小正确示例、参数形状、适用场景和调试步骤。
- 这样下次迁移到同类工具时，复用的是模式，不是记忆碎片。

### 3. schema / OpenAPI 契约决定 function calling 成功率
- 字段名、参数类型、错误返回越明确，模型越少需要猜测。
- 真正该优化的是接口描述质量，而不是寄希望于模型自己补全一切空白。

### 4. 调试流程也应标准化
- `list / describe / schema-check / call` 这条顺序，应该成为默认 runbook。
- 参数名对了但类型错了、对象与字符串形状不一致，都是高频失败点。

## 需要做的决策 / checklist

- 为常用工具保留最小正确示例。
- 调用前先看 schema，不直接盲打。
- skill 文档里明确参数类型、对象形状和错误返回格式。
- 把 CLI、JSON、function-call 三种心智模型明确分开。
- schema 更新后同步更新调用模板。

## 风险 / 边界情况

- 即便用了 function-call 语法，参数 shape 错误仍会导致失败。
- 过度严格的 schema 会抬高接入门槛，需要在灵活性和可验证性之间做平衡。
