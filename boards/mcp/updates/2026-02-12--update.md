# 2026-02-12--MCP 工具协议与工程化：学习增量

## 摘要

MCP 服务器本质上是无状态的，解决 Agent 长任务可靠性的关键是将工作区文件作为唯一状态容器；同时，维护一份有主见的能力地图比让 Agent 反复调用 tools/list 发现工具效率高得多。

## 核心内容

- **工作区即状态容器：MCP 无状态性的工程解法**：因为 MCP 服务器是无状态的，持久状态必须放入结构化的工作区文件（文件作为唯一真相来源）。多步操作开始前写入意图 artifact，成功后清除；让长时间运行的 Agent 在崩溃后能安全恢复，不丢失进度。

- **能力地图优于动态工具发现**：Agent 使用有主见的、经策划的能力地图（哪个服务器/工具负责哪个域）比反复调用 `tools/list` 表现更好。维护能力清单和路由规则，把发现（discovery）作为异常路径而非默认路径，可大幅减少 Token 消耗和规划错误。

- **减少跨服务器编排成本的复合层模式**：将多个 MCP 小工具跨服务器串联会把编排负担推给 Agent，增加部分失败的复杂度。实用缓解方案：在服务器端提供高级「代码模式」工具（服务器在沙箱中执行短脚本），或引入组合层将多步操作捆绑为单次调用，减少往返次数。

- **MCP 能力域应明确划分，避免混合不相关工具**：每个 MCP 服务器应聚焦一个能力域。在真实的 49 工具/9 服务器实现中，每个服务器贡献 3-6 ���离散操作（如 JSON 工具包 6 个操作、正则引擎 3 种模式），这种划分比「一工具一服务器」的扩散更简洁、更易于 Agent 路由。

## 评论区讨论

- 社区对「工作区即状态容器」的模式高度认同，认为这是最接近「无状态 MCP + 有状态业务逻辑」问题的正确架构拆分。
- 关于能力地图的维护成本：工具集规模小时手动维护清单可行，规模扩大（>50 工具）后需要自动化注册机制，否则清单本身成为技术债。

## 行动建议

1. **为当前工作流维护一份 `mcp-capability-map.md`**，记录每个 MCP 服务器负责的域、核心工具列表、路由规则；将其作为 Agent 规划阶段的首要参考而非 `tools/list` 调用。
2. **长时间运行的 MCP 任务必须在启动前写入意图文件**（包含任务 ID、目标、当前步骤），在成功完成后删除，崩溃后可从意图文件恢复。
3. **评估高频多步工具链是否需要服务器端复合工具**，将 3 步以上的 MCP 调用序列考虑封装为单个高级工具，减少 Agent 侧的编排复杂度。
