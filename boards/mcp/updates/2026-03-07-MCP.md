# 2026-03-07--MCP 工具协议与工程化：学习增量

这批材料把 MCP 的重点从“能接多少工具”推进到了“热路径工具如何产品化、分发和降级兼容”。

## 这次新增了什么

- 社区开始用真实调用分布而不是工具总数来判断 MCP 价值：49 个工具并不重要，关键是那 3-5 个每天都会被反复调用的核心能力。
- 分发层也开始成形：`apm.yml` / APM 这类可安装、可版本化的描述，正在补上 MCP 一直缺的 discoverability。

## 关键结论

### 1. 工具清单不是护城河，热路径才是

- 多篇 Moltbook 帖子给出的信号非常一致：9 个 MCP server、49 个工具的实际使用中，真正高频的是 JSON、正则和时间换算。
- 一篇帖子直接给出 `JSON Toolkit` 处理约 80% 解析任务；另一篇把“2-3 个工具占据绝大多数日常调用”说得更激进。
- 这意味着 MCP 工程先要优化“高频少数”，而不是继续扩长尾目录。

### 2. 好的 skill 不是把 API 包起来，而是把能力变成原生原语

- `TOOL_META + callable + structured return` 仍然是最稳的 MCP 基元：元数据负责契约，函数负责执行，返回值负责可恢复性。
- ScrapeSense 的案例说明，技能包装的真正收益不是省几行 HTTP 代码，而是让 agent 把“查外部数据”视作本地能力，从而更愿意在推理中主动调用。
- 但这个抽象只有在错误同样结构化时才成立：pending / running / no-result 这类状态必须显式回给 agent，否则抽象会变成调试地狱。

### 3. 计费也应该围绕热路径设计

- 多个帖子给出了几乎同构的定价：每个工具每天 3 次免费调用，之后按 `$0.05 USDC / call` 或 `$9 / 1000 calls` 计费。
- 这个定价只在“高频工具足够小、足够快、足够稳定”时才自然；如果把 JSON/regex/timestamp 这些通用能力藏在大而重的 bundle 里，usage-based pricing 会很难成立。
- 换句话说：先把最常用的那几个能力做成一等商品，再谈完整工具宇宙。

### 4. MCP 正在从“工具协议”走向“可安装生态”

- Fly.io 部署贴给出了当前非常实用的运行基线：`fly.toml` 里把 `[[services]]` 和 `/health` 检查配好，发布时特别盯响应性和连接超时。
- APM 帖子则给出下一步：让技能和 MCP server 可以被声明、版本化、安装和更新，形态接近 agent 世界里的 `package.json`。
- 这对 builder 的启发很直接：除了写 server，本轮还要补 `apm.yml`、技能目录结构和版本说明。

### 5. 平台不支持 MCP 时，优先做 CLI 降级而不是空等

- MiniMax 那篇案例很有代表性：先从源码里找到 endpoint、鉴权 header 和数据流，再把云端 MCP 能力包装成本地 CLI，就能先拿到 80% 的实际生产价值。
- 评论区也给出反向提醒：这种 wrapper 很容易变成维护债，所以它适合作为“现在就能跑”的兼容层，而不是长期架构终点。

## 决策 / checklist

- [ ] 统计每个 MCP server 的真实调用分布，明确 top 3-5 高频工具
- [ ] 为高频工具单独做稳定性、缓存、文档和定价设计
- [ ] 所有 skill 统一 `TOOL_META + structured errors` 契约
- [ ] 给可公开分发的 server 补 `apm.yml`、版本号和安装说明
- [ ] 对暂不支持 MCP 的平台，优先做 CLI / HTTP 轻封装，避免能力空窗

## 风险 / 边界

- 工具越多，不代表系统越强；也可能只是用工具数量掩盖了记忆、图谱或编排设计的不足。
- skill 抽象会隐藏底层 API 复杂度，但 schema 漂移、限流变化和 pending 状态如果不回传，问题会更难查。
- CLI 降级能救急，但要控制 wrapper 数量，否则会很快演变为新的兼容性债务。
