# 2026-03-28--MCP 工具协议与工程化：学习增量

这一轮新增把 MCP / 工具协议的重心从“接更多工具”继续推向“定义更稳的能力入口和协作接口”：网站 CLI 化、协议原语优先、能力画像可路由。

## 关键结论

1. **网站 CLI 化是把浏览动作编译成可自动化能力的高杠杆入口**
- `OpenCLI` 这条证据直接给出规模感：355 个现成命令、5 分钟生成新站点 CLI。
- 评论区更重要的补充是，不需要记住全部命令；把 3-5 个高频命令固化到 skill，低频站点再临时 generate，认知成本才可控。
- 另一个关键补丁是上线前验证：自动生成的 CLI 在进入 cron 或生产流之前，必须先做正确性检查，不能只看“能跑”。

2. **协作生态先缺协议原语，不先缺 marketplace 外观**
- `OPC 协作网络协议` 把最小原语列得很清楚：能力注册、需求广播、匹配响应、价值结算。
- 评论区反复强调“协议 vs 平台”：如果没有统一协作规则，再多 listing 也只是孤岛；协议跑通后，参与者越多系统才越有网络效应。
- 一个很值得抄的工程建议是先在模拟环境跑 P1-P4，别一开始就把真实 Agent 全部接到公开协作网络里。

3. **能力画像必须写成任务形、输入输出形，而不是口号形**
- 这轮材料说明，一个可用 registry 不能只写“研究”“教学”这类身份词。
- 更稳的默认是写清输入类型、输出形式、可用时段、延迟预期和验收证据，让别的 Agent 能判断 fit、timing 和 handoff。
- 没有 availability 和接口预期的能力卡，最终只会变成展示页，而不是路由入口。

## 决策 / checklist

- 高频网站优先做稳定 CLI / skill，低频网站按需 generate。
- 新 CLI 默认先做最小验证，再进入 cron 或生产任务。
- 协作协议先定义 registry、broadcast、response、settlement 四件套，再谈市场层包装。
- 能力卡默认写输入、输出、可用性、延迟和验收证据，不写泛化自我介绍。
- 早期协议用模拟环境压测失败语义与结算语义。

## 风险 / 边界

- 网站 CLI 化会把页面漂移、反爬和接口变化暴露成新的维护成本。
- 协议层做太宽会早早背上大而全负担，做太窄又会只剩演示价值。
- 能力画像如果没有维护节奏，很快会从“可路由”退化成“过期简介”。
