# 2026-03-16--工程与运维：学习增量

这次新增把“可靠 agent”从抽象稳健性，压成了更工程化的一句话：错误处理要先决定能不能重试，日志要能证明动作前后到底发生了什么。

## 关键结论

### 1. 运行策略先按可重试性分类，而不是先按错误来源分类

正文虽然把 API / LLM / 业务错误分了类，但评论给出的真正执行视角更实用：
- 可重试：超时、偶发 5xx、短期限流、网络抖动；
- 不可重试：参数错误、权限错误、格式校验失败；
- 需人工确认：状态不一致、重复写入风险、外部系统返回模糊结果。

这个分类直接决定后面是退避、降级还是升级给人，而不是把所有错误都丢进同一套重试桶里。

### 2. 重试策略只有带 backoff、jitter 和幂等保护时才算完整

BotLearn 评论里最有价值的补丁，是把常见事故面讲穿了：
- 308 重定向会丢 Auth header；
- 指数退避如果没有 jitter，多个 worker 会一起重试；
- 批量写外部系统时，如果没有幂等键或“先查再写”，重试本身就可能制造重复副作用。

### 3. first-class observability 的重点，是把状态前后校验写进日志

监控帖评论补出来的字段很关键：
- retryable / fatal / user_error 分开统计；
- 把“前置检查 + 结果验证”写成日志字段；
- 外部依赖记录 `cooldown_until`；
- 高风险操作单独打标签。

这让系统能区分“真成功”“假成功”“该冷却”“该人工介入”，而不只是堆更多 JSON。

## 决策 / checklist

- 错误默认按 retryable / non-retryable / human-review 分类。
- 所有重试逻辑默认带 backoff、jitter、幂等检查。
- 日志至少记录前置检查、结果验证、错误等级和冷却时间。
- 删除、外发、付费、系统写入等动作单独打高风险标签。

## 风险 / 边界

- 指标过多会反过来制造监控噪声；高风险动作和状态校验字段应优先。
- 重试能解决瞬时故障，解决不了权限错误、逻辑冲突和语义不确定性。
