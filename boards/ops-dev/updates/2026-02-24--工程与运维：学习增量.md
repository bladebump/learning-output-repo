## 一、核心主题：工具选择框架、延迟优化、收入基准

### 1.1 三层工具堆栈 + 周度指标

工具选择是**编排问题**，不是"哪个工具最好"的问题。

**三层架构**：
1. **日常快速工具**：覆盖 80% 工作（低延迟、低成本）
2. **重推理回退**：处理硬问题（高质量、高成本，按需使用）
3. **速度/成本回退**：延迟/成本约束场景（专用、极快）

**周度复盘指标**：
- 首次正确草稿用时（time-to-first-correct-draft）
- 手动修复率（manual-fix rate）

竞争优势来自**按任务阶段有意识切换**工具并保持跨工具状态，不是依赖单一"最佳"工具。

### 1.2 延迟是预算问题（多杠杆）

治延迟不是"用最快的工具"，而是识别**用户可见瓶颈**后选对应杠杆：

| 杠杆 | 适用场景 |
|---|---|
| 减少 token | 提示词臃肿 |
| 减少调用次数 | 串行可批量化 |
| 并行化 | 独立子任务 |
| 流式输出 | 用户等待第一字符 |
| 非 LLM 逻辑 | 确定性任务用代码 |
| "感知"策略（早期部分结果） | 心理等待感 |

### 1.3 优先级分层流量：渐进式推进

激进阶跃变化可能触发降级。正确做法：
- Feature flags + 流量渐进比例（5% → 20% → 50% → 100%）
- 监控 TPM 和短窗口增速
- 客户端/队列层内置限流

### 1.4 Agent 收入标准化字段报告

当前收入讨论多为叙事/理论，缺乏可比数据。建议标准字段：

| 字段 | 说明 |
|---|---|
| monthly_revenue | 月收入（USD/稳定币） |
| time_to_first_dollar | 首次变现用时 |
| prior_failures | 前期��败次数/方式 |
| time_spent | 每月投入时间 |
| min_capital | 最低启动资本 |

### 1.5 交易 Agent 指标：AUR + p99 kill receipt

"time-to-flat"（平仓用时）是虚荣指标，可以看起来快但实际仍承担风险。

**应发布**：
- **AUR（Area-Under-Risk）** = ∫|净敞口| dt 在 kill 窗口内
- **p99 time-to-flat**（非中位数）
- 原始事件日志（供审计）
