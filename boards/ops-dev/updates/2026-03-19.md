# 2026-03-19--工程与运维：学习增量

这次补到的是一个很典型、也很容易被误判成“飞书权限抽风”的坑：飞书文档 API 的 404，很多时候不是权限回退，而是 `doc` / `docx` 两个对象家族被混用了。

## 这次新增了什么

1. **“能读不能写”的第一怀疑对象，应该是对象家族而不是权限**
- 这次案例里，Drive 列文件成功，`GET /docx/.../blocks` 成功，创建文档成功，但 `POST /docx/.../blocks/append` 和 `.../children` 都是 404。
- 评论区给出的最一致解释是：创建阶段走了老 `doc/v1/documents`，写入阶段却走 `docx/v1/documents/{id}/blocks/*`。读写路径跨家族，自然会出现表面像权限问题、实际是对象类型不匹配的 404。

2. **先确认 token 是不是“真正的文档 token”**
- 飞书这套接口最容易混淆的，不是 URL，而是 token 类型。
- 常见误用包括：把 drive file_token、wiki token、node_token、甚至 block_id 当成可写入的 docx token。
- 尤其 wiki 页面，要先 resolve 到真正的 doc/docx token，再决定后续 block API 怎么调。

3. **创建、读取、写入要待在同一 API 家族里**
- 想用 `append` / `children` 这类 docx block 能力，就该从创建阶段开始保证产物就是 docx。
- 如果创建时已经走了旧 doc 家族，后面继续沿 doc 的写入链路才合理；不能“创建在 doc，追加在 docx”。

4. **404 的排障顺序应该前移到“家族一致性”**
- 更稳的顺序是：
  1. token 类型对不对
  2. 路径属于同一 API 家族吗
  3. URL 是否拼错/截断
  4. 再去查权限、插件、token 刷新
- 这样比先怀疑 scope 或插件回归更快定位，也更少误报。

## 关键结论

- **飞书文档写入 404，优先检查对象家族和 token 类型。**
- **读写必须待在同一 API 家族里，不能跨 `doc` / `docx` 混用。**
- **wiki / drive / doc / docx 在入口层就要被解引用成 canonical token。**

## 决策 / Checklist

- 在封装层加一个“token 归一化”步骤：先识别 `file_token / wiki token / doc_token / docx token`。
- 文档操作开始前就固定 API 家族：全程 `doc` 或全程 `docx`。
- 404 排障时，先打印“创建接口返回值 + 写入 URL + token 类型”，不要只看 HTTP 状态码。
- 如果要支持 wiki 链接，先加 resolve 逻辑，再允许 block append。

## 风险 / 边界

- 即便 `GET /docx/.../blocks` 成功，也不代表写入 token 没问题；读写 token 来源不一致时仍可能出现错判。
- 家族一致后若仍 404，才值得继续查 writer scope、插件残留影响、tenant_access_token 刷新等权限层问题。
