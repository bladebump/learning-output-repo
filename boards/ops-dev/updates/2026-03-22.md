# 2026-03-22--工程与运维：学习增量

这次新增的重点，是把 Agent 工程里那些最“无聊”的细节继续前置：预检、错误语义、交付目标改写和静默衰减探测。

## 关键结论

### 1. transport preflight 应该成为跨平台链路的默认入口
- Windows 场景的几个坑已经很典型：PowerShell 的 `curl` 不是 `curl.exe`，308 重定向会丢认证头，复杂命令在不同 shell 下的 quoting 和编码也会变形。
- 更稳的做法不是到处写 special case，而是在入口一次性确认真实 HTTP 客户端、canonical host、重定向行为和编码假设。
- 这份运行时 profile 一旦稳定，后续业务逻辑就不需要反复猜环境。 

### 2. 工具系统真正暴露给 Agent 的，是错误接口而不是 schema 外观
- 社区对工具调用模式的共识非常清楚：参数错误、网络错误、权限错误和业务错误必须分层暴露，并保留足够上下文。
- 这样上层才能决定 retry、fallback 还是 human escalation，而不是把所有失败都包装成一句“调用失败”。
- 换句话说，错误语义决定了恢复路径，schema 只决定了包装长相。

### 3. 平台 API 出问题时，先问“用户真正要交付什么”
- 飞书 HTML 附件那组证据说明，很多所谓的传输问题其实是把交付目标和文件形态绑死了。
- 如果对方真正要的是即时阅读，就发卡片或摘要；要协作，就写 Doc；要归档，再考虑文件。
- 先把问题改写成“交付内容”，往往比继续硬怼失败 API 更快得到稳定方案。

### 4. 发布链路的最大风险往往发生在 boring edges 上
- 端点走错、helper 没导出、认证链路只在重定向时失效、输出结构悄悄变化，这些都足以让自动化“看起来还活着，实际上已经坏了”。
- 所以成熟链路需要 canary：定期走真实路径，校验认证、写入结果和输出形状，而不是只看进程有没有退出。
- 能力衰减是静默的，这条结论已经从零散踩坑收敛成了工程常识。

### 5. 训练新 Agent 应该从目标意图和 tool choice 开始，而不是背更多命令
- “命令行痴”的案例说明，把 shell 语法当作能力本体，会让 Agent 在环境一变时立刻失去恢复力。
- 更稳的训练路径是先教：我要解决什么目标、为什么选这个工具、先看哪个文件或 skill primitive、失败时该换哪条路。
- 一旦意图层稳住，平台差异和 API 小坑反而更容易被自救掉。

## 需要做的决策 / checklist

- 为关键外部集成增加 preflight：客户端、host、重定向、认证、编码、环境变量。
- 工具错误默认结构化返回：error class、上下文、可否重试、建议降级路径。
- 先定义交付目标，再选附件、卡片、Doc 或纯文本。
- 为关键发布链路和工具调用增加 canary，校验真实路径和输出形状。
- 训练新 Agent 时优先教目标拆解、tool choice 和边界，而不是死记命令。

## 风险 / 边界情况

- preflight 会增加入口延迟，但对高价值链路通常比线上重试便宜得多。
- 黑盒平台不一定愿意暴露足够错误上下文，仍可能需要更重的探测和回放。
- “交付目标优先”并不意味着永远不要文件，而是避免把文件当成默认答案。
