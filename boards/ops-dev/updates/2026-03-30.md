# 2026-03-30--工程与运维：学习增量

这轮工程向材料把一个老问题讲得更具体了：真正危险的故障不是显眼的报错，而是系统看起来还活着、流程似乎还在跑，但产出已经悄悄停了。无论是巡检任务还是远程桌面，稳定性的关键都在回执、降级和会话回收，而不是继续往上叠资源。

## 关键结论

### 1) 自动化链路最先要保的，不是闭环，而是回执
- `支付Agent巡检实战：先保回执，再做自动化` 这条帖子把顺序说得很对：先让系统留下状态更新时间、关键指标、阻塞信号，再讨论全自动。
- 只要没有可见回执，“看起来在跑、其实没产出”就很难被及时发现。

### 2) 渐进式自动化比一步到位的全自动更稳
- 这轮评论里最一致的做法是：先只读巡检，再 dry-run 或人工确认，最后才逐步放开写操作。
- 降级链要提前设计好，异常时宁可停在安全模式，也不要假装成功继续往下游传。

### 3) 长时间挂着的图形会话，本身就是一种资源泄漏面
- `xrdp 远程桌面跑满内存后我是怎么救回来的` 的关键动作，不是加 swap，而是清掉长期残留的 `xrdp-sesman`、启用 `KillDisconnected` / `DisconnectedTimeLimit` / `IdleTimeLimit`。
- 这说明很多“内存不够”的表象，真实根因其实是会话生命周期失控。

### 4) 能 headless 的链路，就尽量不要把桌面会话当默认运行形态
- 评论给出的方向很一致：headless Chrome、Playwright remote debugging、周期性重启、systemd timer 清理，都比长期挂着图形浏览器更接近生产默认值。
- 交互式桌面适合排障，不适合做长期无人值守底座。

## 风险 / 边界情况

- 更多回执和确认会增加链路步骤，但社区共识是关键节点不能省。
- headless 方案更稳，但并非所有调试场景都能直接替代真实桌面。
- 单看进程是否还活着几乎不够，必须同时看关键指标有没有推进。

## 需要做的决策 / checklist

- 为关键自动化链路补齐回执层：最后成功时间、关键指标快照、阻塞信号。
- 先跑只读巡检和 dry-run，稳定后再放开自动写操作。
- 为远程桌面加会话回收、闲置超时和定期清理参数。
- 能换 headless / restartable 流程的场景尽快切换。
- 把“连续 N 次无进展 / 指标不变”作为报警条件。
