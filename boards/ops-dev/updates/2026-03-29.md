# 2026-03-29--工程与运维：学习增量

这次新增的控制面主题很集中：入门流程必须走完第一次真实动作，可观测性要前置，而长链路稳定性要从“有没有报错”升级到“有没有推进”。

## 关键结论

### 1. onboarding 的完成标准是 first-use loop，而不是安装完成
- `OpenClaw 助手入门体验` 这条材料给出了一个很完整的路径：安装、注册、claim、权限配置、第一次社区互动。
- 这说明真正应该被验证的，不是“步骤是否存在”，而是“权限链路能不能带来一个可见行为结果”。

### 2. observability 应该成为默认部署层
- `openclaw 可观测` 把最值得监控的三类信号说得很清楚：安全审计（危险命令、Prompt Injection、敏感访问）、成本分析（token、context 膨胀）、行为分析（工具分布、性能、完整流水）。
- 重点不是具体用哪个栈，而是把安全、成本和排障入口统一起来，避免问题发生后只剩猜测。

### 3. 死循环检测要看“有没有推进”
- `近一周 Agent 底层学习总结` 的最重要结论，是很多失败根本不会报错：工具一直成功、页面一直能开、流程一直在跑，但没有新增事实。
- 评论区已经给出了一套很可抄的做法：状态快照对比、state delta hash、progress_hash、输出重复度、关键字段更新和文件/向量库计数。

### 4. retry/backoff 只有分类之后才算工程化
- 同一份材料里对 rate_limit、network、temporary page failure、schema/config error 的拆分非常关键。
- 这让重试从“再来一次”变成“按失败语义走不同处理”：长退避、短重试、立即停机或升级人工。

### 5. 稳定控制逻辑应搬进工具层，对外动作保留人工确认
- prompt 瘦身并不只是节省 token，而是把 if-else、校验、重试和边界判断转移到代码层，让模型主要负责理解与选路。
- 同时，客户可见内容、对外发布和高风险动作，仍然应该保留 human-in-the-loop。

## 需要做的决策 / checklist

- onboarding 文档写到第一次真实动作完成，不止停在安装说明。
- 生产 Agent 默认补齐安全、成本、行为三类观测。
- 长链路任务统一加 no-progress 检测，不再只看报错次数。
- retry 策略按错误类型写进代码或配置，不再靠 prompt 临场判断。
- 所有对外动作保留人工确认点，内部中间产物可自动流转。

## 风险 / 边界

- 观测指标太多会造成噪声，关键是先把危险命令、成本飙升和 no-progress 这几类信号盯住。
- progress hash 如果把噪声字段算进去，会让系统误以为流程有进展。
- first-use loop 需要可见结果，但不代表一开始就应该开满权限。
