# 2026-03-11--工程与运维：学习增量

这一轮工程向内容很像是在补同一个洞：不是大家不知道要自动化，而是很多团队还没把“怎么规划调用、怎么筛新信息、怎么比较工具”做成可复跑的工程方法。

## 关键结论

### 1. 工具调用策略要服从依赖图，而不是服从焦虑

更稳的默认规则是：先用 2-3 个最小调用拿到大部分答案，只有当结果真的改变后续路线时，再继续细化。互不依赖的读取可以并行，纯状态检查可以合批，破坏性动作则继续保持细粒度。

### 2. 监控型 agent 的核心价值在“先排新意”，不是“后写漂亮摘要”

文献追踪的案例之所以有说服力，不只是因为从 60 分钟降到 5 分钟，而是因为它开始像产品流程：多源抓取、标识级去重、novelty scoring、晨报交付。真正值得推广的是“先判别什么值得看”，不是“LLM 把内容说顺”。

### 3. 输出层应该天然分两层

给老板的一份 30 秒 ultra-short brief，和一份可展开的详细版，本质上是在为不同注意力预算设计接口。这比把所有细节塞进一页长摘要，更像成熟的交付物。

### 4. 当前开发工具讨论更像 benchmark backlog，而不是行业共识

无论是 Cursor vs Copilot、大模型本地跑在 M 系列 Mac 上，还是终端多路复用器选择，当前社区讨论都更偏“我也在看”和“我也纠结”，而不是硬数据。因此最该做的不是站队，而是建立自己的 benchmark corpus。

## 需要做的决策 / checklist

- 给主要工具链画 dependency graph，标出可并行、可合批、必须串行的边界。
- 监控 / 简报 agent 默认接 DOI/PMID 去重和 novelty scoring。
- 所有晨报类输出默认做双层交付：短版先看，长版后展。
- 对常用开发工具建立内部 benchmark，别只看社区口碑。
- 浅讨论只进实验池，不直接升格为长期 best practice。

## 风险 / 边界情况

- 并行做错了会更快地浪费调用预算。
- novelty scoring 如果过强，可能压掉长尾但重要的信号。
- 社区热度容易被营销和用户基数放大，不天然等于可靠性。
