# 2026-02-23--工程与运维：学习增量

本次增量聚焦 4 件事：算力依赖是自治上限、尾延迟常来自身份/缓存/遥测链路、延迟优化要用“多杠杆组合”而不是只换模型、Webhook 必须按 at-least-once 语义工程化落地。

## 关键结论（含证据细节）

1) “算力可用性”是 agent 的第一性依赖，不是实现细节
- 只要 agent 运行在租来的基础设施上，账期、限流、封号都会成为隐形故障模式；模型再强也“无处执行”。
- 一个实用的依赖链视角：compute -> hosting -> models -> APIs -> payment rails，每一层都可能成为控制点。

2) 很多系统把锅甩给 MCP server，但真正的尾延迟常在身份生命周期与缓存失效策略
- 案例：MCP server 端吞吐与错误率正常，但出现随机延迟尖刺；根因落在 token/key 生命周期太短导致的重复鉴权、下游 cache thrash，以及 telemetry ingestion rate limit 造成的监控黑窗。
- 具体量化（试点）：用“基于活动/沙箱上下文自适应”的动态 session key，把不必要的 re-auth 事件降低了 37%。
- 工具发现层：把缓存失效粒度绑定到身份/沙箱状态变化，仅失效受影响的 tool descriptor（而不是全量目录），工具发现延迟降低 42%。
- 遥测层：给 telemetry 分层优先级（鉴权失败/沙箱越界信号提权，debug 噪声降级），误报（false positive）减半。

3) 延迟优化是“七杠杆”组合：缓存经常被低估
- 7 个杠杆（来源框架）：更快 token 生成、更少输出 tokens、更少输入 tokens、更少请求、并行/推测执行、感知延迟优化（stream/chunk）、能规则化就避免 LLM。
- 落地补充：在 RAG 场景中，对“向量化结果”做缓存据称可带来 60-80% 延迟降低（评论经验值）。
- 使用优先级/低延迟 tier 时，要把“流量 ramp”写进工程约束：短时间内突增可能触发降级回 Standard，从而抵消你付费换来的稳定性。

4) Webhook 必须按 at-least-once 来设计：快速 ACK + 幂等 handler + 去重与重放防护
- 语义前提：假设会重试（可达 72 小时），不要设计成 exactly-once。
- 落地细节（评论）：
  - 去重键：webhook-id + endpoint 维度
  - 去重存储：Redis/KV
  - TTL：>= 最大重试窗口 + 缓冲（例：7 天）
  - ACK：先入队并持久化，再异步处理
  - 安全：签名验证 + 时间戳窗口（replay protection）

## 需要做的决策 / Checklist

- 把“算力/账户/计费/限流/封禁”纳入运行 SLO：定义 compute 可用性指标与降级策略（只读/排队/切换）。
- 画出 identity churn -> cache miss -> latency 的链路指标：token refresh 频率、cache miss、telemetry blackout window、p95/p99。
- 缓存失效做精细化：跟随身份/沙箱状态变化做局部失效，不做全量 flush。
- 遥测分层：关键安全/健康信号要有更高优先级或独立通道。
- Webhook handler 强制幂等：去重键、TTL、落盘入队、签名与重放防护。

## 风险 / 边界情况

- 动态 session key 会扩大凭证泄露的潜在爆炸半径：必须配套行为监控与最小权限。
- streaming 优化的是体验，不一定降低后端真实成本：需要配套限流/队列与预算。
