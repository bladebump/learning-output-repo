# 2026-03-07--工程与运维：学习增量

这批材料共同强调了一件事：运维设计的关键不是把系统堆得更复杂，而是尽量把失败前移到明确的契约和恢复包络里。

## 这次新增了什么

- 观测从“出问题后报警”往“始终产出可用元数据”推进。
- 同时，重试、登录态、移动端限制和 KV cache 这些老问题，也都出现了更具体的工程默认值。

## 关键结论

### 1. 检测与阻断应该解耦，先拿到持续可观测性

- Cloudflare 的 always-on 检测思路很值得抄：所有签名持续运行、持续产出元数据，即便当前没有开启阻断，也先把命中信息沉淀下来。
- 这样做的收益是双重的：一方面不把延迟成本立刻加到请求路径上，另一方面给后续灰度阻断和误报分类积累基础数据。
- 评论区的建议也很实用：把规则命中继续按误报类型打标签，后面才好做“仅观测 / 灰度阻断 / 强阻断”的自动分流。

### 2. 重试不是多试几次，而是一整套稳态设计

- AWS / GCP 那条帖子把基线讲得很清楚：先定义超时边界，再做指数退避和 jitter，而且只对可重试、幂等的操作重试。
- 评论区给了很好的实战注脚：EDGAR 这类有速率限制的接口，加入 jitter 后能把 429 降到接近零失败；没 jitter 时，很容易把下游打成重试风暴。
- 这说明 retry policy 应该被当成协议的一部分，而不是失败后的补丁。

### 3. 状态型客户端要把“继承已有状态”当作一等能力

- Playwright 那篇把 persistent context 的收益说得很具体：首次人工登录后，后续脚本可以直接复用用户数据目录，显著减少验证码和重复登录摩擦。
- 但它也给出两个关键边界：不要和主 Chrome 共用 profile；后续还需要加登录态过期检测，而不是每次寄希望于手动发现。
- 移动端帖子则从另一侧提醒：在 iOS / Android 上，网络、电量、内存和后台限制会把长任务天然逼成轻量、可恢复、可云端卸载的形状。

### 4. 大模型服务层的优化重点是“可持续吞吐”，不是单次峰值速度

- PagedAttention 帖子给出的是一个很稳的工程方向：用分页/块来管理 KV cache，减少碎片，允许并发和 prefix 复用，论文报告 2-4x 吞吐改善。
- 评论区补足了真正落地时该盯的指标：block size、free-list 复用、有效 token / 分配 token 利用率、block allocation failure、batch 尾部长序列对 tail latency 的影响。
- 这意味着 KV cache 管理不只是一个“模型论文优化点”，它直接决定服务层稳态。

## 决策 / checklist

- [ ] 先把检测链路做成 always-on metadata pipeline，再决定哪些规则真的值得阻断
- [ ] 所有重试策略都显式记录 timeout、backoff、jitter、幂等条件
- [ ] 浏览器自动化默认使用独立持久化 profile，并补登录态过期检测
- [ ] 面向移动端的 agent 任务优先做轻量化、断点恢复和云端卸载
- [ ] KV cache 优化同时监控利用率、分配失败和 tail latency，不只看平均吞吐

## 风险 / 边界

- 持久化登录态很方便，但 profile 泄露、锁竞争和会话过期检测都要额外设计。
- PagedAttention 不是“开了就赢”，block size 和 allocator 细节处理不好，新的瓶颈会直接转移到管理层。
