# 2026-03-20--工程与运维：学习增量

这次新增的重点，是把几个常见运维坑都收束到一个共同原则上：真正稳定的系统，不依赖“记得做检查”，而依赖不可跳过的生命周期与错误边界。

## 关键结论

### 1. 浏览器持久化配置首先是 daemon 生命周期问题
- `--profile` 这类参数通常只在首次启动时生效，daemon 已经起来后再改参数不会接管旧实例。
- 更稳的排障路径是：停旧进程、清残留锁与目录权限、再带目标 profile 重启。

### 2. 执行前检查必须从文档步骤变成入口断言
- “先检查再执行”如果只写在 SOP 里，迟早会被跳过。
- 真正有效的是把状态文件、锁文件、TTL 和 preflight 函数做成硬约束，让后续动作根本无法越过检查。

### 3. 认证后冻结的前端，要优先看鉴权首包而不是泛排基础设施
- 如果匿名模式正常、带 token 才挂，问题大概率在 auth-only 路径的数据形状或字段假设。
- 先抓 WebSocket 首包、看 `onHello` payload，再决定是否回头查服务端。

### 4. 工具调用的稳定性来自错误语义和降级链路
- 格式选型不是最关键的，真正重要的是错误分类、指数退避、备用路径和人工接管出口。
- 一个能明确说“不知道/需要人工介入”的系统，比一个盲目重试的系统更可靠。

## 需要做的决策 / checklist

- 把 profile 切换明确写成“重启 daemon + 清理残留锁/权限”。
- 所有高风险自动化入口都补上 preflight 断言与状态文件。
- 认证专属故障优先抓首包 payload，不先扩大排查面。
- 工具调用层默认具备重试、降级、人工接管三类动作。
- 前置检查函数统一落日志，方便定位是否真正执行过检查。

## 风险 / 边界情况

- 过度严格的断言会增加低风险任务的执行成本。
- 容错解析提高了成功率，但不能替代参数合理性和业务校验。
- daemon 生命周期问题通常和锁文件、目录权限、残留进程同时出现，单点修补不一定够。
