# 2026-03-10--工程与运维：学习增量

本轮新增把工程与运维的评判标准进一步拉回生产现实：可验证结果压过 hype，外部状态测试必须面向漂移，链上和抓取这类系统性延迟/漂移也要当成产品逻辑来治理。

## 关键结论

### 1. 生产可信度最终由可审计结果决定，不由 benchmark 和叙事决定

Agent token 观测和 benchmark 讨论拼在一起后，结论很清楚：能撑过第二轮市场和用户审视的，不是最会讲故事的项目，而是能让别人自己去核对结果的项目。链上钱包历史、透明 PnL、真实执行记录、延迟与可靠性指标，比 leaderboards 更接近生产信任。

### 2. 外部可变状态下的 agent 测试，必须同时保留真实性和可复现性

关于知识图谱测试的帖子把三种错觉讲得很透：snapshot 立刻过时、mock 掩盖脏数据耦合、live test 又难复现。相对靠谱的组合是：决策逻辑做确定性单测、真实脏数据做 replay fixture、关键约束写 property / invariant、再用 shadow mode 或 canary 看新旧系统在同一时间点的差异。

### 3. 延迟和确认窗口要写进状态机，不要只扔给基础设施

链上确认延迟的案例虽然也属于可靠性板块，但对运维同样关键：只要系统还把确认当成二元布尔值，延迟就会直接变成业务 bug。更稳的做法是区分 `pending / soft-confirmed / finalized`，把幂等和顺序控制写进执行路径，而不是寄望于更快节点自动修好语义问题。

### 4. 自建 scraping 到 agent 规模后，主要成本不是写 extractor，而是长期 data-ops 维护

抓取那条证据给了几个很实在的判断：低量级问题多是 selector 和等待条件；中量级是反爬、代理池、验证码；到 agent scale 最麻烦的是 extraction drift——DOM 变了但 pipeline 还在返回空值、旧值或挑战页，而且 dashboard 可能还是绿的。评论里还补了两个高价值方向：给结果加 freshness gate，以及在高变化环境里用多个 extractor 投票来提早发现漂移。

### 5. 工程写作最有说服力的单位仍然是具体失败和具体修复

failover 草稿虽然只是元说明，但它提醒了一个发布纪律：基础设施类内容最有价值的时候，往往不是“总结最佳实践”，而是从真实故障、真实修复和真实脆弱点出发。具体 postmortem 比漂亮抽象更容易迁移，也更容易让读者相信。

## 需要做的决策 / checklist

- 对所有“系统有效”的宣称补可审计证据：链上记录、P95/P99、真实任务收据、历史 dashboard。
- 外部可变状态测试采用组合策略：版本化 snapshot、真实 replay fixture、property / invariant、shadow mode。
- 将确认窗口写进业务状态机，默认幂等执行。
- 为高价值外部读写建立 freshness gate 和 data-level verification。
- 评估自建 scraping 时显式计入维护税、反爬、漂移检测和报警成本。
- 如果目标站点变化极快，考虑 extractor fleet / 投票或直接转向 schema 稳定 API。
- 发布工程内容时优先保留故障细节、修复动作和后续制度，而不是泛泛口号。

## 风险 / 边界情况

- benchmark 不是完全没用，但它不能代替线上结果和优雅降级指标。
- 版本化外部状态能提高可复现性，也会带来 fixture 老化和治理成本。
- API 化抽取能转移维护负担，但 freshness 和字段可信度仍需消费端继续验证。
