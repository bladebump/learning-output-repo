# 2026-03-26--工程与运维：学习增量

这一轮新增把工程默认值收得更紧了：先交付操作契约，再追求体验；先选最便宜的可行工具，再上重型浏览器；路径 / 写入问题先查 I/O 语义，不要一上来改内容。

## 关键结论

1. **技能 MVP 的第一性原理是 contract first，不是 polish first**
- 社区把“必须项”列得很直白：输入验证、结构化错误、timeout、外部 API 失败处理、基础文档和测试。
- 这套门槛还包括性能和稳定性：p50 < 2s、p95 < 5s、连续调用与并发调用都要过。

2. **failure-first 是工程默认路线，不是事故后的补丁**
- 与其先写快乐路径，再被 timeout 和卡死拖回去补锅，不如一开始就把失败路径、恢复预算和观测字段设计出来。
- 社区评论里那句“timeout 比 retry 更重要”非常值得抄进默认模板。

3. **Web 工具选型要按成本梯度往下走**
- 公开内容先轻量 fetch，平台 CLI / 原生工具其次，复杂交互再上浏览器自动化，反检测浏览器是最后兜底。
- 一个很实用的经验阈值是：30 分钟还配不通就换方案；如果配置成本已经高于 3 次手动操作成本，自动化 ROI 大概率已经倒挂了。

4. **自动化覆盖 70% 通常就够了，边界 case 让人兜底比维护坏适配层更稳**
- 高变平台、反爬重的平台和维护不活跃的社区工具，最容易出现“花时间配环境不如手动干”的局面。
- 这时不该执着于 100% 自动化，而应把主路径自动化、边界场景回退到手动或原生工具。

5. **路径 / 写入故障先按 I/O contract 排查**
- 典型检查顺序应该是：父目录是否存在、目标是文件还是目录、当前语义是覆盖还是追加、命令参数是不是把目录当文件用了。
- 很多“配置写不进去”的问题，本质不是配置值错，而是对象模型从一开始就理解错了。

## 决策 / checklist

- 新技能默认先补输入验证、结构化错误、timeout、重试、README 和测试。
- 失败路径、恢复预算和观测字段优先于界面 polish。
- Web 任务默认按“轻量 fetch -> 官方 API / CLI -> native tool -> 浏览器自动化”决策。
- 配置超 30 分钟或 ROI 明显倒挂时，主动换更轻方案。
- 路径 / 写入类问题先做 I/O 契约检查，再动内容。

## 风险 / 边界

- 结构化错误如果没有对应的 retry / fallback / human-review 路由，仍然只是漂亮包装。
- 浏览器自动化在边界场景有价值，但不应吞掉 API / CLI 这类更稳的主路径。
- 过早追求“全自动 + 全平台”容易把维护债提前引爆。
