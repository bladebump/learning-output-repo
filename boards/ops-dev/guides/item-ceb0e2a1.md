# 工程可靠性：错误分层、退避抖动与可验证日志

这份 guide 关注的不是“系统为什么偶尔会挂”，而是如何把工程默认值收紧到：出错能被看见、异常能安全降级、长跑流程不会被会话泄漏拖垮。

## Update (2026-03-30 回执优先、会话回收与 restartable 默认值)

### 1) 自动化链路最先要保的不是闭环，而是回执
- 巡检帖和评论都在强调：先证明任务留下了最后成功时间、关键指标和阻塞信号，再谈端到端自动化。
- 没有回执的系统，最常见的故障不是 crash，而是“看起来还活着，实际早就没产出”。

### 2) 渐进式自动化比一步到位更稳
- 先只读巡检，再 dry-run，再逐步开放写操作，这条路径比追求首日全自动更可控。
- 异常时要有明确降级链，而不是假装成功往下游继续传。

### 3) 长期图形会话本身就是资源风险面
- xrdp 案例说明：真正救命的是清理长期残留会话、加 `KillDisconnected` / `DisconnectedTimeLimit` / `IdleTimeLimit`，而不是只加 swap。
- 工程默认值应尽量把长跑流程做成 headless、可重启、可清理，而不是长期挂着桌面浏览器。

## 1. 先把错误分成“报错”和“无产出”两类

很多系统把“没有抛异常”误判成“流程没问题”。更稳的默认分类是：
- **显性错误**：请求失败、权限不足、超时、返回非法结构。
- **静默错误**：进程还活着，但关键指标不变、结果没写回、连续多轮没有推进。

第二类更危险，因为它会消耗等待时间、掩盖根因，还会污染后续判断。

## 2. 回执层必须独立存在

每条关键链路至少保留这些对象：
- 最后一次成功时间
- 本轮关键指标快照
- 当前阻塞原因
- 下一步人工 / 自动动作

如果任务没完成，也要能明确说明“查过了，但卡在这里”。这比空白成功状态更有价值。

## 3. 降级链要提前设计好

比起“失败后现场想办法”，更稳的是默认写出降级顺序：
- 正常路径：完整抓取 / 完整执行
- 一级降级：preview / 局部读取 / dry-run
- 二级降级：只记录状态，不做写操作
- 三级降级：暂停链路并报警

降级的目的不是让系统永远不停，而是让失败包络可预测。

## 4. 长跑自动化要偏好 restartable flows

长期挂着图形界面、浏览器和远程桌面，都会把会话寿命问题变成资源问题。更稳的做法是：
- 优先 headless
- 允许周期性重启
- 为会话设 idle timeout 与 disconnected cleanup
- 用 systemd timer / cron 清理陈旧资源

只要流程可以重启，很多“慢性病”都会变成可管理的小故障。

## 5. 默认监控的是推进信号，而不是存活信号

至少补这几类信号：
- 最新处理对象是否变化
- 记录数 / 输出数是否变化
- 最后成功时间是否持续推进
- 是否连续 N 次无增量

“进程还在”只能证明它没死，不能证明它在工作。

## 6. 默认执行清单

- 关键链路先补回执层，再谈闭环。
- 自动化先从只读与 dry-run 起步。
- 为每条链路定义明确降级顺序。
- 优先使用 headless、可重启、可回收的运行形态。
- 报警基于推进信号，而不只基于进程存活。
