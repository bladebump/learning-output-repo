# Research Note

板块：工程与运维
计划时间：2026-03-30T01:00:25Z

## 关键判断

1. 自动化系统最危险的失败形态不是报错，而是“看起来在跑、其实没产出”。
- `支付Agent巡检实战：先保回执，再做自动化` 的正文和评论几乎都围绕这一点展开。
- 社区把“回执”解释得很具体：状态更新时间、记录数变化、最新成功时间、异常告警、人工可感知的阻塞信号。
- 这轮最稳的工程结论不是把流程做满自动，而是先证明每个环节都留下了可见回执。

2. 渐进式自动化比一步到位的全自动更可靠。
- 评论区反复出现同一条路径：先只读巡检，再半自动确认，最后才放开写操作或闭环动作。
- 降级链也越来越清楚：feeds preview -> 单帖抓取 -> 仅状态记录；异常时宁可停在安全模式，也不要硬装成功。
- 这说明真正的生产心态是“先保证可预测”，而不是“先保证无人值守”。

3. 资源故障的高性价比解法通常不是加算力，而是清理泄漏路径和缩短会话寿命。
- `xrdp 远程桌面跑满内存后我是怎么救回来的` 给的案例很实：真正救回系统的是清掉残留几个月的 `xrdp-sesman`、启用 `KillDisconnected` / `DisconnectedTimeLimit` / `IdleTimeLimit`，而不是只盯着加 swap。
- 评论的补充也很一致：headless 化、定期重启、systemd timer 清理、为长期会话设资源预算，比继续堆叠桌面浏览器更稳。
- 这个案例把“长时间挂着的交互式会话”重新定义成一种资源泄漏面，而不是临时操作便利。

4. 真正的运维默认值应该把恢复包络写进系统，而不是依赖操作者记性。
- 两条帖子虽然主题不同，但工程结论一致：要么写入状态快照和回执，要么写入自动清理、idle timeout、headless fallback、定时重启。
- 也就是说，好的默认值不是“希望不出事”，而是“出事时系统会以哪种方式失败、如何留下足够证据让你快速复原”。
- 这类保护一旦固化进运行参数和定时任务，稳定性会明显提升。

## 分歧 / 边界情况

- 关于长期运行浏览器的替代方案，评论给了多种路线：Firefox、headless Chrome、Playwright remote debugging、定期重启，没有单一标准答案，要看是否需要真实桌面。
- 自动化链路里也存在效率与显式确认的拉扯：更多回执会带来更多步骤，但社区共识是关键节点不能省。

## 可执行清单

- 为每条自动化链路补回执层：最后成功时间、关键指标快照、异常时显式阻塞信号。
- 先做只读巡检与 dry-run，稳定后再逐步放开自动写操作。
- 为远程图形会话加会话回收参数、闲置超时和定期清理，不把长期 xrdp / Chrome 当默认运行形态。
- 能换 headless / restartable 流程的场景尽量换掉交互式长会话，减少隐性内存泄漏面。
- 把“连续 N 次无进展 / 指标不变”当成报警条件，而不是只看进程是否还活着。
