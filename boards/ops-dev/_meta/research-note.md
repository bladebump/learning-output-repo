# Research Note - 工程与运维

## 关键结论

1. Tool-making 比 tool-use 更像下一代 agent 的杠杆能力。
- `Large Language Models as Tool Makers` 的核心转向是：任务不再只走 `Task -> LLM -> Output`，而是先让模型分析任务、生成专用工具、测试修正，再让工具执行。
- 这意味着真正的能力增益来自“把重复工作编译成可复用工件”，而不是每次都让模型从头推理。

2. 这条路线最适合高重复、可验证、可缓存的任务。
- 一旦任务存在重复输入模式、明确验收标准或固定转换流程，临时造工具就可能同时换来更高准确率、更低 token 成本和更强一致性。
- 与其说是“更聪明”，不如说是把推理结果沉淀成了局部基础设施。

3. Tool-making 的工程关键不在生成本身，而在测试、版本和复用策略。
- 如果没有自动测试、最小验收、缓存命名和版本管理，模型生成的工具很快会变成另一层不可维护的噪声。
- 因此它应进入工程纪律：生成 -> 运行样例 -> 校验 -> 缓存/登记 -> 下次复用。

4. 不是所有任务都值得造工具。
- 一次性、探索型、边界极多且验收模糊的任务，继续直接推理通常更便宜。
- Tool-making 适合的是“先贵一次，后面越来越便宜”的工作，不适合为了炫技把所有任务都包一层代码。

## 分歧与边界

- 自动生成工具会扩大执行面，若缺乏沙箱和回滚，收益可能被安全与维护成本吃掉。
- 论文式成功不自动等于生产可用；本地环境、依赖管理和错误处理都需要额外工程化。

## 可执行清单 / 决策

- 先识别高重复、可验证任务，再考虑 tool-making。
- 为生成工具补齐样例测试、验收条件和缓存命名规则。
- 把生成后的工具登记到可审计位置，避免“造了但找不到”。
- 对一次性任务维持直接推理，不盲目引入工具层。
- 在权限、沙箱和依赖管理明确前，不让自动生成工具直接碰高风险动作。
