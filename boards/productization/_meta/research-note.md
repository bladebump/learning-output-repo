# 研究笔记：垂直产品化与专家共创

## 关键结论

### 1. 真正高价值的需求，往往只会在真实使用里暴露
- FitCoach 用 18 天从零上线，最关键的转折不是写完功能，而是 Day 13-14 让业务 owner 飞先生亲自上手，一天给出 20+ 个修改点，团队当天完成多轮修复与部署。
- 帖子反复强调的问题不是“功能没想全”，而是“用了才知道”：按错完课无法回退、找不到新增按钮、日期对不上、付款无法部分支付。这类问题靠事前写规格很难完整发现。
- 评论区把这件事概括成“用真实输入取代想象中的输入”，并把这种高频反馈回路视为整个案例最核心的方法论。

### 2. 不会写代码的业务 owner 依然能主导产品质量
- 飞先生不写代码，但他是七家蛋糕店的经营者，知道真实运营里哪些流程最痛：学员管理、排课、收费、LINE OA 自动回复、场地管理、CSV 导入。
- 这说明 AI 在垂直产品化里的价值，不是替代领域专家判断，而是缩短“专家想法 -> 可用系统 -> 真实反馈”的循环时间。
- 评论区多次把这个关系类比成“产品镜像业务认知，再由业务方纠偏”，本质是领域专家与 Agent 的共创，而不是单向交付。

### 3. 窄场景垂直 SaaS 可以在极低成本下快速上线
- 该系统围绕一个清晰场景收敛：教练/学员运营管理，而不是泛化教培平台。
- 技术栈是 React + TypeScript + Supabase + Vercel + LINE Messaging API，作者明确写了月费 NT$0，这种低成本组合说明：只要范围足够窄、反馈足够快，生产级 MVP 完全可能在轻栈上完成。
- 帖子给出的时间线也说明节奏重点在“先做出核心路径，再补管理、登录、集成和导入能力”，而不是一次铺满全部需求。

### 4. 上线前的成败常常取决于环境与集成 preflight，而不只是功能
- 案例里最具操作价值的坑有四类：第一版不能只交 50%-60% 半成品；`toISOString()` 在台灣时区把日期推前一天；Supabase Project ID 的 `l/i` 容易误输；LINE Webhook 的 chatMode 必须从“聊天”切到“Bot”。
- 这些问题共同说明：垂直场景交付不是写完 CRUD 就结束，真正影响可用性的往往是时区、标识符、第三方平台模式、当地用户沟通工具偏好等环境细节。
- 评论区进一步提醒了本地化维度：台灣用户高度依赖 LINE、繁简体与时间格式也需要针对地区处理。

## 分歧 / 边界情况

- 评论里有人追问 20+ 反馈中有多少是功能 bug、多少是体验问题；这说明快速迭代虽然有效，但仍需要区分缺陷类型，否则容易高估“改得快”而低估“改得准”。
- 另一个高频追问是：一天内修 20+ 项后如何避免“改了 A 坏了 B”。这表明用户反馈闭环如果没有最小回归测试与验收清单，会很容易把速度换成新的不稳定性。
- 低成本轻栈适合窄场景 MVP，但不自动等于可复制到所有场景；一旦需求跨店、跨地区、跨支付/消息生态，前置集成复杂度会明显上升。

## 可执行 checklist / 决策

- 先围绕一个业务 owner 最痛的核心流程做最小上线，不要一开始做成大而全平台。
- 第一版必须能跑通主路径，再尽快交给真实使用者，而不是长时间停留在规格讨论。
- 把“环境 preflight”写成固定清单：时区、第三方 webhook 模式、关键 ID 校验、语言/本地化、登录与权限流程。
- 每轮用户反馈至少拆成两类：功能缺陷 / 体验优化，并保留最小回归测试，避免快速迭代造成二次破坏。
- 把真实踩坑写入长期规则库，下次同类产品直接带着 checklist 开工。
