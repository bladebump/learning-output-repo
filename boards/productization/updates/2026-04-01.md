# 2026-04-01--垂直产品化与专家共创：学习增量

这轮材料把“垂直 AI 产品化”的重点讲得很实：真正决定上线速度和产品方向的，不是规格文档写得多细，而是业务 owner 是否能尽快上手、当天给出真实反馈。

## 关键结论

### 1) 真实使用比长时间规格讨论更能暴露高价值问题
- FitCoach 在 Day 13-14 由业务 owner 一天打出 20+ 个修改点，很多都是“用了才知道”的问题：按钮找不到、日期错位、付款流程不顺、操作无法回退。
- 这类问题几乎不可能靠纸面规格完整预判，所以第一版的价值不是“完美”，而是足够可用到能被真实业务撞出问题。

### 2) 领域专家不需要会写代码，也可以成为产品质量的主导者
- 飞先生不会写代码，但他最懂七家门店的真实运营流程；Agent 的作用是把需求快速变成可操作系统，再让领域知识反向纠偏产品。
- 因此“专家共创”不是附属环节，而是垂直 SaaS 的主设计机制。

### 3) 窄场景、轻栈、快部署，是当前垂直 MVP 的高胜率组合
- React + TypeScript + Supabase + Vercel + LINE Messaging API 的组合，在窄流程里能很快上生产。
- 真正重要的不是技术炫技，而是是否围绕一个高频工作流收敛，而不是一开始做成大而全平台。

### 4) 上线前必须把环境与集成 preflight 写成清单
- 这次案例最可复用的教训都在环境细节里：`toISOString()` 时区问题、Supabase Project ID 易混淆、LINE Webhook 需要切 Bot 模式、地区沟通工具和语言习惯要本地化处理。
- 功能完成并不等于可用，环境 preflight 才是很多垂直项目真正的分水岭。

## 需要做的决策 / checklist

- 第一版只做一条业务主路径，但必须可被真实用户立即试用。
- 用户反馈至少分成“功能缺陷 / 体验优化”两类，避免所有问题混在一起处理。
- 上线前固定检查：时区、关键 ID、第三方 webhook 模式、语言与地区适配。
- 每轮快速修复后保留最小回归检查，避免“改了 A 又坏 B”。
- 把真实踩坑沉淀成长期 checklist，别让同类错误反复出现。

## 风险 / 边界情况

- 快速迭代很容易掩盖回归风险，所以必须配最小 smoke test。
- 低成本轻栈适合窄场景 MVP，不代表天然适合所有复杂业务。
