# 研究笔记：提示工程与代码生成

## 关键结论

### 1. 比起泛泛的“step by step”，代码任务更需要样例轨迹锚定
- 原帖作者在滑动窗口最大值题上比较了两种方式：直接写代码容易漏边界，而“先画窗口移动示意图、列出每一步状态”可以一次写出 O(n) 的单调队列解。
- 作者给出的最强提示词不是 `let's think step by step`，而是 `let's trace through an example`，核心作用是把推理锚定到一个可执行路径上。
- 多条评论都认同这一点：trace 并不是让模型更啰嗦，而是强迫它做状态快照，减少自由发挥空间。

### 2. 结构化中间态能把复杂任务从“玄学”变成“可检查”
- 评论区里关于 API 链最有操作价值：不要只说“分步思考”，而是要求模型先构造 A 请求参数、验证 A 返回结构，再用 A 的字段去构造 B 的过滤条件。
- 这说明 structured intermediate states 的关键不在于多写几步，而在于每一步都交代输入、输出、验证点和预期返回形状。
- 一旦中间态被显式写出来，代码、API、多跳任务都更容易定位到底是思路错还是实现错。

### 3. 先暴露边界条件，再写实现，可以显著提高首轮正确率
- 评论里一个高频补充是：在写代码前，先让模型列出空值、并发、时区错位等 edge cases，或者先写伪代码 / 流程图 / 测试样例，再进入实现。
- 这本质上是在把隐藏假设外显化，与 TDD / pre-mortem 很接近。
- 对代码生成来说，先穷举边界与测试路径，往往比“先生成再修补”更省轮次。

### 4. CoT 在这里的真正价值，是降低自由度并提升可验证性
- 多条评论都指出：泛化 CoT 容易写成“思考散文”，而 trace/example/执行计划/伪代码这些具体锚点会收窄输出空间。
- 换句话说，好的 coding prompt 不是鼓励模型“多想一点”，而是要求它把自己准备怎么做、每步依据什么做、会在哪些地方翻车，先写出来给人检查。
- 这也解释了为什么同样是 CoT，编程任务需要更偏工程化的约束语句。

## 分歧 / 边界情况

- 评论里也提出疑问：当问题变成抽象系统设计（如分布式缓存）时，单个样例 trace 可能不够，需要改成执行计划、接口契约、组件交互图等更高层锚点。
- 部分评论存在编码/乱码问题，可读性一般，因此可用证据主要来自原帖与几条清晰评论。
- 如果中间态过于冗长，也可能带来 token 成本上升和注意力分散，所以需要在“可验证”与“过度细化”之间取平衡。

## 可执行 checklist / 决策

- 代码任务默认先要求一个具体样例 trace，再进入实现。
- 对多步 API / 数据处理任务，明确每一步输入、输出、验证条件与返回结构。
- 在写实现前先列 edge cases、伪代码或最小测试样例，防止隐含假设漏掉。
- 对抽象设计问题，把锚点从“样例输入”升级为“组件职责、接口契约、状态流转”。
- 把 CoT 看成约束与可验证机制，而不是鼓励模型生成更长的自述文本。
