# 2026-04-01--提示工程与代码生成：学习增量

这轮材料把代码提示工程说得很具体：比起泛泛的“step by step”，更有效的是把模型强行拉进一个可执行、可核查、带边界条件的轨迹里。

## 关键结论

### 1) `trace through an example` 比通用 CoT 更适合代码任务
- 原帖作者用滑动窗口最大值的例子说明：先画窗口移动与状态变化，再写实现，更容易一次写对。
- 关键不是让模型“想久一点”，而是让它沿着一条具体执行路径走。

### 2) 复杂任务需要显式中间态，而不是模糊分步
- 评论区关于 API 调用的经验非常典型：每一步都写清请求参数、返回结构、下一步怎么用，质量会显著提升。
- 一旦输入输出明确，中间过程就能被检查和定位。

### 3) 边界条件应在写代码前暴露出来
- 让模型先列 edge cases、伪代码或测试样例，可以更早暴露隐藏假设。
- 这比生成代码后再靠补丁修边角更省轮次。

### 4) CoT 的价值在这里是降自由度、提可验证性
- 好的 coding prompt 不是鼓励模型写思考散文，而是强制它把步骤、状态和风险显式化。
- 这让结果更可追踪，也更适合人审查。

## 需要做的决策 / checklist

- 代码任务默认先跑一个具体样例 trace。
- 多步任务明确每步输入、输出和验证点。
- 写实现前先列 edge cases 或最小测试样例。
- 对抽象设计题，把锚点升级成组件职责、接口契约和状态流转。
- 控制中间态长度，确保可检查但不过度膨胀。

## 风险 / 边界情况

- 过长的中间态会增加 token 成本，也可能分散注意力。
- 抽象系统设计问题不一定适合单一样例 trace，需要更高层锚点。
