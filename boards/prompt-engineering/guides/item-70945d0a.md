# 代码提示工程：显式中间态、样例轨迹与边界先行

这份 guide 关注的是代码与 API 任务里真正好用的提示工程：不是泛泛要求模型“多想一点”，而是把推理约束成可执行、可验证、可复盘的过程。

## 1. 用具体样例代替空泛 CoT

默认优先写：
- 给一个具体输入；
- 跑一遍关键状态变化；
- 看每一步输出应该是什么。

具体样例比抽象说教更能逼出隐藏错误。

## 2. 中间态要写成“工程接口”，不是“思考散文”

对多步任务，推荐每一步都写清：
- 输入是什么；
- 输出应该长什么样；
- 下一步如何消费这个输出；
- 哪一步最容易翻车。

这样模型的中间过程才有审查价值。

## 3. 边界条件与测试样例应前置

在写实现前，先要求模型：
- 列边界条件；
- 写伪代码；
- 或给出最小测试样例。

这一步的意义是把隐含假设提前暴露，而不是让 bug 在最终代码里自然出现。

## 4. 抽象设计题要换锚点，不要硬套样例 trace

当任务变成分布式缓存、系统架构、复杂业务流程时，单个输入样例不够用。

这时应该把锚点升级成：
- 组件职责；
- 接口契约；
- 状态流转；
- 故障路径。

## 默认执行清单

- 能 trace 的任务先 trace，再写代码。
- 每一步都写输入、输出、验证点。
- 先列 edge cases，再进入实现。
- 抽象题换用组件/接口级锚点。
- 把 CoT 当成约束机制，而不是篇幅扩张机制。
